## 대표 사례 5가지

### 1. 우리 성과를 우리가 깎았습니다 — 평가셋 확대

예선 제출 당시 판정 일치율은 **95.5%** 였습니다. 좋은 숫자라고 생각했지만, 그 수치의 모수는 **22건**(30건 중 음성 8건 제외)이라 **1건이 4.5%p** 였습니다. 개선을 측정할 수 없는 자였습니다.

평가셋을 **120건**으로 늘리고, 시스템이 본 적 없는 **홀드아웃 30건**을 따로 만들었습니다.

```
기존 22건    95.5%   (21/22)
확대 112건   71.4%   (80/112)
홀드아웃      70.0%   (21/30)    ← 확대셋과 1.4%p 차이
```

**독립적으로 만든 두 세트가 1.4%p 안에서 만났습니다.** 우연이 두 번 같은 값을 내지는 않습니다. 실제 성능은 70% 근처였고 95.5%는 세트가 쉬웠던 것입니다.

이 발견이 없었다면 이후의 모든 개선을 잘못된 기준 위에서 측정했을 것입니다.

### 2. 가장 좋은 질문이 우리 가드레일에 걸려 죽고 있었습니다

사칭 문자에 대해 모델이 이런 질문을 만들었습니다.

```
"받으신 주소 nhis-refund24.com과 공식 주소 nhis.or.kr을 비교해 보셨나요?"
```

사칭 대응으로는 가장 좋은 질문입니다. 그런데 화면에는 전혀 다른 문장이 나갔습니다.

원인은 문장 수를 세는 정규식이었습니다. **도메인 안의 점을 문장 끝으로 셌습니다.**

```
[1] 받으신 주소 nhis-refund24
[2] com과 공식 주소 nhis
[3] or
[4] kr을 비교해 보셨나요        → "4문장" → 길이 초과 → 폴백
```

폴백 문장은 *"기관 이름이 보이지 않는다면 확인해 볼 신호입니다"* 였는데, 그 문자에는 기관명이 명시돼 있었습니다. **어르신이 읽으면 "있으니 괜찮다"로 읽힙니다.** 사칭 문자 앞에서 안심시키는 방향으로 작동하고 있었습니다.

**그리고 저장된 데이터에는 이 문제가 보이지 않았습니다.** 만들어졌다가 전부 죽어서 기록에 남지 않았기 때문입니다. 데이터만 봤다면 "모델이 그런 질문을 안 만든다"고 결론냈을 **생존자 편향**이었고, 라이브에서 직접 써 보고서야 발견했습니다.

수정 후 폴백률 **2.7% → 0.9%**(112건 중 3건 → 1건), 길이 초과로 인한 폴백 0건. 고친 뒤에도 *막아야 할* 문장이 여전히 막히는지 먼저 확인했습니다.

### 3. 데이터를 늘리면 안전장치가 자동으로 느슨해집니다

사기 사례 매칭에 하한선(`min_score`)을 두고 있었는데, 점수 계산에 IDF 가중이 들어 있었습니다.

```
_keyword_weight = log((N_DOCS + 1) / (df + 1)) + 1.0
```

사례를 51건 → 185건으로 늘리면 `log(N+1)` 비가 **1.323**, 즉 모든 단어의 가중치가 **32% 오릅니다.** 하한선 5.0은 그대로인데요. 그리고 우리가 하려던 일이 정확히 "코퍼스 수집"이었습니다.

재교정 곡선을 실측했더니 **더 나쁜 그림**이 나왔습니다.

```
정상 오판 0 을 유지하는 최소 min_score
  N= 51    확대셋  6.75   홀드아웃 11.00
  N= 80            13.75           12.25    ← 2.04배 뜀
  N=185            14.75           13.50
```

**로그를 따르지 않고 계단으로 뜁니다.** 최소 임계는 "가장 높은 점수를 받은 정상 케이스 하나"가 결정하는 극단값이라, 새 사례 하나가 특정 정상 문서와 강하게 겹치면 튀어 오릅니다.

정직하게 덧붙이면 — **당장 오판이 늘지는 않습니다.** 5.0에서의 실제 오판은 N과 무관하게 1건으로 불변입니다. 줄어드는 것은 **안전 여유**이고, 그게 6.75 → 14.75로 깎입니다. 그리고 **N=51인 지금도 5.0은 이미 부족합니다** — 정상 오판 1건이 이미 나고 있습니다.

이 발견 이후 하한선 결정 문서에 *"이것은 N=51에서의 5.0이지 영구 결정이 아니다"* 를 명시하고, 코퍼스 규모가 바뀌면 자동 회귀 검사가 실패하도록 걸었습니다.

### 4. 운영 데이터 262행을 지웠습니다

**세는 조건과 지우는 조건이 달랐습니다.**

```
세는 쿼리    where device_hash = X and created_at >= '15:40'   → 17행
지우는 쿼리  where device_hash = X                             → 262행
```

백업이 없어 복구하지 못했습니다. 더 나쁜 것은 **삭제 직전에 `262`를 화면에 출력해 놓고 같은 명령 블록에서 곧바로 DELETE가 나갔다**는 점입니다. 확인 출력과 삭제 사이에 아무것도 없었습니다.

> 확인을 '출력'하는 것과 '차단'하는 것은 다릅니다.

재발 방지를 문서가 아니라 도구로 만들었습니다. `--expect` 값과 실제 행 수가 다르면 아무것도 지우지 않고 중단합니다. 그리고 **백업을 임시 테이블에 실제로 복원해 행 수와 체크섬을 대조한 뒤에야** 삭제가 진행됩니다.

그 리허설은 다음 날 자기 결함을 잡았습니다 — CSV가 JSON 컬럼을 파이썬 `repr`로 저장해 복원이 불가능한 상태였는데, 리허설이 없었다면 "백업이 있다"고 믿은 채 지웠을 것입니다.

### 5. 허용 목록으로 뒤집었습니다 — 빠뜨렸을 때 어느 쪽으로 실패하는가

어떤 신호가 화면 단계를 올릴지 정하는 규칙이 처음에는 **차단 목록**이었습니다. "이 신호들은 올리지 마라"를 적는 방식입니다. 8/13에 이걸 **허용 목록**으로 뒤집었습니다 — "이 신호들만 올려라".

기능은 같습니다. 다른 것은 **빠뜨렸을 때 어디로 실패하느냐**입니다.

```
차단 목록   새 신호를 목록에 안 넣으면 → 화면이 조용히 더 무서워진다
허용 목록   새 신호를 목록에 안 넣으면 → 화면이 그대로다
```

어휘와 신호는 앞으로 계속 늘어납니다. 그때마다 목록을 갱신하는 것은 사람이고, 사람은 빠뜨립니다. **서버가 모르는 키는 승격될 수 없어야** 합니다.

당시 근거는 원칙뿐이었는데, 8/21 측정에서 숫자가 나왔습니다.

```
확대 평가셋 정상 37건
  주의 신호가 붙은 건        11건
  화면 단계가 실제로 오른 건   2건
  ★ 허용 목록이 막은 것        9건
```

이 9건은 "판정이 틀린 것"이 아니라 **애초에 화면까지 오지 못한 것**입니다. 그래서 신호 기준으로 세면 29.7%, 화면 기준으로는 5.4%가 나옵니다. 두 숫자 다 맞고, **어르신이 보는 것은 화면 쪽**입니다.

| 확신 상태의 오답 근거 | **0건** | **0건** |

가장 중요한 줄은 마지막입니다. **"확신을 준 상태에서 틀린 근거를 붙인 것"이 0건**이어야 합니다. 근거를 못 찾는 것은 화면이 "못 찾았다"고 말하면 되지만, 틀린 근거를 확신과 함께 내미는 것은 되돌릴 방법이 없습니다.

정상 오판을 **두 줄로 적은 이유**가 있습니다. 화면은 5단계(`danger`/`warn`/`act`/`hold`/`ok`)인데, 주황색 **행동 안내(`act`)는 "사기입니다"가 아니라 "인증번호를 넣기 전에 한 번 보세요"** 입니다. 이걸 사기 의심과 같은 칸에 넣으면 실제보다 나쁘게 보이고, 빼면 좋게만 보입니다. 그래서 둘 다 적습니다.

★ 세 건의 정체를 밝혀 둡니다. 확대셋의 `act` 1건은 **인증번호를 요구하는 정상 문자**이고, `warn` 1건은 **앱 설치를 요구하는 정상 문자**입니다. 둘 다 주의 표시가 오히려 정답에 가깝다고 판단했습니다. 홀드아웃 1건은 사기 사례와 어휘가 겹쳤습니다.

★ 그리고 이 표에서 **가장 중요한 것은 화면과 신호가 다르다는 사실**입니다. 확대셋 정상 37건 중 **11건에 주의 신호가 붙지만, 화면 단계를 실제로 올린 것은 2건**입니다. 나머지 9건은 `ATTENTION_KEYS` **허용 목록**이 막았습니다 — 목록에 없는 신호는 단계를 올리지 못하므로, 새 신호를 추가해도 화면이 저절로 무서워지지 않습니다. 신호 기준으로만 세면 29.7%, 화면 기준으로는 5.4%이고, **어르신이 보는 것은 화면 쪽**입니다.

**동시 접속** — 비동기 핸들러 안의 동기 LLM 호출을 제거하고 워커·스레드를 조정한 결과, 동시 3명 기준 텍스트 여정 14.77초 → 5.46초, 사진 경로 24.14초 → 10.70초. 전 구간 실패 0건.

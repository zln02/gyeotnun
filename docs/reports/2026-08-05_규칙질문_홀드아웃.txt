【 한 줄 요약 】
  규칙 질문은 4지표를 다 통과했지만, 그 지표가 잡지 못하는 실패가
  홀드아웃에서 드러났다. 정상 안내문 1건(H05)이 "의심"으로 표시됐다.
  ★ 절대조건 위반. "정상 오판 0건"은 복지로 밖에서 성립하지 않는다.

PART 1.  규칙 기반 질문 생성 재측정 (평가세트 30건)
────────────────────────────────────────────────────────────────

■ 1. 4지표 통과율

  지표              LLM      규칙
  ─────────────────────────────────
  판정 안 함       1.000    1.000
  2문장 이내       1.000    1.000
  신호 대응        0.833    1.000    (분모 6건)
  확인 가능        0.733    1.000
  ─────────────────────────────────
  전부 통과        0.700    1.000
  평균 문장수       1.47     2.00

  생성 시간        9.47초   0.00005초   (약 19만배)

  ★ 이 100% 를 그대로 믿지 마라 — 아래 5번 참고.


■ 2. LLM 필요율 — 정의를 바로잡았다

  (나) 규칙 질문이 4지표에 미달한 비율  ← 정식 정의
       = 0/30 = 0.0%

  (가) 근거 문서가 검색된 비율          ← 기각된 정의
       = 27/30 = 90.0%

  ※ 벤치 스크립트가 여전히 (가) 로 집계하고 있어 로그에 90% 가 찍혔다.
    스크립트를 고쳐 두 정의를 함께 출력하도록 했다(재실행은 안 했다 —
    LLM 30콜 비용이 들고, 원자료로 재집계가 가능하기 때문).


■ 3. 정상 10건 의심 유도 : 0건

  규칙 질문이 정상 안내문에 의심 신호를 붙인 경우 없음.
  → 단, 이건 평가세트의 정상 10건(전부 복지로) 이야기다. PART 2 를 보라.


■ 4. 신호 검출 현황

  사칭 10건 → 미검출 0건    (10/10 검출. 가장 중요한 부분)
  경계 10건 → 미검출 5건    (B01~B05)
  정상 10건 → 미검출 9건    (정상이므로 미검출이 정상 동작)

  경계 10건 상세
    B01~B05  신호 없음
    B06  urgency        B07  loan_bait      B08  agency_money
    B09  personal_info  B10  agency_money


■ 5. ★ 100% 를 신뢰하면 안 되는 이유 (스스로 밝힘)

  4지표 중 2개는 규칙 질문 입장에서 사실상 자동 통과다.

    · 지표2(2문장 이내) — 템플릿을 2문장으로 썼으니 항상 통과한다.
      실제로 규칙의 평균 문장수는 2.00 으로 상한에 딱 붙어 있다.
    · 지표4(확인 가능)  — 템플릿마다 행동 동사와 확인 대상을 넣어
      두었으니 항상 통과한다.

  즉 "규칙 100%" 는 내가 정한 채점 기준을 내가 만든 템플릿이 만족한
  것에 가깝다. 이 숫자를 근거로 LLM 을 걷어내면 위험하다.
  지표3(신호 대응)의 분모도 6건뿐이라 통계적으로 얇다.

  → 결론: 규칙 질문이 LLM 을 대체할 수 있다고 아직 말할 수 없다.


■ 6. 템플릿 작성 시 평가셋을 참조했는가

  참조하지 않았다.
  이전에 평가셋 실패 케이스(S06/S09/S10)를 보고 사전을 고친 적이 있어
  git checkout 으로 되돌렸고, 공개 자료(금융감독원·경찰청)의 수법 분류만
  보고 다시 작성했다. 잔여 참조 0건을 확인했다.

  주목할 점: 공개 분류에서 출발했는데도 같은 3개 범주가 다시 나왔다.
  평가셋을 봐서 얻은 게 아니라 실제로 흔한 수법이었다는 뜻이다.


■ 7. 부수 발견 — 프로덕션 버그 (수정 안 함)

  services/prompt_chain.count_sentences() 가 마침표를 무조건 문장
  구분자로 센다. 그래서 "go.kr" 같은 도메인이 들어간 1문장을 2~3문장으로
  세고, 불필요한 재생성이 일어난다.

  실측: 이번 30건에서 재생성 12회 중 too_long 9회. S08·B08 은 3회 모두
  실패해 폴백으로 떨어졌다(GN-001 2건).

  → prompt_chain.py 는 건드리지 말라고 하셔서 고치지 않았다.
    채점기에서는 도메인 마침표를 보호해 LLM·규칙 양쪽에 똑같이 적용했다.

■ H05 실패 원인 — 규칙 질문이 아니라 사기사례 매칭기다

  원문: "기초연금 지급일 안내입니다. 매월 25일 등록하신 계좌로
        입금되며, 변경 사항이 있으시면 주민센터를 방문해 신청하실
        수 있습니다."

  계층별 추적
    detect_signals()    → contact_in_image (severity=info) → 판정 영향 없음
    규칙 질문 생성      → 중립적 질문 생성 → 판정 영향 없음
    match_scam_cases()  → 2건 매칭 (attention) → ★ 이것이 의심 판정 유발

  오매칭된 사기 사례
    1) 저금리 대환대출 빙자 + 가상계좌 이체 사례
    2) 통장협박(계좌 소액 입금 후 지급정지) 사례

  둘 다 H05 와 수법이 전혀 다르다. "정부·계좌·지급·신청" 같은 일반
  어휘가 겹쳐서 걸렸다.

  → 지시하신 대로 '계좌' 과잉반응은 실재했다. 다만 과잉반응한 주체가
    질문 생성기가 아니라 사기사례 매칭기였다.

  정상 "등록하신 계좌로 입금됩니다"  vs  사칭 "안전계좌로 보내세요"
  → 현재 시스템은 이 둘을 구분하지 못한다.


■ 유사도 분포 — 코퍼스 편중이 수치로 확인됐다

                        최소      중앙      최대
  기존 정상 10건(복지로) 0.6820   0.7677   0.8601
  홀드아웃 5건(5개 기관) 0.5864   0.6680   0.7169

  홀드아웃의 최대값(0.7169)이 기존 정상의 중앙값(0.7677)에도 못 미친다.
  확신 임계값 0.679 를 넘긴 건 2/5 뿐이다(기존은 10/10).

  H04 는 최상위 매칭이 「조현병」 문서였다 — 관련 문서 자체가 코퍼스에
  없다는 뜻이다. 검색 튜닝으로는 해결되지 않는다.


■ 절대조건 준수 확인

  1. 코퍼스에 넣지 않았다 — 스크립트가 매 실행마다 코퍼스 전체를
     검색해 확인한다. 결과: 섞인 홀드아웃 없음.
  2. 기존 30건과 합치지 않았다 — 별도 파일·스크립트·결과다.
  3. 이 5건을 보고 코드를 고치지 않았다. 실패를 실패로 남긴다.

결론 / 다음 우선순위
────────────────────────────────────────────────────────────────

  · 기획서에 "정상 오판 0건" 이라고 쓸 수 없다. 복지로 밖에서 깨진다.
  · 규칙 질문의 100% 는 채점 기준이 느슨해서 나온 값이다. 이걸 근거로
    LLM 을 제거하지 마라.
  · 정상 오판의 직접 원인은 OCR 도 임베딩도 아닌 match_scam_cases()
    오탐이다. 30건 평가에서 경계 7건이 의심으로 간 것과 같은 원인이다.

  다음 순서 제안 (결정은 사용자)
    1) match_scam_cases() 매칭 방식 재검토
       — 단, 임계값을 올리면 사칭 검출이 떨어진다. 30건+홀드아웃 5건을
         함께 보고 판단해야 한다.
       — ★ 홀드아웃 5건에 맞춰 조정하면 검증이 아니라 짜맞추기가 된다.
    2) 코퍼스 다변화 (건강보험공단·국민연금공단·질병관리청)
       — H04 처럼 문서가 아예 없는 경우는 검색으로 못 고친다.

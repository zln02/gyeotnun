PaddleOCR CLI 튜닝 — 전처리·검출기 (2026-08-06)

  실험 전용 · 코드 미변경(api/ 동결) · 커밋 없음 · 시간 상한 3시간 내(약 1h20m 소요).
  하네스는 이전 재측정과 동일 데이터셋·지표(곁눈_평가세트_30건.csv +
  ocr_eval{,_hard}), 말풍선 필터는 전처리된 이미지에 같은 좌표계로 적용.

0. 먼저 (질문 0)

- 말풍선 영역 필터는 이미 PaddleOCR 파이프라인에 적용돼 있었다. 재측정 벤치가
  local_ocr._keep_bubble_boxes(easyocr 0.730→0.885 를 만든 그 로직)를 써서 말풍선
  텍스트를 collect_evidence 에 넣었다. 그 효과(paddle 기준):
  clean 인식 0.951→0.951(변화 없음), hard 인식 0.822→0.901(+0.079).
  (easyocr 의 0.730→0.885 는 ocr_testset(24장)이라는 별개 데이터셋 수치라 폭은
  직접 비교되지 않는다 — 로직은 동일.)
- "hard set 0.733" 은 근거검색 성공률이다 (인식 정확도가 아니다).
  hard 인식 정확도는 0.901(말풍선)/0.822(무필터).
- hard set 근거검색 성공률 = 0.733, hard set = 30장(정상10·사칭10·경계10).

1. 결론 (한 줄)

일반 전처리와 검출기 파라미터 튜닝 어느 것도 hard set 의 근거검색을 baseline
위로 올리지 못했다. 원인은 OCR 품질이 아니라 검색/코퍼스 계층이었다(아래 §5).
정상 10건 오판 0건은 시험한 모든 조합에서 유지됐다.

2. 전처리 실험 (일반 기법만) — 켜고/끄고, clean+hard 동시

tuning-hard 15 + clean 30. deskew·denoise·clahe·upscale 순서.

| 전처리 | clean 인식 | clean 근거검색 | hard 인식(말풍선) | hard 근거검색 | 정상오판 | 판정 |
|---|---|---|---|---|---|---|
| baseline | 0.951 | 0.800 | 0.894 | 0.800 | 0 | — |
| deskew | 0.951 | 0.800 | 0.607 | 0.400 | 0 | 기각(hard 급락) |
| clahe | 0.897↓ | 0.700↓ | 0.876 | 0.800 | 0 | 기각(clean 하락) |
| denoise | 0.957 | 0.800 | 0.819 | 0.733↓ | 0 | 기각(hard 근거검색 하락) |
| upscale | 0.979↑ | 0.833↑ | 0.821 | 0.733↓ | 0 | 기각(hard 하락, clean만 개선) |

- deskew 는 해롭다: 카톡 캡처는 기울지 않았는데 텍스트 레이아웃 기준 각도추정이
  멀쩡한 화면을 회전시켜 hard 근거검색을 0.8→0.4 로 반토막.
- clahe 는 clean 을 떨어뜨린다(대비 정규화가 깨끗한 이미지의 글자 경계를 흐림) → 기각 규칙.
- denoise·upscale 은 hard 근거검색을 오히려 낮춘다. upscale 은 clean 만 올린다.
- ★ hard 실패 이미지를 열어 파라미터를 맞추지 않았다 — 일반 기법의 on/off 만 봤다.

3. 검출기 파라미터 — clean 함께

text_det_thresh(기본0.3) · text_det_box_thresh(0.6) · text_det_unclip_ratio(1.5).

| 설정 | clean 인식 | clean 근거검색 | hard 인식(말풍선) | hard 근거검색 | 정상오판 |
|---|---|---|---|---|---|
| baseline | 0.951 | 0.800 | 0.894 | 0.800 | 0 |
| box_thresh=0.4 | 0.974↑ | 0.800 | 0.894 | 0.800 | 0 |
| box=0.4 + unclip=2.0 | 0.956 | 0.767↓ | 0.897 | 0.733↓ | 0 |
| unclip=2.0 | 0.934↓ | 0.767↓ | 0.897 | 0.733↓ | 0 |
| thresh=0.2 + box=0.4 | 0.973 | 0.767↓ | 0.897 | 0.800 | 0 |

- box_thresh 를 0.6→0.4 로 낮추면 clean 인식이 0.951→0.974 로 오르고(무해), 그 외엔
  전부 그대로다. 다만 hard 근거검색은 안 움직인다(튜닝 목표엔 도움 안 됨).
- unclip_ratio 를 키우면 clean·hard 근거검색이 함께 내려간다(박스를 과확장해 인접
  UI 텍스트를 본문에 끌어들임) → 채택 불가.
- 어떤 검출기 설정도 hard 근거검색을 baseline(0.8) 위로 올리지 못했다.

4. 홀드아웃 (질문 3)

hard 30장을 유형별 5:5 로 tuning 15 / validation 15 로 나눴다. 나눌 수는 있으나
표본이 작다(유형별 5장). 튜닝용에서만 조정하고 검증용은 마지막 1회만 측정.

| set | clean 근거검색 | hard 근거검색 | 정상오판 |
|---|---|---|---|
| tuning-15 (baseline) | 0.800 | 0.800 | 0 |
| validation-15 (baseline) | 0.800 | 0.667 | 0 |
| validation-15 (box_thresh=0.4) | 0.800 | 0.667 | 0 |
| full-30 (baseline) | 0.800 | 0.733 | 0 |

- 튜닝에서 baseline 을 이긴 조합이 없어 채택할 것이 없다. 검증셋은 baseline 과
  box_thresh=0.4 로 1회씩만 측정했고 hard 근거검색은 둘 다 0.667 로 동일(box04 는
  clean 인식만 개선하는데 그 개선은 검증 clean 에서도 0.974 로 재현됨).
- ★ 부산물 경고: 근거검색 지표가 15장에서 tuning 0.800 vs validation 0.667 로
  크게 갈렸다(full 0.733). n=15 에서 이 지표는 ±0.13 수준으로 불안정하므로,
  작은 hard 부분집합의 근거검색 개선/악화는 신중히 봐야 한다.

5. 왜 튜닝이 안 먹혔나 — 실패는 OCR 이 아니라 검색 계층 (진단)

full hard 30장에서 근거검색 실패(경계 제외, 경계는 근거없음이 정답) 4건:

| case | 유형 | OCR 인식정확도 | verdict_hint |
|---|---|---|---|
| S03 | 사칭 | 0.99 | no_source_found |
| S07 | 사칭 | 0.95 | no_source_found |
| S05 | 사칭 | 0.79 | no_source_found |
| S08 | 사칭 | 0.79 | no_source_found |

S03·S07 은 OCR 이 거의 완벽(0.99·0.95)한데도 근거검색이 실패한다. 글자를 정확히
읽었는데 collect_evidence 가 대응 공식 문서를 못 찾은 것이다 — OCR 문제가 아니라
검색/코퍼스 문제. 그래서 전처리·검출기 튜닝(=OCR 단계 개선)으로는 고칠 수 없다.
남은 2건(S05·S08, 0.79)만 OCR 열화가 섞여 있고, 이마저 일반 전처리로는 clean 을
깨지 않고 못 올렸다.

6. 절대 조건 (질문 4)

정상 10건 오판 0건 — 시험한 16개 조합 전부에서 유지. 위반 0. (측정 subset 의
정상분에서도 partially_matched 오판 없음.)

7. 정리

| 항목 | 결과 |
|---|---|
| 전처리 4종 | 채택할 것 없음 (deskew 유해, clahe clean 하락, denoise/upscale hard 하락) |
| 검출기 | box_thresh=0.4 가 clean 인식만 무해하게 +0.02, hard 개선은 없음 |
| 홀드아웃 | 튜닝에서 baseline 초과 조합 없음 → 채택 없음. 지표가 n=15 에서 불안정 |
| 절대조건 | 전 조합 정상오판 0 |
| 근본 | hard 근거검색 실패의 절반이 OCR 이 아닌 검색 계층(S03 0.99·S07 0.95) |

→ OCR 파이프라인 튜닝으로 hard set 을 끌어올리는 여지는 사실상 없다. hard 개선이
필요하다면 OCR 이 아니라 검색/코퍼스 쪽(사칭 문구에 대응하는 공식 문서 확보,
매칭 로직)을 봐야 한다. box_thresh=0.4 는 clean 인식을 무해하게 올리는 선택지로만
기록한다(이번 채택 아님).

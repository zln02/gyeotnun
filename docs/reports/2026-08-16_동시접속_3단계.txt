동시 접속 개선 — 3단계: 저장소 외부화 + purge + 문서 갱신 (2026-08-16, #33)
================================================================================

지시: _MEMORY_STORE → Postgres. checks · taggings 를 purge 대상에 추가(90일).
      마이그레이션 후 격리 환경에서 재시작 생존 확인.
      ★ 이게 끝나야 기획서 "90일 삭제" 서술 전체가 참이 된다.
      ★ 재시작 시 소멸하던 특성이 사라지므로 개인정보 문서 서술을 함께 갱신하라.

★★ 이 단계에서 2단계가 만든 라이브 회귀를 하나 발견해 고쳤다. 3절이 그 이야기다. ★★


1. 무엇을 바꿨나
----------------

  services/check_store.py (신설)   저장·조회·이력·태깅
  routers/checks.py                _MEMORY_STORE dict 제거 → check_store
  routers/dialogue.py              대화 이력을 DB 에 누적
  routers/verdict.py               판단·오판유형을 taggings 에 저장(전에는 저장 안 함)
  models/db.py                     checks.device_hash · checks.history ·
                                   taggings.device_hash 추가
  tools/migrate_check_store.py     기존 테이블에 컬럼 추가(멱등, 컬럼 추가만)
  tools/purge_old_records.py       checks · evidence · taggings 를 삭제 대상에 추가

  ★★ device_id 원문을 저장하지 않는다 ★★
    README 7장이 "사용자 식별은 device_id 의 SHA-256 해시만 사용합니다"라고
    못박고 있다. 메모리 dict 시절엔 원문을 들고 있었지만 프로세스 안에서만 살다
    사라졌다. **DB 로 옮기면서 원문을 넣었다면 그 서술이 그날로 거짓이 된다.**
    그래서 sha256 만 저장하고 소유자 대조도 해시끼리 한다.
    test_check_store.py 가 **행 전체를 문자열로 만들어** 원문이 섞였는지 단정한다
    (컬럼 하나만 보면 나중에 누가 컬럼을 더 만들어 흘릴 때 못 잡는다).

  ★ purge 삭제 순서: 자식(evidence·taggings) 먼저, 부모(checks) 나중.
    자식은 '자기 나이'가 아니라 **부모 checks 의 나이**로 지운다 - 그래야 부모가
    사라지는데 자식만 남는 상태가 안 생긴다. 순서가 거꾸로면 FK 위반으로
    트랜잭션 전체가 실패한다. 테스트로 단정했다.

3. ★★ 2단계가 만든 라이브 회귀 — 임베딩 검색이 통째로 죽어 있었다 ★★
----------------------------------------------------------------------

  [3-1] 어떻게 발견했나

    3단계 라이브 확인 중, 같은 문장인데 판정이 달랐다.
        재시작 전  hint=needs_check
        재시작 후  hint=no_source_found
    "판정이 재시작으로 바뀐다"는 그냥 넘길 수 없어서 파고들었다.

    같은 컨테이너 안에서 **새 프로세스로** 같은 입력을 계산하면 needs_check(refs 2),
    **HTTP 로 부르면** no_source_found(refs 1). 실행 중인 서버 프로세스에만 있는
    상태라는 뜻이다. 서버 로그를 직접 읽고서야 보였다:

        WARNING [official_search] 임베딩 검색 실패 - BM25 로 폴백:
                질의 임베딩 실패: Cannot copy out of meta tensor; no data!
        ERROR   [incident] code=EX-003

  [3-2] 원인

    services/embeddings.py 의 `_get_local_model()` 이 **락 없는 지연 싱글턴**이었다.
    요청이 이벤트 루프에서만 돌던 시절엔 로더에 들어오는 스레드가 프리워밍 스레드
    하나뿐이라 우연히 안전했다. **2단계에서 요청을 스레드풀로 빼자** 프리워밍
    스레드와 요청 스레드가 동시에 로더에 들어갔다. 둘 다 `is None` 을 보고 각자
    로드를 시작하고, 한쪽이 반쯤 만들어진 객체를 전역에 대입하면 그 프로세스는
    **재시작 전까지 영구히 BM25 로만** 답한다.

    ★ 실측으로 확인: 락 없는 구현에 8스레드를 넣으면 로드가 **8번** 일어난다.
      락을 넣으면 1번이다.

  [3-3] ★ 왜 안 잡혔나 — 이게 제일 중요하다

    - pytest 는 단일 스레드다 → 통과
    - render_verdict 142건 대조는 **별도 프로세스**(dump_screen_payloads)에서
      계산한다 → 통과
    - 2단계에서 한 "동시 12건 vs 순차 12건" 대조도 통과했다. 그 컨테이너는
      **프리워밍이 끝난 뒤** 요청을 받았기 때문이다. 경합 자체가 안 일어났다.
    - 그리고 이 버그는 **터지지 않는다.** 폴백이 있어서 사용자에겐 200 이 나가고
      근거 품질만 조용히 떨어진다. 화면은 멀쩡해 보인다.

    → 게이트 세 개를 다 통과하고 라이브에 나갔다. 잡은 것은 "판정이 두 번 다르다"는
      한 줄과, 그걸 그냥 넘기지 않고 서버 로그까지 읽은 것뿐이다.

  [3-4] 조치

    1) 이중 검사 락 + **완성된 객체만 전역에 대입**(실패해도 전역을 오염시키지 않는다)
    2) 재발 방지 테스트 2건 (tests/test_search_fallback.py)
       - 8스레드 동시 진입 시 로드가 **정확히 1회**인지 (락이 없으면 결정적으로 깨진다)
       - 로드 실패가 싱글턴을 오염시키지 않는지
    3) ★ 측정 스크립트가 스스로 검사하게 했다(bench_with_postgres.sh).
       임베딩이 폴백하면 **더 빨라진다.** 그걸 모르고 "개선됐다"고 적으면 거짓
       보고가 된다. 이제 폴백이 1건이라도 있으면 "측정 무효"를 찍는다.
    4) 검증: 운영 재시작 직후 **프리워밍과 일부러 경합시켜** 동시 5건을 쏘았다.
       5건 전부 hint=needs_check · refs=2 · 임베딩 실패 0건 · meta tensor 0건.

  [3-5] 영향 범위

    error_logs 에 EX-003 10건 + EX-006 1건이 남았다(2026-08-16 13:21~13:35 UTC).
    전부 내 3단계 확인 요청 시간대다. **행은 지우지 않았다** - 삭제는 사람이 정한다.
    ★ EX-006(검색 폴백률 경보)이 스스로 울렸다. 관측 장치는 제 일을 했다.
    2단계 배포(그 이전)의 라이브 확인은 needs_check + 실제 근거 링크가 나왔으므로
    그 시점엔 경합이 일어나지 않았다. 경합은 "요청이 프리워밍 도중에 도착할 때"만
    일어난다 - 재시작 직후에만 생기는 창이다.


4. 재시작 생존 확인 (지시받은 항목)
------------------------------------

  격리 환경(api/experiments/verify_restart_survival.sh):
      재시작 전  check 생성 → evidence(needs_check) → dialogue 1턴
      docker restart
      재시작 후  같은 check_id 로 evidence 정상 · dialogue 2턴 정상
                 이력 3줄이 그대로 남아 있음
                   질문1: ... / 사용자 답변: 문자로 받았어요 / 질문2: ...
                 ★ 다른 device_id → HTTP 404 (소유자 대조 유지)

  운영에서도 같은 흐름을 확인했다:
      POST → evidence → dialogue → verdict(taggings 저장) → **운영 컨테이너 재시작**
      → 같은 check_id 로 evidence 정상. 전에는 여기서 404 였다.
      다른 device_id → 404.

  운영 DB 확인:
      checks 행에 device_hash(64자 해시)만 있고 **원문 device_id 가 들어간 행 0건**
      taggings 에 decision=hold · error_type=number_condition · device_hash 있음

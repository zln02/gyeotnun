2. 대장 L4 — 유형으로 올렸습니다
================================

  docs/evaluation/본체결함_발견대장.md

      ### L4. 실행 시점에 달라지는 값을 문서에 고정하지 않는다

  경위를 그대로 적었습니다 — 8/21 에 321 을 세 곳에 박았고, 다음 날 실험 파일을
  하나 추가하자 322 가 됐습니다. test_experiment_db_guard 가 experiments/·tools/
  를 스캔해 파라미터를 만들기 때문입니다.

  ★ 핵심을 이렇게 적었습니다.

      나쁜 점은 틀린 것 자체가 아니라 **아무도 모른다는 것**이다.
      테스트는 계속 통과하고 화면도 정상이다. 문서만 조용히 어긋난다 —
      L1(옛 경로가 조용히 오답을 만든다)과 같은 실패 방식이고,
      대상이 코드가 아니라 문서일 뿐이다.

  규칙은 셋 중 하나를 고르는 형태로 만들었습니다.

      적지 않는다     늘 변하고 감시할 가치가 낮을 때 (테스트 수)
      날짜를 병기한다  그 시점 값이 의미 있을 때 (측정 결과)
      감시를 붙인다    바뀌면 재측정이 필요할 때 (코퍼스 규모 — M3)

  [2-2] ★ 같은 눈으로 README 를 훑었더니 두 개가 더 나왔습니다

      값                              방어
      ------------------------------  --------------------------------------
      테스트 수                       적지 않기로 함 (이번 조치)
      코퍼스 1,059 / 2,036 / 51       ✓ 감시 있음 — 바뀌면 회귀 검사 FAIL
      측정 결과 4지표                 ✓ "2026-08-21 기준" 병기
      확인 1건 원가                   ✓ "도입가 기준 · 정상가" 조건 병기
      ★ 처리 시간 5.46초 · 10.70초    날짜도 감시도 없음
      ★ 기각 7 · 정정 7 · 사고 1      기록이 늘면 어긋남 · 감시 없음

      → 이 둘은 아직 방어가 없습니다. 대장에 "남은 것" 으로 적어 뒀고,
        **이번에 고치지는 않았습니다** — 지시 범위 밖이고, 어떻게 방어할지
        (날짜 병기 / 세는 스크립트 / 그냥 두기)는 사람이 정할 일입니다.

      ★ 특히 "기각 7 · 정정 7" 은 이 저장소의 대표 서술이라 그냥 두면 계속
        늘면서 어긋납니다. 날짜를 붙이는 것이 가장 싸 보입니다.

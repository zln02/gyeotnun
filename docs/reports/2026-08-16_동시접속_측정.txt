동시 접속 측정 (#33) — 측정만. 설계는 사람이 정한다. (2026-08-16)
====================================================================

지시: 1) 측정 먼저 — 로컬에서 동시 1·2·3·5명 응답 시간·실패 건수. 라이브를 부하로
         때리지 마라.
      2) 측정 보고 후 대기. 저장소 외부화 방식(설계)은 사람이 정한다.
      3) 설계에 포함할 것 — purge 대상 추가 / 워커 증설 시 모델 메모리 / 테스트 DB 분리

아래는 전부 실측이다. 추정한 곳은 그렇다고 적었다.
설계안은 쓰지 않았다. 3번 항목은 "설계에 넣을 수치"만 재서 담았다.


0. 안전 조치 — 무엇을 안 건드렸나
---------------------------------

  - 라이브 URL(https://gyeotnun.duckdns.org)로는 한 건도 쏘지 않았다. 127.0.0.1:8000 만.
  - 워커·메모리 측정은 **같은 이미지로 새로 띄운 격리 컨테이너**에서 했다.
    별도 이름 · 127.0.0.1:8010 · --network bridge(compose 의 db 호스트명이 해석조차
    안 된다) · DATABASE_URL 을 sqlite 로 덮고 sqlite 가 아니면 즉시 중단.
    측정 후 컨테이너 삭제. 운영 컨테이너는 재시작조차 하지 않았다.
  - 운영 DB 오염 0 — 측정 전후 직접 셌다.
        error_logs 3 → 3     checks 0 → 0     events 3417 → 3417
        taggings 0 → 0       evidence 0 → 0

  ※ 한 가지는 밝혀 둔다. 127.0.0.1:8000 은 nginx 가 프록시하는 그 프로세스와
    같은 프로세스다. 측정 중 실사용자가 있었다면 그 순간 대기가 생겼다.
    공개 경로를 때리지 않았다는 뜻이지, 프로세스가 별개라는 뜻이 아니다.


1. 텍스트 경로 — 동시 1·2·3·5 (운영 컨테이너, 라운드 5회씩)
------------------------------------------------------------

'확인 1건' = POST /checks → GET /checks/{id}/evidence 전체 흐름.

  본문 A (주소 없음 — 로컬 CPU 만 탐)
     N   건수  실패 |  전체 중앙   전체 최대
     1     5     0  |    0.30s      0.73s
     2    10     0  |    0.41s      0.95s
     3    15     0  |    0.48s      0.97s
     5    25     0  |    0.60s      1.23s

  본문 B (주소 있음 — url_expand 가 외부로 HEAD 를 보냄)
     N   건수  실패 |  전체 중앙   전체 최대
     1     5     0  |    0.35s      0.39s
     2    10     0  |    0.63s      0.91s
     3    15     0  |    0.74s      1.19s
     5    25     0  |    1.21s      2.30s

  ★ 실패 0건. 어느 수준에서도 에러가 나지 않는다. 느려질 뿐이다.

  ★ 완전히 직렬이다. 동시 5명이 언제 끝나는지 찍어 보면 계단이 보인다.
      A  0.26 / 0.48 / 0.68 / 0.84 / 1.02   (간격 약 0.19s)
      B  0.39 / 0.84 / 1.13 / 1.42 / 1.74   (간격 약 0.34s)
    한 번에 한 건씩 처리된다. N 번째 사용자는 앞의 N-1 명을 다 기다린다.

  ★ 원인은 워커 1개만이 아니다. routers/checks.py 의 get_evidence 는 async def
    인데 그 안에서 search.collect_evidence() 를 **동기로** 부른다. 그동안 이벤트
    루프가 통째로 멈춘다. 워커를 늘려도 워커 하나 안에서는 여전히 직렬이다.

  ★ B 의 간격이 A 의 1.8배인 것도 같은 이유다. url_expand 의 외부 HEAD(최대 3초
    타임아웃)가 동기 소켓 호출이라 그동안 다른 사용자 전원이 멈춘다.
    지금은 대상 서버가 빨라서 0.15초쯤이지만, 느린 서버 하나가 걸리면
    **그 3초를 동시 접속자 전원이 함께 기다린다.**

3. 워커 증설 — ★ 지금 CPU 에서는 오히려 느려진다
-------------------------------------------------

격리 컨테이너에서 같은 사진 5장을 동시에 보냈다. 워밍업 12건을 먼저 보내
"워커마다 첫 요청이 느리다"는 설명은 배제했다(PREWARM 로그도 워커 수×2줄 확인).

  설정                          동시 5건 마지막 완료   컨테이너 메모리
  ---------------------------------------------------------------------
  워커 1 (현재 운영 설정)              11.46s              843 MiB
  워커 2                               17.25s             1.659 GiB
  워커 4                               20.11s             3.271 GiB

  ★★ 워커를 4배로 늘리니 2배 느려졌다. 메모리는 4배를 썼다. ★★

  이유: 요청 1건이 이미 CPU 2.5코어를 쓴다(오늘 측정 피크 248.8%, 4 vCPU).
       PaddleOCR·torch 가 내부적으로 여러 스레드를 쓰기 때문이다. 워커를 늘리면
       프로세스마다 그 스레드 풀을 또 만들어 4 vCPU 를 서로 뺏는다.
       ★ 즉 병목은 워커 수가 아니라 **4 vCPU** 다.

  스레드 수를 1로 묶고 다시 쟀다
  (OMP_NUM_THREADS · MKL_NUM_THREADS · OPENBLAS_NUM_THREADS · FLAGS_paddle_num_threads)

  설정                          단독 1건(중앙)   동시 5건 마지막   메모리
  ---------------------------------------------------------------------------
  워커 1 · 스레드 무제한 (현재)      2.32s           11.46s        843 MiB
  워커 1 · 스레드 1                  1.67s            8.20s        843 MiB
  워커 4 · 스레드 1                    -              5.02s       3.271 GiB

  ★ 스레드 제한은 혼자 쓸 때도 빨라진다(2.32s → 1.67s). 편차도 줄었다
    (1.88~2.52s → 1.66~1.72s). 이 박스에서는 트레이드오프가 관측되지 않았다.
  ★ 스레드를 묶은 뒤에야 워커 증설이 값을 한다(8.20s → 5.02s).
    순서가 거꾸로면 돈(메모리)만 쓰고 느려진다.

  ※ 이 측정은 OCR(사진) 경로다. 텍스트 경로(임베딩)에서도 같은지는 재지 않았다.
    설계 단계에서 따로 재야 한다. 지금 "확인 못 함"이다.


4. 모델 상주 메모리 — 워커 수만큼 복제되나?
--------------------------------------------

  ★ 복제된다. 공유되지 않는다.

  워커 1   842.8 MiB
  워커 2   1.659 GiB   (+855 MiB)
  워커 4   3.271 GiB   (+855 MiB/워커)

  워커 하나를 더 붙일 때마다 +855 MiB 다. 단독 워커 상주치(843 MiB)와 거의 같다 =
  공유되는 페이지가 사실상 없다. uvicorn --workers 는 각 워커에서 앱을 새로 임포트
  하고, PREWARM=1 이 워커마다 따로 모델을 올리기 때문이다(prewarm 로그가 워커 수
  ×2줄 찍힌다).

  ★ 부하 후 상주치가 올라가 고정된다. 운영 컨테이너 실측:
        측정 전 836 MiB → 텍스트 부하 중 838 MiB(변화 없음)
                        → OCR 부하 후 1.011 GiB 로 고정(반환 안 됨)
    2026-08-14 감사의 관측(837 → 1539 → 1139MB)과 같은 거동이다.
    ★ 계산에는 843 MiB 가 아니라 **워커당 1.0~1.2 GiB** 로 잡아야 한다.

  15.4 GiB 안에서의 계산 (현재 호스트 여유 10.6 GiB, gyeotnun 스택 전체 약 950 MiB)

    워커 1   0.85 ~ 1.2 GiB     ← 현재
    워커 2   1.7  ~ 2.4 GiB
    워커 4   3.3  ~ 4.8 GiB
    워커 8   6.8  ~ 9.6 GiB     ← 4 vCPU 라 의미 없다. 계산상으로만 적는다

  ★ 메모리는 워커 4까지 여유가 있다. 막는 것은 메모리가 아니라 CPU 다.
  ★ 단 2026-08-14 감사가 지적한 것이 그대로 남아 있다 —
    docker-compose.yml 에 mem_limit/cpus 제한이 **전혀 없다.** 워커를 늘리면
    같은 호스트의 다른 프로젝트(next-server 13000 · urban-immune 18000/18001 등)가
    그만큼 밀린다.

  ※ 공유가 가능한지: gunicorn --preload + UvicornWorker 로 마스터에서 모델을 올린 뒤
    fork 하면 COW 로 공유될 여지가 있다. **재 보지 않았다.** 추측이므로 수치를 쓰지
    않는다. 설계에서 채택하려면 그때 재야 한다.


5. purge 대상 — 저장소를 DB 로 옮기면 무엇이 늘어나나
-----------------------------------------------------

  지금 purge 대상 (tools/purge_old_records.py, 매일 04:00 cron)
      events · error_logs   ← 관측 로그 2종뿐

  지금 DB 에 안 들어가는 것 (전부 _MEMORY_STORE, 파이썬 dict)
      checks · evidence · taggings   ← 실측 0행 (오늘도 0행 확인)

  ★ 그래서 기획서의 "90일 삭제" 서술은 **지금은 관측 로그에만 참이다.**
    checks/taggings 가 DB 로 가는 순간, purge 에 그 테이블을 추가해야 비로소
    서술 전체가 참이 된다. purge_old_records.py 머리말에 이미 그렇게 적혀 있다:
    "이후 DB 로 옮기면 여기 추가할 것".

  DB 테이블 전체 (9개)
      checks · corpus · error_logs · events · evidence · taggings ·
      training_cards · users · weekly_reports

  설계 시 확인할 것 (측정 아님 — 목록만)
    - checks 는 masked_text 를 담는다. 원문 컬럼은 없다(그건 지금도 그렇다).
    - taggings/evidence 는 checks 에 FK 로 매달리므로 삭제 순서가 있다.
    - 보관 기간을 테이블마다 다르게 둘지(관측 로그 90일 / 서비스 데이터 90일).


6. 테스트 DB 분리 — 전제는 이미 충족돼 있다
--------------------------------------------

  api/tests/conftest.py 가 DATABASE_URL 을 임시 SQLite 로 덮고, sqlite 가 아니면
  즉시 RuntimeError 로 중단한다(2026-08-15). test_db_isolation.py 가 그걸 단정한다.
  → 저장소를 DB 로 옮기는 작업이 pytest 로 운영 DB 를 오염시킬 경로는 닫혀 있다.

  ★ 이번 측정에서도 그대로 확인됐다. 측정 전후 운영 DB 행수 변화 0.

8. 대기 — 사람이 정할 것
------------------------

  지시대로 설계는 쓰지 않았다. 결정에 필요한 수치는 위에 다 있다.
  결정해야 할 것으로 보이는 지점만 적어 둔다(제안이 아니라 목록이다).

  (1) 저장소 외부화 방식 — DB 냐 Redis 냐, checks 만이냐 evidence/taggings 까지냐
  (2) 그때 purge 에 추가할 테이블과 보관 기간
  (3) 워커 수 — ★ 스레드 수 제한이 먼저다. 순서가 거꾸로면 느려진다(3절)
  (4) 동기 호출을 스레드풀로 뺄지 (get_evidence 의 async def 안 동기 호출).
      메모리 0으로 직렬을 푸는 경로지만 **재 보지 않았다.** 채택하려면 측정 먼저.
  (5) docker-compose 에 mem_limit/cpus 를 넣을지 (지금 무제한)
  (6) url_expand 의 외부 HEAD 를 요청 흐름에서 뺄지
      → ★ 2026-08-16 확정: **흐름 유지**. 2단계에서 스레드풀로 옮겨져 느린 대상이
        다른 사용자를 막지 않게 됐고, 3초 상한이 이미 있다. 이 항목은 닫혔다.

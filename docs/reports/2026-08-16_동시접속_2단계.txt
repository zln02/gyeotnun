================================================================

지시: collect_evidence · url_expand · LLM 호출을 이벤트 루프 밖으로.
      LLM 은 공식 비동기 클라이언트가 있으면 그것, 없으면 스레드풀.
      ★ 판정 로직 무변경 — 실행 방식만 바꾼다.
      render_verdict.mjs 전수 대조로 출력 불변 확인.

1. 무엇을 바꿨나 (판정 로직은 한 줄도 안 바꿨다)
------------------------------------------------

  routers/dialogue.py
      collect_evidence  → await run_in_threadpool(...)
      질문 생성          → await prompt_chain.agenerate_question(...)   (AsyncAnthropic)
  routers/checks.py
      get_evidence 의 collect_evidence  → await run_in_threadpool(...)
      create_check 의 OCR·링크 추출      → await run_in_threadpool(...)
  services/prompt_chain.py
      _question_driver 를 새로 만들고, generate_question / agenerate_question 이
      **같은 드라이버**를 돌린다.
  services/ocr.py
      Paddle 추론을 전용 스레드 1개에 고정 (3절 참고)

  ★ url_expand 는 따로 손대지 않았다. collect_evidence 안에서 불리므로
    collect_evidence 가 루프 밖으로 나가면 함께 나간다.

  ★★ 가드레일을 사본으로 두지 않았다 ★★
    비동기 버전을 만들려면 3회 재시도 + 금지어 검사 + 폴백 루프가 필요한데,
    동기용·비동기용으로 **사본을 두 벌 두면 언젠가 한쪽만 고쳐진다.** 그 순간
    원칙을 어긴 질문이 화면에 나간다 - prompt_chain.py 가 막으려는 바로 그 일이다.
    그래서 루프는 _question_driver 하나만 두고, "Claude 를 어떻게 부르는가"만
    호출자가 정하게 했다. 동기·비동기가 가드레일이 다를 수 없는 구조다.

    이걸 주장으로만 두지 않고 테스트로 박았다(test_sync_and_async_agree):
    같은 응답 열에 대해 질문·why·보기·링크·폴백여부·재생성통계가 **완전히 같은지**
    4가지 시나리오로 단정한다. 갈라지면 테스트가 깨진다.

3. ★★ 배포 전 격리 측정이 잡아낸 것 — 사진 경로 전면 장애 ★★
--------------------------------------------------------------

  OCR 을 스레드풀로 빼자마자 사진 경로가 무너졌다. 격리 측정 결과:

      동시 1명  3건 중 3건 실패
      동시 3명  9건 중 9건 실패 (+ 300초 타임아웃 1건)
      동시 5명 15건 중 12건 실패
      서버 로그: EX-001 "로컬 OCR(PaddleOCR) 추론 실패: std::exception"

  ★ 그대로 배포했으면 어르신의 주 진입 경로(사진 올리기)가 통째로 죽었다.
    "각 단계 배포 전 격리 측정" 지시가 정확히 이걸 잡았다.

  [3-1] 첫 진단이 틀렸다 — 락으로는 안 고쳐졌다

    "동시 실행이 문제"라 보고 threading.Lock 으로 predict() 를 직렬화했다.
    **그래도 똑같이 실패했다.** 그래서 다시 쟀다:
      - curl 로 한 건 → 200 OK (2.17초). 멀쩡하다.
      - 순차로 3건 → 3건 다 성공.
      - 동시 3건 → 2건이 501.
    직렬화했는데도 깨진다면 원인은 동시 실행이 아니다.

  [3-2] 진짜 원인 — 예측기가 '만들어진 스레드'에 묶인다

    스레드풀은 요청마다 다른 스레드를 쓴다. Paddle 의 C++ 예측기는 자기를 만든
    스레드에서만 안전하다. 순차 요청이 우연히 통과한 것은 스레드풀이 같은 유휴
    스레드를 재사용해서였다 - 동시에 들어오는 순간 새 스레드가 쓰이고 죽는다.

    → **전용 스레드 1개**(ThreadPoolExecutor(max_workers=1))에 고정했다.
      로드도 추론도 전부 그 스레드에서 돈다. max_workers=1 이라 직렬화도 따라온다.
    → 프리워밍도 같은 스레드를 타게 고쳤다(main.py). 백그라운드 스레드에서 예측기를
      만들면 이후 **모든** 요청이 죽는다.

    고친 뒤: 동시 1·3·5 전부 실패 0건, 그리고 위 [2-2]처럼 오히려 빨라졌다.

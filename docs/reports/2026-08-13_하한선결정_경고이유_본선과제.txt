1. 결정 — min_score 는 5.0 유지
================================================================
문서: docs/evaluation/하한선_결정_2026-08-13.md
코드 변경 없음. corpus_index.match_scam_cases(min_score=5.0) 기본값 그대로.

결정 : 5.0 유지
결정일: 2026-08-13
결정자: 사람

근거
  (1) 깨끗한 하한선이 존재하지 않는다
      정상 최고 10.98(H19) > 사칭 최저 3.56(H26).
      3.56~10.98 구간에서 두 분포가 겹친다. 어떤 값을 골라도 한쪽을 잃는다.

  (2) 올리면 사칭 검출이 반토막 난다
      min_score   정상 오판(확대/홀드)   사칭 경고(확대/홀드)
        5.0 유지      1/37 · 1/10           16/37 · 2/10
        6.75          0/37 · 1/10           14/37 · 2/10
       11.0           0/37 · 0/10            9/37 · 1/10
      6.75 는 확대셋에서만 0 이고 홀드아웃 1건은 남는다 —
      "한쪽만 좋아지는 값은 채택하지 않는다" 원칙에 걸린다.
      양쪽 0 을 만드는 11.0 은 오판 2건을 지우려고 사칭 경고 8건을 끈다.

  (3) 남는 오판 1건(R11)은 축2 기준으로는 정답이다
      R11 = 실사용 원문 KB국민카드 당첨안내 문자. 위험행동 = 앱설치.
        축1 판정: 기대판단 정상 -> 경고  => 오판
        축2 안전: 위험행동 앱설치 -> 경고 => 정답
      6.75 로 올리면 축1 오판 1->0 과 축2 있음 17->14 가 동시에 일어난다.
      오판 1건을 지우는 것이 곧 주의 표시 1건을 끄는 것이다.
      앱 설치 요구에 주의를 붙이는 것 자체는 잘못이 아니다.
      잘못된 것은 그 이유를 화면이 말하지 않는다는 점이다 -> 아래 2번.

  (4) 헛경고는 하한선으로 풀리지 않는다
      축2 없음은 확대셋에서 13.0 까지 올려야 2->1. 원인이 사기사례 매칭이 아니다.

전제
  CI 회귀 테스트가 기준선을 지킨다.
    api/tests/test_scam_threshold_regression.py
    BASELINE = {"확대 평가셋": 1, "홀드아웃": 1}
  5.0 유지는 "지금 1건뿐이라 감당한다"는 판단이므로,
  1건이 늘어나는 순간 이 결정의 전제가 깨진다. 그때 테스트가 알려 준다.
  ★ 그 사실을 테스트 docstring 에도 적어 뒀다 — 실패했을 때 상수부터 고치지
    말고 결정 문서를 먼저 읽게 하기 위해서다.

재검토 조건 — SCAM_CASES 규모가 바뀔 때
  _keyword_weight = log((N+1)/(df+1))+1 이라 N 이 늘면 모든 점수가 함께 오른다.
  min_score 5.0 은 절대값이라 따라가지 않는다.
    확대 정상 최고(R11)  N=51 6.72  -> N=185 14.58  (+117%)
    홀드 정상 최고(H19)  N=51 10.98 -> N=185 13.48  (+23%)
  즉 5.0 유지는 "N=51 에서의 5.0" 을 유지한다는 뜻이지 영구 결정이 아니다.
  절차: test_scam_corpus_size_is_recorded 실패 -> exp_scam_min_score_tradeoff.py
        재측정 -> docs/evaluation/ 에 기록 -> 결정 갱신. 숫자만 올리지 않는다.

2. 본선 과제 — 경고의 이유를 화면이 말하게 한다
================================================================
문서: docs/evaluation/본선과제_경고이유_화면표시.md
지금 고치지 않는다. 기록만 한다.

현재 R11 화면 (2026-08-13 실측)
  tier      warn (주황)
  제목      확인이 필요한 문자예요
  사실 한 줄 이전에 확인된 사례와 비슷한 문장이 있어요
  경고 신호  similar_scam_case (attention) — 유일한 경고 신호

어긋나는 지점
  사용자가 읽는 뜻   "이 문자는 사기와 비슷하다"
  실제로 잡은 것     "앱 설치를 요구한다" (위험행동=앱설치, 겹친 단어 [쿠폰, 설치])
  경고는 옳다. 이유가 틀렸다.

왜 단순 문구 문제가 아닌가
  1. 정직성 원칙 위반. verdict.js 머리말이 "'사실 한 줄'은 실제로 검출한 것만
     적는다" 라고 못 박았는데, 검출하지 않은 것을 적고 있다.
  2. 행동으로 이어지지 않는다. "비슷한 문장이 있어요"를 읽고 무엇을 할지 알 수 없다.
  3. 경보 피로. 정상 문자에까지 "사기와 비슷"이 붙으면 진짜 경고까지 무시된다.

사실 정리 — 필요한 정보는 이미 서버에 있다
  api/services/search.py 에 detect_risk_action() 과 RISK_ACTION_KEYWORDS 가
  2026-08-12 부터 들어와 있다. 그런데 그 결과는 urgency_pressure 의 severity 를
  낮출지 판단하는 데에만 쓰인다(search.py:144, 150 두 곳이 전부).
  화면으로 나가는 신호가 아니다.
  => 새 판정 로직을 만드는 과제가 아니라, 있는 것을 전달하는 과제다.

  프런트: verdict.js 가 similar_scam_case 에 고정 문구 하나를 걸어 뒀다.
         어떤 이유로 걸렸든 같은 문장이 나간다.

본선에서 할 일
  1. detect_risk_action() 결과를 화면까지 내려보낼지 결정 (신호로? 필드로?)
  2. 위험행동 종류별 화면 문구·행동 안내 결정 — 문구는 사람이 정한다
  3. 경고 이유가 여러 개일 때의 우선순위 (R11 은 앱설치 + 사기사례 매칭)
  4. 평가셋·홀드아웃 양쪽 전후 대조 후 사람이 채택 결정

방향 예시 (확정 문구 아님. 선택지다)
  "앱을 설치하라는 문자예요 / 설치 전에 공식 앱스토어에서 직접 검색해 보세요"

문구 제약 (기존 기준 그대로)
  - '사기'·'가짜' 를 쓰지 않는다 (validate_question 금지어와 같은 기준)
  - '찾았어요' 를 쓰지 않는다 (초록 tier 문구와 겹쳐 S22 를 재생산한다)
  - 검출하지 않은 것을 적지 않는다

지금 하지 않는 이유
  1. 판정 로직 변경이다. 신호를 새로 내보내면 tier 계산에 영향이 간다. 8/8 사고 경로.
  2. 예선 제출 수치가 재측정 대상이 된다. 축1·축2 양쪽이 움직인다.
  3. 60대 대상 문구를 코드 쪽에서 임의 확정하면 안 된다 (A안 때와 같다).

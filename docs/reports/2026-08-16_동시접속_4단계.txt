동시 접속 개선 — 4단계: 워커 2 + compose 리소스 제한 (2026-08-16, #33)
================================================================================

지시: cpus 3.0 · mem_limit 4g · 워커 2 (메모리 2.4GiB 예산).
      ★ 3단계 전에 워커를 늘리지 마라 — 404 가 난다.


1. 전제 확인 — 왜 이제는 워커를 늘려도 되나
--------------------------------------------

  워커를 1개로 묶어 둔 이유는 성능이 아니라 **정합성**이었다. 확인 기록이 프로세스
  메모리에 있어, POST /checks 를 받은 워커와 evidence/dialogue 를 받은 워커가 다르면
  404 가 났다. 3단계에서 저장소를 Postgres 로 옮기며 그 전제가 사라졌다.

  ★ 말로 끝내지 않고 실측했다. 격리 환경에서 2워커로 전체 흐름을 돌렸다.
      텍스트 POST→evidence  동시 1·3·5 각 3라운드 (총 27건)  → 실패 0
      POST→evidence→dialogue 동시 3명                        → 실패 0
      라이브에서도 POST→evidence→verdict 5회                 → 404 0건
    워커를 가로질러도 기록을 찾는다. 전제 충족.


2. 전후 비교 — 동시 1·3·5 (격리 Postgres, 임베딩 폴백 0건 검증됨)
------------------------------------------------------------------

  텍스트 경로 (POST + evidence) — 마지막 완료 중앙
      N |  3단계(워커1)     4단계(워커2)     실패
      1 |  0.10s            0.14s            0
      3 |  0.21s            0.17s            0
      5 |  0.34s            0.27s            0

  사진 경로 (POST, OCR) — 마지막 완료 중앙
      N |  3단계(워커1)     4단계(워커2)     실패
      1 |  1.66s            1.72s            0
      3 |  5.21s            3.89s            0
      5 |  8.48s            5.90s            0     ← 1.4배

  ★ 사진 경로가 크게 좋아진 이유: OCR 은 워커 안에서 전용 스레드 1개에 묶여 있는데
    (2단계, Paddle 스레드 제약), **워커가 2개면 전용 스레드도 2개**가 된다.
    즉 워커 증설은 여기서 OCR 병렬도를 1 → 2 로 올리는 유일한 수단이다.

  ★ 단독 1건은 오히려 조금 느리다(1.66 → 1.72s, 0.10 → 0.14s). CPU 를 3개로 제한한
    영향과 워커 간 경합이다. **혼자 쓸 때 손해, 여럿이 쓸 때 이득**인 교환이다.
    시연은 여럿이 동시에 쓰는 상황이므로 이 교환을 택했다.

  메모리: 859 MiB → 1.692 GiB (워커당 약 0.85GiB). mem_limit 4g 안에 넉넉히 들어간다.


3. 배포한 것
------------

  docker-compose.yml api 서비스
      cpus: 3.0
      mem_limit: 4g
      command: ... --workers 2

  적용 확인(docker inspect): NanoCpus=3000000000 · Memory=4294967296
  실제 사용:  1.692GiB / 4GiB · prewarm 로그 4줄(워커 2 × 임베딩·OCR)

  ★ cpus 3.0 인 이유: 4 vCPU 중 1개를 호스트에 남긴다. 전에는 제한이 **전혀 없어서**
    api 가 CPU·메모리를 무제한 점유할 수 있었고, 같은 호스트에 다른 프로젝트가
    함께 도는 상태라 그건 사고 경로였다(8/14 감사 지적 사항).

  ★ 워커를 3 이상으로 올리지 말 것. 요청 1건이 이미 CPU 2.5코어를 쓰고, 4 vCPU
    에서는 워커를 늘릴수록 서로 밀어낸다(8/16 실측: 워커4 가 워커1 보다 느렸다).
    compose 주석에도 못 박아 뒀다.


4. ★ 워커가 2개가 되면서 바뀐 것 — 관측 정확도
-----------------------------------------------

  폴백률 상시 관측(GN-003 질문 생성 · EX-006 검색)은 프로세스 메모리의 deque 다.
  **워커마다 따로 쌓인다.** 그래서 경보가 뜨기까지 걸리는 요청 수가 대략 2배가 된다
  (최소 표본 5건을 워커별로 채워야 한다).

  ★ 놓치는 것은 아니다 - 폴백률이 높으면 어느 워커든 결국 임계를 넘는다.
    다만 "즉시" 는 아니다. 전역 정확도가 필요해지면 이 관측을 공유 저장소로 옮겨야
    한다. 지금은 그 정확도가 필요하지 않아 두었고, **코드 주석과 이 보고서에
    적어 둔다** - 조용히 둔감해지는 것이 제일 나쁘다.

  관련 주석을 사실에 맞게 고쳤다:
      routers/dialogue.py · services/search.py · services/fallback_watch.py
      docs/security/final_hardening_2026-08-06.md ("워커 1개" 판단에 갱신 주석)

6. 전체 요약 — 0단계에서 4단계까지
-----------------------------------

  사용자 전체 여정, 동시 3명, 마지막 사용자 기준 (LLM 실호출 포함)

      텍스트 여정   14.77s  →  5.46s     (2.7배)
      사진 여정     24.14s  →  10.70s    (2.3배)   ※ 2단계 시점 측정
      사진 POST 동시 5명   11.87s → 5.90s (2.0배)  ※ 1→4단계

  단계별로 무엇이 얼마를 줬는지
      1단계 스레드 제한   텍스트 경로 약 2배. 체감은 거의 없다(여정의 98%가 LLM).
      2단계 블로킹 제거   ★ 여기가 대부분이다. LLM 동기 호출이 요청당 4.7초씩
                          이벤트 루프를 막고 있었다.
      3단계 저장소 외부화 성능 목적이 아니다. 재시작 생존 + 90일 삭제 + 4단계의 전제.
                          비용은 요청당 0.03~0.35초.
      4단계 워커 2        사진 경로 1.4배(OCR 병렬도 1→2). 리소스 상한 신설.

  ★ 이 과정에서 장애 두 건을 배포 전 격리 측정으로 잡았고(2단계 OCR 전면 실패),
    한 건은 배포 후 라이브에서 잡았다(3단계에서 발견한 임베딩 로더 경합 -
    2단계가 만든 것). 세 번째 것은 게이트 세 개를 모두 통과했고, 잡은 단서는
    "같은 문장인데 재시작 전후 판정이 다르다" 한 줄이었다.
    → 그래서 측정 스크립트가 임베딩 폴백을 스스로 검출하게 만들어 두었다.


7. 남은 것
----------

  - OCR 은 워커당 한 장씩이다. 사진 동시 5명이면 마지막 사람이 5.9초.
    더 줄이려면 워커를 늘려야 하는데 4 vCPU 에서는 2가 상한이다(3 이상은 느려진다).
    그 위는 서버 사양 문제다.
  - 폴백률 관측의 워커 간 분산(4절). 필요해지면 공유 저장소로.
  - url_expand 의 외부 HEAD 는 이제 이벤트 루프를 막지 않지만, 여전히 요청 흐름
    안에 있다(최대 3초). 뺄지는 아직 정하지 않았다.

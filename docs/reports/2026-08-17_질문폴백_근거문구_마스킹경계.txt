1. (나) 원인 규명 — 프롬프트가 아니라 폴백 문장이었다
=====================================================

  [1-1] ★★ 라이브에 나온 그 질문은 LLM 이 만든 문장이 아니다 ★★

    코드를 읽다가 찾았다. prompt_chain.py 의 FALLBACK_QUESTION 이
    **라이브에서 나온 문장과 글자 하나까지 같다**(프로그램으로 비교 확인).

        FALLBACK_QUESTION =
          "이 글에 적힌 내용을 어느 기관에서 발표했는지 글 안에서 한번 찾아봐
           주시겠어요? 기관 이름이 보이지 않는다면 그것만으로도 한 번 더 확인해
           볼 신호입니다."

    3회 재생성이 모두 검증을 통과하지 못했을 때 내려가는 **고정 문장**이고,
    그 문장이 "기관 이름이 보이지 않는다면" 을 **하드코딩**하고 있다.
    → 입력에 기관명이 있으면 폴백은 **반드시** (나)가 된다. 확률이 아니라 구조다.

    ★ 폴백 보기(FALLBACK_OPTIONS)도 같은 전제를 담고 있다:
        "기관 이름이 적혀 있어요" / "찾지 못하겠어요" / "잘 모르겠어요"
      첫 보기를 고르면 "있으니 괜찮다" 가 한 번 더 굳는다.

  [1-2] 지시받은 확인 — 기관명이 프롬프트 컨텍스트로 가는가

    ★ **간다.** build_messages() 가 `[사용자가 받은 글]\\n{extracted_text}` 로
      원문 전체를 그대로 넣는다. 기관명만 따로 빼거나 요약하지 않는다.
      (prompt_chain.py 는 읽기만 했다. 고치지 않았다.)
    → 그러므로 (나)의 원인은 컨텍스트 누락이 **아니다.**

  [1-3] 실측 — 기관명이 있는 26건 × 2회 (LLM 52건, 약 1,173원)

        생성 52건
          폴백           2건  → 그중 (나) **2건 (100%)**
          모델이 생성    50건  → 그중 (나) **0건 (0%)**

        ★ (나) 전체 2/52 = 3.8%
        ★ 폴백일 때      100%   ← 구조적으로 확정된다
        ★ 모델 생성일 때   0%   ← 50건 중 한 건도 없다

    폴백이 난 건은 S08 하나이고, 2회 모두 폴백했다(재현된다).

  [1-4] 왜 S08 은 매번 폴백하는가 — 사슬을 끝까지 따라갔다 (LLM 3건 추가)

        근거 0건("검색 결과 없음")
          → 모델이 출처 없이 설명하려다 **4문장**을 쓴다
          → 길이 가드레일(2문장 이내)이 3회 모두 차단 (too_long ×3)
          → 폴백
          → 폴백 문장의 하드코딩된 전제
          → 입력에 [기관명]이 있으므로 (나)

    금지어가 아니라 **길이**로 막혔다. 3회 다 같은 사유다.

  [1-5] ★★ 그래서 검사기를 생성 루프에 연결해도 (나)는 안 막힌다 ★★

    지난 보고에서 나는 "(나)만 먼저 켜는 선택지도 있다"고 적었다. **틀렸다.**
    폴백은 재생성 루프 **밖**에 있다. 검사기를 루프에 넣어도 폴백 문장은 검사 대상이
    아니고, 설령 검사한다 해도 폴백은 마지막 수단이라 물러설 곳이 없다.

    → 실제로 (나)를 없애려면 손댈 곳은 셋 중 하나다(전부 사람이 정할 일):
        (a) 폴백 문장·보기에서 전제를 뺀다        ← 가장 작고 확실하다
        (b) 근거 0건일 때 길이 초과가 잦은 것을 줄인다 (폴백 자체를 줄인다)
        (c) 폴백을 입력에 따라 두 벌로 나눈다 (기관명 유무)
    ★ 어느 것도 하지 않았다. 지시가 "연결은 하지 마라" 였고, 원인이 밝혀진 이상
      검사기 연결은 이 문제의 해법이 아니기 때문이다.

5. compose `environment:` 함정 — 목록 (고치지 않음)
===================================================

  api 서비스 `environment:` 에 하드코딩된 값 **11개** 중, `.env.example` 에도
  문서화돼 있어 **`.env` 를 고쳐도 무시되는 것이 3개**다.

      키               .env.example        compose            결과
      APP_ENV          local|dev|prod 문서   local 하드코딩      .env 무시
      DATABASE_URL     문서화               postgres URL       .env 무시
      MAX_UPLOAD_MB    문서화               10                 .env 무시

  나머지 8개(HF_HOME · HOME · PADDLE_* · OCR_PROVIDER · OMP/MKL/OPENBLAS_NUM_THREADS)
  는 `.env.example` 에 없다 - compose 전용 값이라 함정이 아니다.

  ★ **API 키 5종은 compose 가 덮지 않는다.**
    ANTHROPIC_API_KEY · GOOGLE_VISION_API_KEY · NAVER_CLIENT_ID ·
    NAVER_CLIENT_SECRET · UPSTAGE_API_KEY 는 `.env` 대로 동작한다.
    가장 중요한 값들은 무사하다 - 급한 문제가 아닌 이유다.

  ★ 값 자체보다 **"`.env` 를 고쳐도 안 바뀐다"** 가 문제다. `DATABASE_URL` 이
    특히 그렇다 - `.env` 로 다른 DB 를 가리켜도 조용히 무시된다.
  ★ 지금 고치지 않았다(지시). README "남은 과제" 에 표로 기록했다.

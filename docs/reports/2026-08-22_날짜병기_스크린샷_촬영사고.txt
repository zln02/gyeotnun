0. ★★ 먼저 보고할 것 — 제가 운영 api 컨테이너를 재시작시켰습니다
================================================================

  뒷정리를 하면서 이 명령을 보냈습니다.

      docker compose exec -T api sh -c "kill 1 2>/dev/null; pkill -f 'port 8010'"

  촬영용으로 컨테이너 안에 띄운 격리 uvicorn(8010) 을 죽이려던 것인데,
  **`kill 1` 이 컨테이너의 PID 1, 즉 운영 uvicorn 을 죽였습니다.**
  docker 재시작 정책으로 즉시 다시 떴습니다(Up 5분).

  ■ 왜 그랬나
    격리 uvicorn 의 PID 를 확인하지 않고 "혹시 1이면" 하는 식으로 두 명령을
    한 줄에 넣었습니다. **pkill 하나로 충분했는데 kill 1 을 앞에 붙였습니다.**
    ★ 8/16 262행 사고와 같은 형태입니다 — 좁혀야 할 대상을 넓게 잡았습니다.
      그때는 WHERE 절이었고 이번엔 PID 였습니다.

  ■ 영향 — 실측
      라이브 /health                        200
      운영 checks 최근 2시간 생성            0행
      EX-003(임베딩 실패) 최근 2시간         0건   (전체는 여전히 10건)
      EX-006(검색 폴백률) 최근 2시간         0건   (전체는 여전히 1건)
      로그의 meta tensor 오류(최근 10분)     0건
      재시작 후 임베딩 검색                  ✓ 정상 (1건 반환)
      재시작 후 판정 재현                    needs_check · refs 1  ✓

    → 측정 가능한 피해는 없습니다. 다만 **짧은 무중단 중단**이 있었고,
      그 순간 사용자가 있었다면 요청이 실패했을 것입니다.

  ■ verify_restart_race.sh 를 돌리지 않았습니다 — 판단과 근거

    그 검사는 **배포 절차**의 필수 단계이고, 내용은 "재시작 → 프리워밍 중
    동시 5건 투입 → 판정 일치·경합 오류 0 확인" 입니다.
    지금 돌리면 **살아 있는 서비스를 한 번 더 재시작**하게 됩니다.

    코드 변경이 없고, 위 실측이 이미 그 검사가 보려는 것(임베딩 로드 실패·
    경합 오류·판정 불일치)을 전부 0으로 보여 주므로, 재시작을 한 번 더 하는 것이
    위험을 줄이는 게 아니라 늘린다고 판단했습니다.

    ★ 다만 이건 제 판단입니다. 절차대로 돌리길 원하시면 말씀해 주십시오.
      (돌리면 다시 한 번 재시작됩니다.)

  ■ 재발 방지 — 제안 (적용 안 함)
      컨테이너 안에서 프로세스를 죽일 때 `kill 1` 을 쓰지 않는다.
      죽일 대상의 PID 를 먼저 확인하고, pkill 은 패턴을 좁혀 쓴다.
      ★ CLAUDE.md 의 "운영 DB 는 절대 직접 지우지 않는다" 옆에 한 줄로 둘
        만한 성격입니다 — 지시하시면 넣겠습니다.


1. 날짜 병기 두 곳 — 대장 L4 의 남은 줄을 닫았습니다
====================================================

      처리 시간   "텍스트 14.77→5.46초 · 사진 24.14→10.70초 · 실패 0
                   **(2026-08-16 기준)**"
      기록 건수   "기각 7 · 정정 7 · 사고 1
                   **── 2026-08-22 기준. 기록이 늘면 이 수도 늘어납니다**"

  ★ 세는 스크립트는 만들지 않았습니다. 지시대로이고, 이유를 대장에 적었습니다.

      스크립트를 만들면 그 자체가 **또 어긋날 수 있는 자산**이 된다 —
      기각·정정의 정의가 바뀌면 스크립트도 고쳐야 하고, 안 고치면 이번과
      똑같이 조용히 어긋난다.
      ★ 이 판단은 L4 의 규칙 자체에 대한 것이다: **방어 장치를 늘리는 것이
        늘 답은 아니다.** 감시할 가치가 낮은 값에는 날짜가 정답이다.

  ★ 두 줄의 성격이 다르다는 것도 적었습니다.
      처리 시간   그 시점의 사실 → 날짜만 있으면 영원히 참이다
      기록 건수   계속 늘어난다 → 날짜만 있으면 "왜 안 늘었지" 로 읽힌다
                  그래서 "늘어난다" 는 말을 본문에 함께 넣었다

  L4 의 README 현황 표는 이제 여섯 줄 전부 셋 중 하나(적지 않음 / 날짜 병기 /
  감시)로 닫혔습니다.

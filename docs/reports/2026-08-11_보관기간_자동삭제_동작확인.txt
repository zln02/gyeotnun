2. ModuleNotFoundError 가 여전히 나는가
---------------------------------------
아니다. 로그 전체에서 트레이스백은 맨 위 4줄, 단 1회뿐이다.

  Traceback (most recent call last):
    File "/app/tools/purge_old_records.py", line 19, in <module>
      from config import settings
  ModuleNotFoundError: No module named 'config'

그 이후 8/7 · 8/8 · 8/9 · 8/10 · 8/11 다섯 번 모두 정상 완료 줄로 끝난다.

원인은 실행 형태였다. 파일 경로로 실행하면 sys.path 가 /app/tools 가 되어
`from config import settings` 가 죽는다. 지금 crontab 은 -m 형태로 돌린다.


3. 실패 기간
------------
종료 시점 : 확실. 2026-08-07 16:11:15 UTC 에 첫 성공이 찍혔다.
              [purge] cutoff=2026-05-09T16:11:15.657424 (90일) 삭제: events=0 error_logs=0
              [purge] 2026-08-07 16:11:15 UTC 보관 90일 초과 삭제 완료: ...
            (04:00 이 아닌 16:11 이므로 cron 이 아니라 수동 실행으로 보인다 — 추측)

시작 시점 : ★ 확인 불가.
            purge.log 는 트레이스백 1건만 담고 있고 그 이전 이력이 없다.
            로테이션된 로그도 없다(find 결과 purge*.log 는 이 파일 하나뿐).
            즉 "언제부터" 실패했는지는 이 로그로 알 수 없다.

            purge_old_records.py 독스트링에는 "2026-08-07 까지 04:00 cron 이
            이 이유로 매일 실패했다"고 적혀 있으나, 이는 코드 주석이지
            로그 근거가 아니다. 주석을 근거로 기간을 단정하지 않는다.


4. 성공 시 삭제 건수가 로그에 남는가
------------------------------------
남는다. 실행 1회당 2줄이 찍힌다.

  [purge] cutoff=<UTC ISO> (90일) 삭제: events=N error_logs=N
  [purge] <UTC 시각> 보관 90일 초과 삭제 완료: events=N건, error_logs=N건

다만 지금까지 기록된 건수는 5회 전부 0건이다.
이것은 고장이 아니다 — 서비스 가동 이력이 90일 미만이라 컷오프(2026-05-x)보다
오래된 행이 애초에 존재하지 않는다. 삭제 로직이 도는 것과 지울 게 있는 것은
다른 문제이고, 로그는 "0건 삭제"를 정직하게 남기고 있다.

★ 2026-08-11 추가 검증으로 이 공백을 메웠다 → 아래 4-1.


4-1. 실제 삭제 검증 (2026-08-11 추가)
------------------------------------
"지울 게 없어서 0건" 과 "지우는 기능이 동작한다" 는 다른 문제라, 더미 행으로
직접 확인했다.

격리 조건 (운영 DB 는 건드리지 않았다):
  - 운영 DB 는 Postgres(db:5432/gyeotnun). 검증은 DATABASE_URL 을
    sqlite:////tmp/purge_verify.db 로 덮어써서 완전히 분리된 파일에서 돌렸다.
  - 스크립트에 `assert "purge_verify" in str(engine.url)` 가드를 넣어
    운영 DB 로 붙으면 즉시 중단되게 했다.
  - purge_old_records.py 는 수정하지 않았다. purge() 를 그대로 import 해 호출했다.
  - 검증 후 /tmp/purge_verify.db 삭제.

넣은 건수:
  events     10건 = 컷오프보다 5일 더 오래된 7건 + 최근(1일 전) 3건
  error_logs  6건 = 오래된 4건 + 최근 2건

로그 출력 그대로:
  [검증] DATABASE_URL = sqlite:////tmp/purge_verify.db
  [검증] RETENTION_DAYS=90  cutoff=2026-05-13T22:07:59.840231
  [검증] 삽입 완료 - events=10건(오래된 7 + 최근 3), error_logs=6건(오래된 4 + 최근 2)
  --- purge 실행 (tools.purge_old_records.purge 원본 호출) ---
  --- 반환값: {'events': 7, 'error_logs': 4} ---
  [purge] cutoff=2026-05-13T22:07:59.902561 (90일) 삭제: events=7 error_logs=4
  [검증] 실행 후 - events=3건, error_logs=2건
  [검증] 실제 삭제 - events=7건, error_logs=4건
  [검증] 판정: 통과 - 오래된 행만 정확히 삭제됨

지워진 건수: events 7건 / error_logs 4건 — 넣은 오래된 행 수와 정확히 일치한다.
최근 행(events 3 / error_logs 2)은 그대로 남았다. 즉 컷오프 경계가 제대로 걸린다.

운영 DB 무영향 확인 (읽기만):
  운영 DATABASE_URL : db:5432/gyeotnun
  운영 events    : 3107 건
  운영 error_logs: 244 건

결론: 삭제 기능은 실제로 동작한다. 지금까지 로그가 0건이었던 것은
      지울 대상이 없었기 때문이 맞다.


5. crontab 등록 여부
--------------------
등록돼 있다. ubuntu 사용자 crontab:

  # 보관 90일 초과 관측 로그(events/error_logs) 삭제 - 매일 04:00
  0 4 * * * cd /home/ubuntu/gyeotnun && sudo docker compose exec -T api \
            python -m tools.purge_old_records \
            >> /home/ubuntu/gyeotnun/deploy/purge.log 2>&1

root crontab 없음, /etc/cron.d 에도 purge 항목 없음.
실제 04:00:02~04:00:03 에 로그가 찍힌 것이 8/8·8/9·8/10·8/11 4일 연속 확인되므로,
등록만 된 게 아니라 실제로 발화하고 있다.


6. ★ 기획서와 어긋나는 부분 (이게 진짜 문제다)
----------------------------------------------
삭제 잡은 동작한다. 그런데 기획서가 말하는 대상과 실제 대상이 다르다.

  기획서 2.5 / 3.4 : "마스킹 텍스트 · 놓친 질문 · 최종 선택만 90일 보관 후 자동 삭제"
  실제 삭제 대상   : events, error_logs (관측 로그 2종)

purge_old_records.py:38 이 도는 테이블은 Event 와 ErrorLog 둘뿐이다.
마스킹 텍스트(checks) · 놓친 질문 · 최종 선택(taggings) 은 이 잡이 건드리지 않는다.

이유는 스크립트 독스트링에 적혀 있다 —
  "checks/taggings 등 서비스 데이터는 현재 DB 에 쓰이지 않으므로(인메모리) 대상이 아니다."

README "알려진 한계" 의 "확인 기록을 프로세스 메모리에 보관한다" 와 같은 사실이다.
인메모리라서 프로세스가 재시작되면 사라지므로 90일 축적 위험 자체는 없지만,
"90일 보관 후 자동 삭제한다"는 서술은 그 데이터에 대해 성립하지 않는다.


7. 수정안 (실행 전 확인 요청 — 아직 아무것도 안 고쳤다)
-------------------------------------------------------
코드는 고칠 것이 없다. 고칠 것은 기획서 문안이다. 두 가지 안을 낸다.

안 A (사실 그대로, 권장)
  "관측 로그(행동 계측·장애 로그)는 90일 보관 후 매일 04:00 자동 삭제하며,
   삭제 시각과 건수를 로그에 기록한다. 마스킹 텍스트·놓친 질문·최종 선택은
   현재 프로세스 메모리에만 두어 재시작 시 소멸하며, DB 이전 시 동일한 삭제
   대상에 포함한다."

안 B (문구 최소 수정)
  "마스킹 텍스트·놓친 질문·최종 선택만" → "관측 기록만"
  으로 바꾸고 3.4 의 "삭제 작업과 건수는 매일 기록한다" 는 그대로 둔다
  (이 부분은 실제로 그렇게 동작한다).

어느 쪽으로 갈지 알려 주시면 그때 반영하겠다.
purge_old_records.py 는 손대지 않는 것이 맞다고 본다 — 지울 대상이 DB 에 없는데
코드에 테이블만 추가하면 돌지 않는 코드를 늘리는 셈이다.

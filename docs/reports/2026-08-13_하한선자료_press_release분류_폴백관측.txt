표에서 바로 읽히는 것
  1. 두 세트가 요구하는 값이 다르다. 정상 오판 0 최소값 = 확대 6.75 / 홀드 11.00.
     확대셋만 보고 6.75 를 고르면 홀드아웃 오판 1건은 그대로 남는다.
  2. 11.00 이면 사칭 검출이 반토막. 확대 16->9, 홀드 2->1.
  3. 헛경고(축2 없음)는 거의 안 준다. 확대는 13.0 까지 올려야 2->1.
     헛경고 원인은 사기사례 매칭이 아니다. 하한선으로 풀 문제가 아니다.
  4. R11 은 두 축이 정면 충돌하는 건이다. 기대판단은 정상인데 위험행동은 앱설치다.
     R11 의 경고는 축1 로는 오판이고 축2 로는 정답이다. 6.75 로 올리면
     축1 오판 1->0 과 축2 있음 17->14 가 동시에 일어난다.
     어느 숫자를 보느냐에 따라 같은 변경이 개선으로도 후퇴로도 보인다.

채택 제안 없음. 하한선은 사람이 정한다.

(f) 검색 폴백 관측
================================================================
1. 기록이 남는가 -> 남는다. 단, 개별 발생만.
   - gyeotnun.search 로거(도커 로그)
       "[official_search] 임베딩 검색 실패 - BM25 로 폴백: <사유>"  WARNING
   - log_incident("EX-003") -> gyeotnun.incidents 로거 + DB error_logs 테이블
       GET /errors/summary 로 집계 조회 가능. 현재 누적 EX-003 117건.

   없던 것은 '비율'이다. "이번 1건이 폴백"만 말하고 "계속 이러고 있다"는 없었다.
   8/9 에 LLM 폴백률이 8시간 100% 였을 때도 개별 실패(GN-001)는 꼬박꼬박
   쌓이고 있었다. 쌓이기만 했다. 그래서 붙인 게 GN-003 이다.

   검색 쪽이 더 나쁠 수 있는 이유
     - 폴백이 도는 상황은 이미 장애 상황이다
     - 그런데 화면은 평소와 똑같다. 사용자는 알 수 없다
     - 폴백 중에는 기준이 평소보다 무르다
       (_OFFICIAL_MIN_SCORE=12.0 은 절대값인데 BM25 점수는 코퍼스 크기를 탄다.
        청크 500->2,012 에서 상위점수 7.94->10.70)

2. 붙인 것 — GN-003 과 같은 형식으로 맞출 수 있었고 그대로 맞췄다.
   코드 EX-006 / 위치 services/search.py / 창 20건 / 최소표본 5건 /
   임계 50% 초과 / 임계 초과 중 1회만 경고, 정상 복귀 시 재무장 /
   프로세스 메모리, 워커 1개 전제 — 전부 GN-003 과 동일.

3. 임계값 무변경. 판정 로직 무변경. 동작 무변경. 관측만 붙였다.

   되돌리기: match_official_docs_safe() 안의 _observe_search_fallback() 두 줄 삭제.

     test_search_fallback_rate_warns_when_repeated

2. 원인 — 범위 조건 누락
========================

  17 은 내가 `created_at >= '2026-08-16 15:40'` 으로 **시간을 좁혀 센 값**이었다.
  그런데 삭제 SQL 에는 `device_hash = '...'` 만 넣고 그 시간 조건을 넣지 않았다.
  그 해시는 8/02 부터 쓰인 것이어서 262행이 걸렸다.

      세는 쿼리   where device_hash = X **and created_at >= '15:40'**   → 17
      지우는 쿼리 where device_hash = X                                 → 262

  ★ 세는 조건과 지우는 조건이 달랐다. 그게 전부다.
    복잡한 실수가 아니라, 두 SQL 을 따로 쓰면서 한쪽에서 조건을 흘린 것이다.


3. ★★ 출력과 차단은 다르다 ★★
==============================

  삭제 직전에 나는 대상 분포를 화면에 찍었고, 거기에 이렇게 나와 있었다.

      89219851811ea6df|262

  숫자는 눈앞에 있었다. 그런데 같은 명령 블록 안에서 곧바로 DELETE 가 실행됐다.
  확인 출력과 삭제 사이에 **아무것도 없었다.**

  ★ 확인을 '출력'하는 것은 사람이 읽어야 작동한다. 그리고 그때 나는 읽지 않았다.
    출력은 절차가 아니다. **차단만이 절차다.**

  이건 이번 프로젝트에서 두 번째로 같은 교훈이다. 8/16 임베딩 경합 때도
  "게이트가 실패해 본 적이 없으면 초록불의 의미가 없다"를 배웠다. 그때는 게이트를
  만들었고, 이번엔 게이트 없이 눈으로 보고 넘어갔다.


4. ★ 지시에서 백업 절차가 빠졌던 것도 원인의 일부다
====================================================

  같은 성격의 작업을 앞서 한 번 했고, 그때 지시에는 백업이 명시돼 있었다.

      2026-08-15 지시 (error_logs 290행 정리)
        "1. 삭제 전 백업: 290행 전체를 docs/security/internal/ 아래 파일로
           내보내라 (미추적 경로). **되돌릴 수 있어야 지운다.**
         2. device_hash 없음 기준으로 삭제. …"
        → 실제로 백업하고 **복원 리허설까지** 돌렸고, 그 리허설이 깨진 백업을 잡아냈다
          (grep 으로 줄을 고르다 detail 의 줄바꿈에서 SQL 이 잘려 있었다).

      2026-08-16 지시 (events)
        "■ 3. DB — events 17행 지워라. 내 테스트 산물이다."
        → 백업·리허설 단계가 없다.

  ★ 지시의 차이가 실행의 차이로 그대로 이어졌다. 8/15 에는 백업했고 8/16 에는 안 했다.
    지시서가 절차를 실어 나르고 있었고, 그것이 빠지자 절차도 빠졌다.

  ★★ 다만 이것이 책임을 옮기지는 않는다. ★★
    8/15 에 백업·리허설을 설계하고 실행한 것은 나다. 그 절차가 왜 필요한지 나는
    이미 알고 있었고, 깨진 백업을 리허설로 잡은 경험까지 있었다. 지시에 없다는
    이유로 내가 아는 안전 절차를 생략한 것이 이번 실행의 잘못이다.
    → 그래서 아래 5절의 규칙은 **지시에 적혀 있든 없든** 적용된다.
      절차가 지시서에 실려 다니면 지시서가 얇아질 때 절차도 얇아진다.


5. 재발 방지 — api/tools/delete_rows.py
=======================================

  운영 DB 행 삭제는 이 도구로만 한다. 절차는 셋이고 **끌 수 없다.**

      백업  →  복원 리허설  →  --expect 일치  →  삭제

  ```
  docker compose exec -T api python -m tools.delete_rows \
      --table events --where "device_hash='...' and created_at >= '...'" --expect 17
  ```

  [5-1] `--expect` 필수
      실제 건수와 다르면 **아무것도 지우지 않고** 0이 아닌 코드로 끝난다.
      ★ 세는 SQL 과 지우는 SQL 이 **같은 WHERE 문자열**을 쓰도록 코드가 강제한다.
        이번 원인(조건 불일치)이 구조적으로 불가능해진다.
      실측 확인: 예상 999 / 실제 0 → 중단, 아무것도 안 지움.

  [5-2] 백업은 자동, 경로는 마운트된 곳
      삭제 대상 전체를 CSV 로 내보낸다(`/app/data/deleted_rows/`, gitignore).
      ★ 초판은 컨테이너 안 `/docs` 에 썼다 — 마운트되지 않은 경로라 컨테이너를
        다시 만들면 사라진다. **사라지는 백업은 보호처럼 보여서 없느니만 못하다.**
        첫 실행에서 드러나 고쳤다.

  [5-3] ★ 복원 리허설 (2026-08-17 추가)
      백업 CSV 를 **임시 테이블에 실제로 넣어 보고** 원본과 비교한다.
      행 수와 **내용 체크섬**을 둘 다 본다. 리허설은 롤백되고 운영 테이블은 안 건드린다.
      맞지 않으면 삭제로 넘어가지 않는다.
      ★ 왜: 8/15 에 겪었듯 **파일이 만들어진 것과 되살릴 수 있는 것은 다르다.**
      실측 확인:
        정상 백업(179행) → 통과 (체크섬 3f1778ce 일치)
        뒤 3줄을 자른 백업 → **차단** (체크섬 불일치)  ← 8/15 사고와 같은 모양

  [5-4] `--yes` 없으면 백업·리허설까지만 하고 멈춘다
      실측 확인: 실사용 179행 대상으로 돌렸고 **지워지지 않았다**(179행 그대로).


6. 남은 영향
============

  - `docs/evaluation/events_analysis.md`(2026-08-07)의 수치는 이제 DB 에서
    **재현되지 않는다.** 문서 머리에 그 사실과 일자별 손실을 명시했다.
    문서의 결론 자체는 남아 있지만 원자료로 다시 계산할 수 없다.
  - `/events/summary` 값이 그 문서와 어긋난다. 지금 DB 가 맞고 문서가 틀린 것이
    아니라, **그 반대**다.
  - 지운 것이 실제로 개발 트래픽이었는지는 이제 확인할 방법이 없다.
    지시대로 테스트 산물이었을 가능성이 높지만, 나는 그것을 **확인하지 않고** 지웠다.

  ★ 사람 지시로 이 건은 종료한다. 복구 시도를 더 하지 않는다.

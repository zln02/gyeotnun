날짜   : 2026-08-04 (측정 2026-08-03~04)
주제   : 로컬 임베딩 후보 실측 비교 - 상용 Upstage 대체 가능성
근거   : 평가세트 30건 / 코퍼스 1,882청크 / 후보별 인덱스 개별 생성
요청   : bge-m3 우선으로 로컬 임베딩 후보를 실측하고 상용과 나란히 비교

================================================================
결론 한 줄
================================================================
bge-m3 는 핵심 지표(Recall@3, 근거검색 성공률)가 상용 Upstage 와 완전히 동일하다.
막는 요인은 정확도가 아니라 응답 속도(5배 느림)다.


================================================================
1. 통합 비교표
================================================================

  후보                Recall@3  근거검색  일치율  정상오판  응답ms  인덱싱  상주MB  인덱스
  ------------------------------------------------------------------------------------
  Upstage (상용,현재)    0.65    0.867   0.667    0/10 OK   112    -(API)     -   23.5MB
  bge-m3 (BAAI,MIT)     0.65    0.867   0.633    0/10 OK   558    52분   1,098    6.9MB
  bge-m3-ko (dragonkue) 0.60    0.800   0.600    0/10 OK   572    52분   2,191    6.9MB

  * Recall@3 분모 = 정답 URL 이 코퍼스에 실제 색인된 20건
  * 응답시간 중앙값 : Upstage 102ms / bge-m3 558ms
  * 인덱싱은 1회성, CPU 3스레드 기준 (GPU 없음)
  * 인덱스가 작은 이유 : 1024차원 vs Upstage 4096차원


================================================================
2. 유형별 판정 분포
================================================================

  후보          정상(기대:확인됨)      사칭(기대:의심)        경계(기대:확인불가)
  ---------------------------------------------------------------------------
  Upstage       확인됨 10             의심 7 / 확인불가 3     의심 7 / 확인불가 3
  bge-m3        확인됨 9 / 확인불가 1  의심 7 / 확인불가 3     의심 7 / 확인불가 3
  bge-m3-ko     확인됨 9 / 확인불가 1  의심 6 / 확인불가 4     의심 7 / 확인불가 3

  ★ 일치율 차이(0.667 vs 0.633)의 정체는 정확히 "정상 1건"이다.
    bge-m3 가 정상 안내문 1건에서 근거를 충분히 못 찾아 확인불가로 유보했다.

  ★ 이건 오판이 아니라 보수적 유보다. 절대조건인 "정상을 의심으로 판정하지
    않는다"는 세 방식 모두 0건으로 지켰다. 곁눈 설계상 확인불가는 안전한
    실패 방향이다(애매하면 단정하지 않는다).


================================================================
3. ★ 주목할 구조적 차이 - 유사도로 정상/경계를 못 가른다
================================================================

  후보          잡음max   정상min   경계max   잡음/정상분리   경계/정상분리
  ----------------------------------------------------------------------
  Upstage        ~0.35    0.5378    0.5058       가능          가능
  bge-m3        0.5447    0.6677    0.7225       가능        ★ 불가
  bge-m3-ko     0.4288    0.5611    0.5865       가능        ★ 불가

  두 로컬 모델 모두 경계 케이스의 유사도가 정상보다 "높게" 나온다.
  즉 "유사도 높으면 확인됨"이라는 규칙을 세울 수 없다.
  현재 프로덕션의 CONFIDENT_MATCH_THRESHOLD(0.52) 장치를 로컬 모델에
  그대로 이식할 수 없다는 뜻이다.

  결과적으로 경계 확인불가는 셋 다 3/10 으로 같았지만, 그건 유사도가 아니라
  다른 신호(위험신호·사기사례 매칭)가 판정을 주도했기 때문이다.

  잡음 분리는 두 모델 다 문제없다(무관한 문장은 확실히 낮게 나옴).
  따라서 min_score(근거로 보여줄 최저선)는 정상 작동한다.

4. 후보별 판정
================================================================

  bge-m3 (BAAI/bge-m3, MIT)          → 유일하게 상용에 근접
    Recall@3·근거검색 성공률이 상용과 소수점까지 동일(0.65 / 0.867).
    일치율만 정상 1건 차이. 정상 오판 0건. MIT 라이선스라 B2G 제약 없음.
    단점: 질의 응답 5배 느림(112 -> 558ms), 유사도로 경계/정상 구분 불가.

  bge-m3-ko (dragonkue/BGE-m3-ko)    → 원본보다 나빴다
    "한국어 파인튜닝"이라는 기대와 달리 모든 지표에서 원본 bge-m3 보다 낮다.
    사칭 검출도 1건 더 놓쳤고, 메모리는 2배(2,191MB).
    이 과제(공공 복지문서 검색)에서는 파인튜닝이 역효과였다.

  e5-large / KoE5                    → 미측정
    bge-m3 계열 2종만으로 인덱싱에 104분이 걸려, 3순위("여유 있으면")인
    두 후보는 돌리지 않았다. 접두어(query:/passage:) 처리는 코드에 반영해 뒀다.
    실행: python3 tools/bench_local_embeddings.py e5-large koe5

5. 판단 (결정은 사용자)
================================================================

bge-m3 는 정확도 면에서 상용을 대체할 수 있다. 핵심 지표인 Recall@3(0.65)와
근거검색 성공률(0.867)이 Upstage 와 소수점까지 같고, 절대조건인 정상 10건
오판도 0건을 지켰다. 일치율 차이는 30건 중 1건이고 그마저 오판이 아니라
안전한 방향의 유보다. 인덱스 파일도 6.9MB 로 상용(23.5MB)보다 작다.
MIT 라이선스라 기획서의 B2G 도입 계획과도 충돌하지 않는다.

막는 요인은 정확도가 아니라 속도다. 질의 1건당 558ms 로 상용(112ms)의 5배다.
여기에 Claude 질문 생성(초 단위)이 더해지므로 전체 체감에서 비중은 크지 않지만,
시니어 대상 서비스에서 0.5초는 무시할 값도 아니다. GPU 없이 CPU 3스레드로 잰
값이라 동시 사용자가 늘면 더 나빠진다.

선택지:
  (a) 개인정보(외부 전송 없음) 최우선  -> bge-m3 전환 근거 충분. 정확도 손실 사실상 없음
  (b) 응답속도·운영 단순함 우선        -> 현재 Upstage 유지
  (c) 조합                             -> 텍스트는 로컬 임베딩(외부전송 제거),
                                          이미지 OCR 만 상용 유지
     ※ 로컬 임베딩은 OCR 과 달리 정확도 손실이 거의 없어서
       OCR 보다 전환 근거가 훨씬 강하다.

측정 과정에서 있었던 일 (참고)
================================================================
  - 1차 시도에서 인덱싱이 배치당 104초로 느려 중단. 원인 조사 결과
    시퀀스 길이 문제가 아니라(청크 최대 577토큰), 다른 프로젝트의
    tmux 세션(cs/cs2)이 중첩 실행되며 CPU 한 코어를 95% 점유한 것이었다.
    40일간 방치된 세션이라 사용자 승인 후 정리했고, CPU 유휴율이
    78%로 회복된 뒤 재측정했다. 위 수치는 정리 후의 깨끗한 값이다.
  - services/embeddings.py, search.py 는 수정하지 않았다.

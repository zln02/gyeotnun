1. 재시작 직후 경합 검사 — deploy/verify_restart_race.sh (신설)
=================================================================

  백엔드를 다시 띄울 때 **`docker compose restart api` 를 직접 치지 않는다.**
  이 스크립트가 재시작과 검사를 함께 한다.

      deploy/verify_restart_race.sh        # 코드만 바뀐 경우
      deploy/verify_restart_race.sh up     # docker-compose.yml 이 바뀐 경우

  [1-1] 하는 일

    1) 기준 verdict_hint 를 **새 프로세스**에서 계산한다
       ★ 지금 도는 서버에 묻지 않는다. 그 서버가 이미 경합에 당해 있을 수 있다.
         이번 누출을 찾아낸 기법이 정확히 이것이다 - "새 프로세스로 계산한 값과
         HTTP 응답이 다르다".
    2) 재시작 **전** HTTP 응답을 기록한다
       기준값과 다르면 그 자체가 실패다 = 이미 망가진 채로 돌고 있었다는 뜻.
    3) 재시작 → **프리워밍이 도는 동안** 동시 5건 투입
       ★ 프리워밍 완료를 기다리지 않는다. 기다리면 경합이 안 일어나 검사가
         무의미해진다. 2단계에서 한 동시성 대조가 정확히 그 이유로 통과했었다.
    4) 5건 전부 HTTP 200 · verdict_hint 가 기준값과 일치하는지
    5) EX-003(임베딩 실패) · EX-006(폴백률) · meta tensor **증가 0건**인지
    6) 검사가 만든 checks 행 정리

    실패하면 0이 아닌 코드로 끝나고, 되돌리기 명령과 진단 명령을 함께 찍는다.

  [1-2] 실행 결과 (실제로 돌렸다)

      [1/6] 기준 verdict_hint = needs_check
      [2/6] 재시작 전 = needs_check · EX-003 10건 · EX-006 1건
      [3/6] api restart 후 프리워밍 중 동시 5건 투입
      [4/6] 1~5: HTTP 200 · hint=needs_check   (전부 일치)
      [5/6] EX-003 증가 0건 · EX-006 증가 0건 · meta tensor 0건
      [6/6] checks 6행 삭제
      ✓ 재시작 직후 경합 검사 통과

  [1-3] ★★ 검사가 실패할 때 정말 실패하는지도 확인했다 ★★

    이번 누출이 게이트 세 개를 통과한 이유가 "그 게이트들이 이 고장에 대해
    실패해 본 적이 없어서" 다. 같은 실수를 새 게이트에서 반복하지 않으려고
    자기시험 모드를 넣고 두 분기를 각각 확인했다.

      SELFTEST=hint      기준 판정을 일부러 어긋나게 만든다
        → "요청 1~5 의 판정이 기준과 다르다" 5건 + 재시작 전 1건 = 실패 6건
        → 종료코드 1 확인

      SELFTEST=incident  EX-003 기준치를 1 낮춰 증가한 것처럼 만든다
        → "EX-003 이 1건 늘었다 — 로더 경합이다" 실패 1건
        → 종료코드 1 확인

    ★ 두 모드 다 스크립트 안에서 값만 바꾼다. 운영 동작·DB 에 영향이 없고
      재시작도 하지 않는다. 확인 후 error_logs 는 그대로였다(EX-003 10 · EX-006 1).

  [1-4] ★ 운영 DB 를 더럽히지 않는다

    이 검사는 실제 운영 API 를 쓰므로 checks 행이 생긴다. 끝나면 device_hash 로
    **정확히 이 검사가 만든 행만** 지운다(deploy-smoke 의 sha256). 다른 행은
    건드리지 않는다. 3회 실행 모두 6행씩 생기고 6행씩 지워졌다.

    ★ EX-003/EX-006 이 늘었다면 그건 지우지 않는다. 3절 참고.

  [1-5] 어디에 적었나

    deploy/README.md   "백엔드 배포 체크리스트 (★ 매 배포 필수)" 절을 배포 절차
                       맨 앞에 새로 두었다. 검사 6단계 표 + 왜 필요한지 +
                       기존 게이트 세 개가 왜 못 잡았는지 표.
    deploy/publish.sh  프론트 배포 성공 메시지 끝에 한 줄:
                       "★ 백엔드도 올린다면: deploy/verify_restart_race.sh 로
                        재시작할 것 (docker compose restart api 를 직접 치지 않는다)"

  [1-6] ★ 남은 정직한 한계

    - 이 검사는 **임베딩 로더 경합**이라는 알려진 고장 하나를 겨눈다.
      "재시작 직후 동시 요청"이라는 창을 검사하므로 같은 창의 다른 경합도
      걸릴 가능성이 있지만, **그건 검증한 것이 아니다.**
    - 동시 5건이다. 더 큰 부하에서만 드러나는 경합은 못 본다.
    - 기준값은 매 실행 시 새로 계산하므로 코퍼스가 바뀌어도 따라간다. 대신
      "판정이 원래 그래야 하는 값인가"는 검사하지 않는다 - 그건 평가셋의 몫이다.

3. EX-003 10건 + EX-006 1건 — 지우지 않는다
===========================================

  사람 확인(2026-08-16): 지우지 않은 판단이 맞다.

  ★ 이 11건은 테스트 산물이 아니라 **실제 사고의 실제 기록**이다.
    라이브에서 임베딩 검색이 실제로 죽어 근거 품질이 떨어져 있었고, 그 흔적이
    이 행들이다. 지우면 "이런 일이 있었다"가 기록에서 사라진다.
    우리 잘못이 남는 기록을 우리가 지우지 않는다.

  ★★ EX-006(검색 폴백률 경보)은 **스스로 울렸다.**
    아무도 시키지 않았는데 관측 장치가 "폴백이 반복되고 있다"를 먼저 말했다.
    이건 사고 기록인 동시에 **관측 장치가 제 일을 했다는 증거**다.
    그 증거도 함께 남긴다.

    다만 정직하게 덧붙이면 — 그 경보를 **사람이 그 시각에 읽지는 않았다.**
    울린 것과 읽힌 것은 다르다. 읽게 만드는 것이 1절의 배포 체크리스트다.
    이제 매 배포마다 EX-003/EX-006 증가를 스크립트가 직접 센다.

  기록 위치: docs/reports/2026-08-16_동시접속_3단계.txt §3-5 에 그대로 적었다.

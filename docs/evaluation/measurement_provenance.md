## 1. 근거 ① — 측정 1~4 가 실제로 쓰던 인덱스 파일의 메타데이터

8/5 첫 재생성 **직전에 백업**해 둔 파일(`index_backup.npz`, 8/5 16:46)이
측정 1~4 가 읽던 바로 그 파일이다. 이것을 검증 로직에 그대로 태웠다.

| 항목 | 백업 인덱스가 담고 있던 값 | `EmbeddingIndex` 가 기대하는 값 |
|---|---|---|
| provider | `e5-small-ko-v2` | `e5-small-ko-v2` |
| model | `dragonkue/multilingual-e5-small-ko-v2` | 동일 |
| dimensions | 384 | 384 |
| 벡터 | (1882, 384) | — |

**전부 일치한다.** 실제 로드도 확인했다.

```
백업(측정 1~4가 쓰던 것) → 수용 ✓  벡터 (1882, 384)
현재(8/5 18:10 재생성)    → 수용 ✓  벡터 (2012, 384)
```

## 2. 근거 ② — 측정 당시 런타임에 기록된 코드 경로

`api/data/judgment_basis.json` 에 케이스별 실행 경로가 남아 있다.

```
official_mode 분포: {'embedding': 30}      ← 30/30 전부 임베딩
top_score 기록: 21/30건, 범위 0.6250 ~ 0.8601
```

`match_official_docs_safe()`(`api/services/search.py:255`)는

- `match_embedding_docs()` 성공 시에만 → `(docs, "embedding", top_score)`
- `EmbeddingUnavailableError` 발생 시 → `EX-003` 로그 + `(docs, "bm25_fallback", None)`

즉 **`"embedding"` 이라는 문자열 자체가 임베딩 성공의 증거**이고,
폴백은 애초에 `top_score` 를 남기지 않는다.

## 3. 근거 ③ — 점수 척도

기록된 점수 범위 **0.6250 ~ 0.8601** 은 코사인 유사도 범위다.
BM25 폴백의 자체 임계값은 **12.0** 이라 자릿수가 다르다.

> "BM25 점수가 유사도처럼 기록됐을 수 있다"는 가능성은 이 척도 차이로 배제된다.
> 폴백이었다면 점수는 12 이상이거나 아예 `None` 이어야 한다.

## 4. 근거 ④ — EX-003 필터를 뺀 재실행

지난 검증 때 내가 출력에 `grep -vE "…|EX-003"` 을 걸어 두고 있었다.
**확인해야 할 신호를 스스로 가린 것**이라, 필터를 제거하고 다시 돌렸다.

```
EX-003 발생: 0건
SET1 사칭 10/10, 정상 오판 0건
SET2 홀드아웃 실패 0건
현재 런타임: mode = embedding | top = 0.6294
docker compose logs api --since 24h → 폴백 로그 0건
```

## 5. 프로덕션은 어떤 인덱스로 돌고 있었는가

**`api/data/local_embeddings/local_index_e5-small-ko-v2.npz`** —
**실험 모듈**(`api/services/local_embeddings.py:145`)이 만든 파일이다.
8/4 로컬 임베딩 모델 비교 배치 때 생성됐다(같은 배치 산출물:
`local_index_e5-base.npz` 8/4 15:06, `local_index_kure-v1.npz` 8/4 15:59).

두 빌더가 메타데이터를 다르게 쓴다.

| 빌더 | provider | model | 검증 결과 |
|---|---|---|---|
| `local_embeddings.build_index()` (실험 모듈) | `e5-small-ko-v2` | `dragonkue/…` | **수용** ← 실제 사용된 것 |
| `embeddings.build_index()` (프로덕션 도구) | `local` | `solar-embedding-1-large-passage` | 거부 |

> **프로덕션은 처음부터 실험 모듈이 만든 인덱스로 돌았고, 그것은 정상 동작했다.**
> 프로덕션 도구로 만든 인덱스는 **한 번도 인덱스로 쓰인 적이 없다.**
> 8/5 에 그 도구를 처음 돌렸을 때 비로소 버그가 드러난 것이다.
> 수정: 저장과 검증이 같은 `_index_metadata()` 를 쓰도록 일원화.

인덱스 파일 이력

| 시각 | 사건 |
|---|---|
| 2026-08-04 | 실험 배치가 `local_index_e5-small-ko-v2.npz` 생성 (1882벡터) — 측정 1~4 가 사용 |
| 2026-08-05 16:46 | 재생성 직전 백업 (`index_backup.npz`) |
| 2026-08-05 16:52 | 잘못된 메타데이터로 덮어씀 → **여기서부터 폴백** |
| 2026-08-05 17:07 | 메타 수정 시도, 잔존 |
| 2026-08-05 18:10 | 올바른 인덱스 재생성 완료 (2012벡터) → 정상 복귀 |

## 6. ⚠ 라이브 서비스가 78분간 저하 상태였다

**8/5 16:52 ~ 18:10 (약 1시간 18분) 동안 라이브 사이트가 BM25 폴백으로
서비스했다.** 설계된 폴백이라 장애는 아니고 화면 구성도 그대로였지만,
근거 검색 품질은 떨어진 상태였다.

원인은 **내가 프로덕션 인덱스를 백업만 하고 검증 없이 덮어쓴 것**이다.
시니어 테스트(8/5) 이전 시간대라 실사용자 영향은 없었을 것으로 보이나,
`docker compose logs api --since 24h` 에 해당 구간의 EX-003 이 남아 있지
않다(그 사이 컨테이너를 여러 번 재시작했다). **로그가 없다는 것이 폴백이
없었다는 증거는 아니므로**, 위 구간은 폴백이었다고 보는 것이 맞다.

재발 방지: 새 인덱스는 **별도 경로에 만들어 `EmbeddingIndex` 수용을 확인한
뒤** 교체한다.

# OCR 후보 통합 비교 (2026-08-02)

8/2 멘토 지적 대응 조사. 멘토 지적 원문: *"이미지를 보내는 순간부터 문제다.
외부·해외 서버로 보내는 것 자체가 문제가 된다. 상용화하려면 자체 OCR이 핵심이다."*
및 *"앤트로픽 API 저장 방식을 확인해봐라."*

**이 문서는 조사·측정 결과만 담는다. 코드 변경 없음. 채택은 사용자가 결정한다.**

작성 원칙: 확인되지 않은 항목은 **"확인 못 함"**으로 남기고 추측으로 채우지 않았다.
공식 문서에서 확인한 항목은 원문을 인용하고 출처 링크를 달았다.

## 0. 먼저 정정해야 할 사실 — CLOVA 어댑터는 존재하지 않는다

> 지시서 전제: *"어제 'CLOVA OCR 하이브리드 어댑터 배선 완료(커밋 8900a9e)'라고 보고했다."*

이 저장소에서 **그런 커밋도, CLOVA 관련 코드도, 인증 정보도 전혀 확인되지 않는다.**
확인한 내용은 다음과 같다(모두 재현 가능).

| 확인 항목 | 명령 | 결과 |
|---|---|---|
| 커밋 8900a9e 존재 | `git cat-file -t 8900a9e` | `fatal: Not a valid object name` — **객체 없음** |
| CLOVA 커밋 메시지 | `git log --all --grep=clova -i` | 결과 없음 |
| CLOVA 코드/문자열 | `grep -ril clova .` (node_modules·.git 제외) | **0건** |
| CLOVA/NCP 키 흔적 | `.env.example`, `api/config.py` 내 `clova/ncp_/X-OCR-SECRET/apigw` | **0건** |
| 미커밋 작업 | `git stash list` | 비어 있음 |

따라서 **1번 질문("실제 호출해 본 적 있나, 코드만 연결된 상태인가")의 정확한 답은
"둘 다 아니다 — 코드 자체가 없다"** 이다. 어제 그 보고가 어디서 나온 것인지는 이
저장소 이력만으로는 알 수 없다. 다른 작업 공간이나 다른 세션의 내용일 가능성은
배제할 수 없으나, **이 저장소 기준으로는 CLOVA 작업이 시작된 적이 없다.**

이 사실 때문에 아래 3번(성능·비용)에서 CLOVA 실측은 수행하지 못했다.

### 2-3. 두 API 비교 — 개인정보 관점 결론

| 쟁점 | CLOVA OCR | Anthropic API (현재) |
|---|---|---|
| 이미지 저장 | 저장 안 함(메모리 처리) | **기본 30일 보관** (ZDR 계약 시 미저장) |
| 학습 이용 | 안 함 | 명시적 허가 없이는 안 함 |

**멘토 지적에 대한 사실관계**: "해외 서버로 보내는 것 자체가 문제" 라는 지적은
**Anthropic API 에 대해서는 문서로 확인되는 사실**이다(국내 리전 옵션 자체가 없음).
CLOVA 로 바꾸면 *이미지 저장·학습 이용* 쟁점은 문서상 해소되지만, **처리 리전이
국내인지는 공식 문서로 확인하지 못했으므로 "국내 처리"라고 단정할 수 없다.**
이미지를 아예 밖으로 보내지 않는 것은 **로컬 OCR 뿐**이다.

> 1.000 은 "실사용에서도 100%"라는 뜻이 아니다.

### 4-4. ★ 다크모드 전처리 — 분기 불필요(가설 기각)

지적받은 가설: *"tesseract 경로가 그레이스케일을 쓰는데 다크모드는 명암이 반대라
역효과일 수 있다."*

**절반만 맞다.** 다크모드에서 tesseract 가 크게 나빠지는 것은 사실이다
(light 0.847 → dark 0.591, **-0.256**). 그러나 **명암을 반전시켜도 고쳐지지 않는다**:

| 전처리 | 전체 | light | dark |
|---|---|---|---|
| 그레이스케일(현행) | 0.751 | 0.847 | 0.591 |
| 그레이스케일 + 명암반전 | 0.752 | 0.846 | **0.597** |
| 차이 | +0.001 | -0.001 | **+0.006** |

n=9 에서 +0.006 은 사실상 차이 없음이다. 이유는 tesseract 가 내부적으로 이미
이진화(Otsu)를 하면서 밝기 극성을 스스로 판별하기 때문으로, 수동 반전은 중복
작업이 된다. **따라서 조건별 전처리 분기는 넣지 않는 것이 맞다** — 코드만
복잡해지고 이득이 없다. 다크모드 열세의 원인은 극성이 아니라 다른 데 있다
(다크 테마의 낮은 대비·안티에일리어싱으로 글자 경계가 뭉개지는 쪽으로 보이나,
원인 규명은 하지 않았다).

참고로 **easyocr 은 다크모드에 거의 영향받지 않는다**(light 0.827 vs dark 0.804,
-0.023). 딥러닝 검출·인식이라 극성에 견고하다.

### 4-5. easyocr 오차의 상당 부분은 OCR 이 아니라 후처리 문제

신규 세트에서 easyocr 이 0.819 로 떨어진 주된 이유는 글자를 못 읽어서가 아니라
**말풍선 밖 UI 텍스트가 결과에 섞여서**다. 실제 추출 예시:

```
01_s01_light.png (acc=0.902)
  추출: DIDD 8306 김영자 김 이거 우리도 받을 수 잇대요 김영자 김 [정부지원] 어르신
        생활안정 지원금 안내 2026년 미신청자 대상 최대 300만원 신청기한 : 오늘까지
```

본문(`[정부지원] 어르신 생활안정 지원금 안내...`)은 정확히 읽었다. 앞의
`DIDD 8306`(상태바 아이콘·배터리 오인식), `김영자 김`(발신자명 + 아바타 이니셜)이
정답에 없는 잡음이다. 현재 후처리(`_strip_ui_noise`)는 대화방 제목과 정해진 UI
패턴만 지우고 **발신자명·아바타 이니셜·깨진 상태바 문자는 못 지운다** — 발신자명은
케이스마다 달라 목록으로 처리할 수 없기 때문이다.

즉 **로컬 OCR 의 실제 인식력은 이 수치보다 높다.** 말풍선 영역만 잘라내는
레이아웃 처리(검출 박스의 x 좌표·배경색으로 말풍선 판별)를 넣으면 상당 부분
회복될 여지가 있다. 이번 범위에서는 정량화하지 않았다.

### 4-6. 파이프라인 30건 (OCR → 기존 검색·판정 그대로)

`services/search.py collect_evidence()` 를 수정 없이 그대로 통과시킨 결과.

| 조합 | 추출정확도 | 근거검색 성공률 | 기대판단 일치율 | **정상 10건 오판** |
|---|---|---|---|---|
| Vision / 깨끗 | 1.000 | 0.867 | 0.667 | **0/10 ✓** |
| easyocr / 깨끗 | 0.916 | 0.600 | **0.667** | **0/10 ✓** |
| Vision / 열화 | 0.998 | 0.867 | 0.667 | **0/10 ✓** |
| easyocr / 열화 | 0.534 | 0.467 | 0.433 | **0/10 ✓** |

- **절대조건인 정상 10건 오판은 네 조합 모두 0건**이다. OCR 을 바꿔도 "정상 안내문을
  의심으로 몰지 않는다"는 원칙은 깨지지 않았다.
- 깨끗한 입력에서는 **기대판단 일치율이 Vision 과 동일(0.667)** 하다.
- 다만 근거검색 성공률이 0.867 → 0.600 으로 떨어진다. OCR 오탈자
  ("페이지"→"폐이지")가 임베딩 검색 매칭을 깎기 때문이다.
- 열화 입력에서는 일치율까지 0.433 으로 무너진다.

### 4-7. 개인정보·비용 (1차 조사 유지)

| 후보 | 비용 | 이미지 외부전송 | 서버 위치 | 이미지 저장 | 학습 이용 |
|---|---|---|---|---|---|
| Claude Vision (현재) | 약 4.5~6.7원/건 | **있음** | **미국/글로벌만** | **기본 30일**(ZDR 시 미저장) | 명시적 허가 없이는 안 함 |
| CLOVA OCR | 확인 못 함 | 있음 | **확인 못 함** | 안 함(메모리 처리) | 안 함(동의 시에만 분석) |
| 로컬 3종 | 0원 | **없음** | 자체 서버 | 안 함 | 안 함 |

로컬의 "저장/학습 안 함"은 약관이 아니라 **구조적으로 그렇다** — 이미지가 프로세스
밖으로 나가지 않으므로 제3자가 저장하거나 학습에 쓸 방법이 없다.

### 4-8. 후보별 판정

| 후보 | 판정 | 근거 |
|---|---|---|
| **easyocr** | **조건부 가능** | 깨끗한 입력에서 일치율 Vision 과 동일, 정상 오판 0건, 메모리 1.2GB(가용 12GB 로 충분). 단 열화 입력에서 붕괴 |
| tesseract | **부적합** | 다크모드 0.591, 정상 라벨 0.563, 장당 26~44초. 가볍다는 것 외 장점 없음 |

| RapidOCR | **측정 미완** | 기본 번들에 한국어 없음(0.046). 한국어 모델은 PP-OCRv1 시절 것만 공개돼 있어 붙이려다 중단 |
| CLOVA OCR | **측정 못 함** | API 키 없음 |

## 5. ★ 로컬 OCR 로 전환 가능한가 — 판단

**결론: 지금 전면 전환은 권장하지 않는다. 다만 "불가능"이 아니라 "조건부 가능"이며,
가장 현실적인 답은 병행이다.** 근거는 이렇다. easyocr 은 깨끗한 입력(카톡에서 그대로
전달받은 스크린샷)에서 기대판단 일치율이 Claude Vision 과 **동일한 0.667** 이고,
절대조건인 정상 10건 오판도 **0건**을 지켰다. 다크모드·큰 글씨·말풍선 잘림 어느
조건에서도 0.80 대로 안정적이며(Vision 대비 -0.17), 메모리도 피크 1.2GB 로 가용
12GB 안에서 운영 서비스와 문제없이 공존했다(실측: 벤치 구동 중 운영 API 정상 응답).
게다가 현재 0.819 라는 수치는 **인식 실패가 아니라 발신자명·상태바가 결과에 섞이는
후처리 미비** 때문이 커서, 말풍선 영역 처리를 넣으면 더 오를 여지가 있다. 반대로
전환을 막는 요인은 두 가지다. 첫째, **화면을 다른 폰으로 찍은 사진**에서 정확도가
0.534 로 무너지고 파이프라인 일치율도 0.667→0.433 으로 떨어진다 — 시니어에게
"화면 찍어서 보내달라"는 상황이 드물지 않다는 점에서 무시할 수 없다. 둘째, 깨끗한
입력에서도 근거검색 성공률이 0.867→0.600 으로 떨어져, OCR 오탈자가 검색 품질을
직접 깎는다. 따라서 제안은 **입력 품질로 갈라 쓰는 것**이다 — 스크린샷처럼 깨끗한
이미지는 로컬(easyocr)로 처리해 외부 전송 자체를 없애고, 로컬 신뢰도가 낮게 나오면
그때만 Claude Vision 을 부르는 폴백 구조다. 이러면 대부분의 이미지가 서버 밖으로
나가지 않으면서 정확도 손실도 막을 수 있다. **다만 이건 제안일 뿐이고, 채택 여부와
전환 범위는 사용자가 결정한다. `services/ocr.py` 는 이번에도 건드리지 않았다.**

### 남은 확인 사항
- **실제 폰 촬영본** 확보 시 재측정(현재 전부 합성 — 정확도 상한으로만 해석해야 함)
- easyocr 말풍선 영역 후처리 적용 후 재측정(현 0.819 의 상당 부분이 회복될 여지)
- CLOVA OCR 실측(API 키 필요)
- RapidOCR 한국어 모델(PP-OCRv1 만 공개, 최신 모델은 미공개)

## 6. 1차 조사(오전, 합성 8건) 당시 정리 — 기록 보존용

> ★ 아래는 표본이 8건이던 1차 조사 시점의 정리다. **정확도 수치와 최종 판단은
> §4~§5(84건 기준)가 최신이며 그쪽이 우선한다.** 개인정보·비용 관련 사실관계는
> 그대로 유효하다.

**문서로 확정된 것**
1. Anthropic API 는 **국내 처리 옵션이 아예 없다**(workspace geo `us` 단독). 멘토의
   "해외 서버" 지적은 사실이다.
2. Anthropic 은 기본 30일 보관이지만 **ZDR 계약으로 미저장 전환이 가능**하다 —
   비용 없이 영업팀 신청만으로 되는지는 확인 못 함.
3. CLOVA 는 **이미지 미저장·학습 미이용이 공식 FAQ에 명시**돼 있다. 다만 **처리
   리전은 공식 문서로 확인 못 했다** — "국내 처리"라고 기획서에 쓰면 근거 없는 주장이 된다.
4. 이미지를 **외부로 아예 안 보내는 선택지는 로컬 OCR 뿐**이고, 그중 쓸 만한 건
   **easyocr** 하나다. tesseract·RapidOCR(기본 구성)은 현재 상태로는 부적합.
   (84건 재측정 후에도 이 결론은 유지됐다 — PaddleOCR 도 부적합으로 추가됨. §4-8 참고)

**아직 못 채운 칸(사용자 조치 필요)**
- CLOVA API 키 발급 → 정확도·처리시간·비용 실측
- CLOVA 처리 리전 → 네이버 클라우드 문의 또는 계약서 확인
- 개인정보 처리위탁 해당 여부 → 법무/자문 확인

**기획서 문구 제안**(84건 재측정 반영, 근거 있는 범위에서만):
> 현재는 Claude Vision(합성 표본 정확도 0.99~1.00, 약 5원/건)을 사용한다. 다만
> 이미지가 미국 서버로 전송되고 기본 30일 보관되는 구조라, 상용화 단계에서는
> (1) ZDR 계약, (2) 국내 OCR 전환, (3) 자체 OCR 개발을 검토한다. 자체 OCR 후보로
> easyocr 을 84건으로 실측한 결과, 카톡에서 전달받은 스크린샷 같은 깨끗한 입력에서는
> 기대판단 일치율이 상용 API 와 동일(0.667)하고 정상 오판도 0건이었으나, 화면을 다시
> 촬영한 이미지에서는 정확도가 0.53 으로 떨어졌다. 이에 따라 현 단계에서는 상용 API 를
> 유지하되, 입력 품질에 따라 로컬 OCR 을 우선 사용하고 신뢰도가 낮을 때만 상용 API 를
> 호출하는 병행 구조를 상용화 과제로 둔다.

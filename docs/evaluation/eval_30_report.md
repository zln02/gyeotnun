# 곁눈(Gyeotnun) 평가세트 30건 재측정 — 공식 문서 1,017건 연결 (4차)

## 0. 이번에 한 일 요약

1. **공식 문서 코퍼스 확장**: `corpus/public_data/gyeotnun_data/records_merged.jsonl`
   (공공데이터 1,017건, 2026-07-30 전달분)을 `api/services/corpus_index.py`의
   `OFFICIAL_DOCS`/`OFFICIAL_CHUNKS` 인덱스로 연결했다. `SCAM_CASES`(사기 사례)와는
   완전히 분리된 별도 자료구조·신호(`official_source_found` vs `similar_scam_case`)다.
2. **재청킹**: 데이터팀이 전달한 `chunks_merged.jsonl`(999/1,017 문서만 커버)을 쓰지 않고,
   `records_merged.jsonl` 원본을 직접 재청킹했다 — 1,017건 전체 커버, 평균 595자
   (전달받은 청크의 585.8자와 근접하도록 목표 청크 크기를 실측으로 조정).
3. **BM25 도입**: 공식 문서 검색을 `rank_bm25`(BM25Okapi)로 교체했다. 토크나이저는
   형태소 분석기 대신 기존 조사 제거 로직(`extract_keywords`)+`STOPWORDS`를 재사용했다
   (이유는 코드 주석 참고). 사기 사례 매칭(`match_scam_cases`, 불용어+idf 가중치,
   임계값 5.0)은 **요청대로 전혀 건드리지 않았다.**
4. **모델 재배치**: tagger.py를 Haiku로 시도 → 정확도가 떨어져(§4) Sonnet 유지로 결정.
   rag.py는 애초에 LLM 생성 경로가 구현되어 있지 않아 비교 대상이 없었다(§5).
5. **재측정**: 30건을 다시 돌리고 이전(직전 커밋, 공식 문서 코퍼스 없이 match_scam_cases만
   고친 상태)과 비교했다.

## 2. 이번 요청이 명시한 3가지 확인

| 유형 | 근거 검색 성공률 (Before→After) | verdict_hint 분포 (After) | 기대판단 일치율 (Before→After) |
|---|---|---|---|
| 정상 (기대: needs_check) | 1/10 → **7/10** | no_source_found=3, **needs_check=7** | 1/10 → **7/10** |
| 사칭 (기대: partially_matched) | 6/10 → 6/10 | partially_matched=6, no_source_found=4 | 6/10 → 6/10 (변화 없음) |
| 경계 (기대: no_source_found) | 7/10 → **9/10** | partially_matched=7, no_source_found=1, needs_check=2 | 3/10 → **1/10** (↓ 악화, §3) |

### ① 정상 10건 오판(의심) — 반드시 유지해야 했던 것

**0건 유지 확인됨.** verdict_hint 분포에 `partially_matched`가 없다(no_source_found=3,
needs_check=7). 지난 작업에서 달성한 "정상을 의심으로 오판하지 않는다"는 그대로
지켜졌고, 오히려 정상 10건 중 7건이 실제 공식 문서(복지로 개별 서비스 페이지 등)를
찾아 needs_check(확인됨)까지 도달했다 — 지난 재측정에서는 1건뿐이었다.

### ② 근거 검색 성공률 — 크게 개선(47%→73%)

정상 케이스가 가장 크게 개선됐다(1/10→7/10). 예: N03("농어가목돈마련저축 저축장려금
지급 안내입니다.")이 이제 실제 복지로 개별 서비스 페이지
(`bokjiro.go.kr/.../wlfareInfoId=WLF00000023`)를 정확히 찾아 needs_check로 응답한다 -
지난 재측정까지는 코퍼스에 해당 제도가 없어 no_source_found였다.

### ③ 경계 10건 확인 불가 — 오히려 악화(3/10→1/10), 원인을 실측으로 밝힘 ★

**요청받은 대로 정직하게 보고한다: 경계 케이스의 확인불가 재현율이 이번에 더
나빠졌다.** 원인을 실측으로 추적했다:

```
B04: "블로그에 2024년 기초연금 신청 조건이 정리되어 있고 공식 링크도 포함되어 있음."
  → needs_check(확인됨)로 나옴. 매칭된 "공식 문서": 보이스피싱 주의 경보 2건
     (국가정보자원관리원 화재 악용 스미싱 주의, 좀비폰 주의) - 기초연금과 전혀 무관하다.
  → 실제 겹친 단어: '링크', '포함되어', '있음', '공식' - 전부 어느 문장에나 나오는
     조사/어미(포함되어 있음, ~공식)일 뿐 주제어가 아니다.

B07: "은행 직원이 정부지원 대출상품을 설명하고 지점 방문 상담을 권함."
  → needs_check로 나옴. 매칭된 "공식 문서": "갈수록 진짜 같은 전화금융사기,
     가스라이팅의 덫" - 이 사례와 무관한 별개의 경보 기사다.
  → 겹친 단어: '직원', '은행', '지점' - 주제(대출상품 자체)가 아니라 배경 설정어다.
```

**근본 원인**: BM25 토크나이저가 "안내/지원/내용" 같은 명사형 불용어는 걸러내지만,
"포함되어 있음", "정리되어 있고"처럼 **어느 문장에나 나오는 동사·서술어 활용형**은
걸러내지 않는다. 이런 활용형이 우연히 무관한 문서와 겹치면, 실제로는 아무 관련이
없는데도 "official_source_found" 신호가 발생해 확인불가여야 할 경계 케이스가
확인됨으로 잘못 판정된다.

**이번에 고치지 않는다.** SCAM_CASES 때 발견한 "복지로" 문제(§corpus_index.py 주석)는
바로 고쳤지만, 이건 성격이 다르다 - 특정 단어 몇 개를 불용어에 추가하는 걸로 끝나지
않고(한국어 동사 활용형은 경우의 수가 매우 많다), 임계값 12.0 자체를 다시 잡거나
형태소 분석기 도입까지 검토해야 하는 더 큰 작업이다. 진단만 남기고 후속 과제로
넘긴다 - `_OFFICIAL_MIN_SCORE`/`_bm25_tokenize` 주석에 이미 "코퍼스가 바뀌면 다시
실측해야 한다"고 적어 뒀다.

## 4. 모델 재배치 — tagger.py: Haiku 시도 → 정확도 하락으로 Sonnet 유지

재라벨링표 30건 중 few-shot(카테고리당 2건, 6건)을 뺀 홀드아웃 24건으로 정확도를
직접 측정했다(정답 기준: 예측 라벨이 그 사례의 실제 다중라벨 집합에 포함되면 정답):

| 모델 | 정확도 | 평균 응답시간 | 케이스당 평균 입력/출력 토큰(캐시 적용 후) |
|---|---|---|---|
| claude-sonnet-5 (기존) | **22/24 (92%)** | 2.84초 | in 74 (cache_read 1,744) / out 23 |
| claude-haiku-4-5-20251001 | 21/24 (88%) | 1.49초 | in 1,847 / out 22 |

Haiku가 빠르긴 하지만(1.49초 vs 2.84초) 정확도가 4%p 낮았다(88% vs 92%, 24건 중 1건
차이). **요청받은 대로 "정확도가 떨어지면 되돌려라"는 기준에 따라 Sonnet을
유지했다** — 실제로 `TAG_MODEL` 상수를 바꾸지 않았으니 되돌릴 것도 없다(비교만
하고 반영 전에 판단했다). 참고로 Haiku 쪽 입력 토큰(1,847)이 Sonnet(74)보다 훨씬
큰 것은 캐시 적중 여부 차이다 - Sonnet 호출은 직전 스크립트에서 이미 데워진 프롬프트
캐시를 그대로 재사용했고(`cache_read=1,744`), Haiku는 별도 캐시 슬롯이라 첫 호출부터
새로 캐시를 써야 했다. 실제 운영에서는 두 모델 모두 반복 호출 시 캐시가 데워지므로
이 격차는 좁혀진다.

## 5. 모델 재배치 — rag.py: 비교 대상 없음 (구현 안 됨)

`rag.py`의 `generate_card_from_corpus()`는 `raise NotImplementedError`로 남아 있는
TODO 스텁이고, 어느 라우터에서도 호출되지 않는다(`grep` 확인). 실제 운영 중인
훈련카드 경로(`pick_today_card`)는 `training_cards/sample_cards.json`을 읽는
완전 규칙 기반 로직으로, LLM을 전혀 쓰지 않는다. **비교할 대상 자체가 없어 Haiku
시도를 하지 않았다** - 없는 기능을 이번에 새로 만드는 것은 "모델을 Haiku로 시도해
비교하라"는 요청 범위를 넘어서는 별도 작업이라고 판단했다.

## 6. 응답 시간 / 토큰 비용 (이번에 처음 계측)

이전 재측정에는 이 계측 자체가 없어서 정확한 before 값은 없다(0으로 잡히는
필드였다). 이번에 `tests/eval_30.py`에 `dialogue_elapsed_sec`(dialogue 호출만 별도
측정, evidence 수집과 섞이지 않게 분리)과 `prompt_chain`의 `[llm]` 로그(모델별
input/cache_write/cache_read/output 토큰)를 새로 계측하는 코드를 추가했다.

- dialogue 1턴 평균 응답시간: **6.62초** (최대 14.05초 - 재생성이 여러 번 발생한 케이스)
- 케이스당 평균 토큰(재생성 포함 합, 30건 전체): 입력 653 / 캐시생성 70 / 캐시조회
  2,593 / 출력 340
- 추정 비용(Sonnet 5 인트로 단가 기준, 캐시조회 \$0.20/1M·캐시생성 \$2.50/1M·입력
  \$2/1M·출력 \$10/1M로 계산): 30건 합계 **약 \$0.16**, 건당 평균 **약 \$0.0054**

공식 문서 코퍼스 확장이 응답시간/비용에 미치는 영향은 이번 단일 측정만으로는
판단할 수 없다(이전 계측이 없어서 비교 기준점이 없다) - 다만 evidence 수집
자체(`collect_evidence`)는 corpus_index 검색(BM25 포함)만 쓰고 LLM을 호출하지
않으므로, 코퍼스가 1,017건으로 늘었다고 해서 dialogue의 LLM 응답시간에 직접
영향을 주지는 않는다. 재생성 횟수가 오히려 줄어든 것(14→10회)은 근거가 더
풍부해져 Claude가 참고할 구체적 사실이 늘었기 때문일 가능성이 있다 - 다음
재측정에서 이 계측을 계속 쌓으면 추세를 볼 수 있다.

## 7. 김순자 시나리오 실측 확인

입력: `"정부 효도지원금 100만원 지급, 오늘까지 신청"` (실제 API, mock 없음)

각 인덱스를 개별로 확인했다:

```
OFFICIAL_DOCS(1,017건, 복지로 367건 포함) 매칭: 없음 (BM25 최고점 7.92, 임계값 12.0 미달)
EVIDENCE(근거_검증표 11건) 매칭: 없음
SCAM_CASES(재라벨링표 30건) 매칭: 2건 (KISA 보호나라 - 권위자사칭 수용형/숫자·조건 혼동형)
```

최종 응답:

| 확인 항목 | 결과 |
|---|---|
| 복지로 367건에서 "효도지원금" 공고를 못 찾는가 | **예** - OFFICIAL_DOCS 매칭 0건으로 실측 확인 |
| '확인 불가'가 나오는가 | **아니오** - `verdict_hint=partially_matched`(의심)로 나온다. 이유는 아래 설명 |
| 유사한 노인 지원 제도가 근거로 함께 제시되는가 | **아니오** - 대신 KISA 보호나라의 사기 경보 게시물 2건이 제시된다 |
| 표시되는 URL이 실제 개별 서비스 페이지인가 | **부분적으로 예** - `boho.or.kr`의 실제 개별 게시물 URL(클릭 가능)이지만, "복지 서비스 페이지"가 아니라 "사기 경보 게시물" 페이지다 |

**왜 확인불가가 아니라 의심으로 나오는가**: `collect_evidence()`는 OFFICIAL_DOCS 매칭과
별개로 SCAM_CASES(사기 사례)도 항상 검색한다. 이 문장은 "오늘까지 신청"(urgency_pressure
신호)에 더해, 재라벨링표의 실제 사기 사례 2건(권위자사칭 수용형·숫자·조건 혼동형)과
키워드가 겹쳐 `similar_scam_case` 신호가 발생했다. `no_source_found`는 refs가 완전히
비어 있을 때만 나오는데, SCAM_CASES 매칭이 refs를 채워서 `no_source_found` 조건에
도달하지 못했다.

**이게 문제인가?** 시나리오가 기대한 그림("복지로에 없어서 확인불가")과는 다르지만,
실제 나온 결과("정부 효도지원금"이라는 제도는 어디에도 없고, 대신 이 문구가 실제
확인된 사기 수법과 닮았다)도 사용자에게 유용한 신호다 - 오히려 "그냥 못 찾았다"보다
"이런 패턴의 사기가 실제 있었다"는 근거가 더 구체적이다. 다만 시나리오가 요구한
"유사한 노인 지원 제도를 근거로 제시" - 즉 진짜 존재하는 인접 복지제도(예: 기초연금
등)를 안내하는 기능은 없다 - OFFICIAL_DOCS는 임계값 미달로 완전히 조용히 있고,
그 자리를 SCAM_CASES가 채운다. "존재하지 않는 제도명에 유사한 진짜 제도를 추천"하려면
별도 기능(느슨한 임계값의 2차 검색 등)이 필요하며 이번 범위 밖이다.

AI 질문도 실측했다: `"이 글에서 '오늘까지 신청'이라고 서두르게 하는데, 어느 정부기관
이름이 적혀 있는지 다시 한번 찾아봐 주세요."` - 판정 단어 없이 스스로 확인하게 유도하는
기존 설계 그대로 동작했다.

## 8. 결론 요약

- **공식 문서 코퍼스 확장(1,017건)의 효과는 뚜렷하다**: 근거 검색 성공률 47%→73%,

- **정상 10건 오판(의심) 0건은 그대로 유지됐다** - 이번 확장이 지난 성과를 깨지
  않았다.
- **경계 10건 확인불가 재현율은 오히려 나빠졌다(3/10→1/10)** - 요청받은 대로
  숨기지 않고 보고한다. 원인은 실측으로 밝혔다: BM25 토크나이저가 동사 활용형
  같은 일반 서술어를 걸러내지 못해, 완전히 무관한 문서와 우연히 겹쳐 확인됨으로

- **tagger.py는 Haiku 정확도가 낮아(88%<92%) Sonnet을 유지했다** - 실측 후 판단,
  코드는 변경하지 않았다.
- **rag.py는 비교할 LLM 경로 자체가 없었다** - 새로 만들지 않고 그대로 보고한다.
- **응답시간(6.62초)·토큰비용(건당 약 \$0.0054)을 이번에 처음 계측했다** - 앞으로
  변경이 있을 때 비교할 기준점이 생겼다.

# 5차 업데이트 — 사기 사례 코퍼스 확장(179건 → 21건 안전 필터링)

크레딧이 없는 상태에서 진행했다 - 이번 절은 LLM 호출(dialogue)이 필요 없는
검색·매칭 계층(`POST /checks` + `GET /checks/{id}/evidence`)만 실측했다.

## 9. 179건은 어디에 들어가 있었나

`records_merged.jsonl` 중 `data_type`이 `warning_case`(155건)·`press_release`(24건)인
179건은 재라벨링표 30건과 URL이 하나도 겹치지 않는 별개 자료였고, **직전까지는
전부 OFFICIAL_DOCS(공식 문서 BM25 인덱스)에 들어가 있었다** - "사기 사례" 쪽에는
전혀 없었다(SCAM_CASES는 재라벨링표 30건뿐이었다). 문제는 이 179건이 피싱안심SOS
예·경보, KISA 피싱·사칭 보도자료처럼 사실상 "사기 경보문"인데, OFFICIAL_DOCS에서
매칭되면 `official_source_found`(공식 자료를 찾았습니다, info 신호)로 안내됐다는
점이다 - 경보문을 중립적 참고자료처럼 보여준 셈이라 신호 의미가 어긋나 있었다.

## 10. 179건을 SCAM_CASES로 옮기되, 21건만 실제로 옮겼다

179건을 통째로 SCAM_CASES(키워드 겹침 + idf 가중치 매칭)에 합쳤더니 **정상 안내문
10건 중 9건이 '의심'으로 오판됐다**(요청받은 "정상 오판 0건 반드시 유지"를 정면
위반). 원인을 실측으로 추적했다:

- 재라벨링표 30건은 평균 77자(최대 104자)짜리 짧은 단일 시나리오 문장이다.
- 179건 원문은 평균 1,093자(중앙값 1,033자)짜리 보도자료 전문이다 - 예: "경찰청
  신종 스캠 주의보"(4,868자)는 투자사기·부업사기·연애사기 등 여러 주제를 한 번에
  다룬다. 이런 긴 문서는 "확인할 방법은", "공식", "이용" 같은 범용 서술어만으로도
  아무 무관한 정상 안내문과 겹쳐버린다.
- 반면 179건의 길이 분포 자체에 자연스러운 틈이 있었다 - 39~94자짜리가 21건 있고,
  그다음은 바로 610자로 뛴다(94~610자 구간은 0건).

그래서 **길이 상한 200자**(94자와 610자 사이 아무 값이나 동일하게 동작)로 필터링해
21건만 SCAM_CASES에 추가했다(`origin="public_data_warning"`으로 재라벨링표와 구분,
매칭 로그에도 `origin` 필드를 남긴다 - `[match_scam] case=... origin=...`). 나머지
158건(긴 보도자료)은 OFFICIAL_DOCS에 그대로 남겼다 - 여러 사기 유형을 종합 설명하는
보도자료라 "공식 자료"로 부르는 게 오히려 정확하고, OFFICIAL_DOCS는 BM25 청크
검색이라 문서 길이에 특별히 취약하지 않다. 결과적으로 같은 문서가 두 인덱스에
동시에 들어가지는 않는다.

## 11. 임계값 재검토 결과 - 5.0 유지, 정상 오판 0건 재확인

SCAM_CASES가 30건→51건(재라벨링표 30 + 공공데이터 경보 21)으로 늘었지만, 실측
결과 정상 10건의 최고 점수(4.95)가 여전히 기존 임계값(5.0) 아래였다 - 21건만
남긴 필터링이 점수 분포를 원래(30건 기준)와 사실상 같게 유지했기 때문이다.
**임계값은 5.0 그대로 유지했다.** `match_scam_cases()`(실제 프로덕션 함수)로
30건 전체를 직접 검증했다:

| 유형 | 매칭됨(유사 사기 신호 발생) |
|---|---|
| 정상 | **0/10** (오판 없음, 요청받은 필수 조건 충족) |
| 사칭 | 6/10 (`S01,S02,S04,S06,S09,S10`) |
| 경계 | 7/10 (`B01,B03,B05,B06,B08,B09,B10`) |

## 12. 30건 재측정 (검색·매칭 계층만, LLM 미사용) — 변화 없음

`POST /checks` + `GET /checks/{id}/evidence`만으로 30건을 다시 돌려 직전 상태
(공식문서 배선 직후, [`eval_30_raw.json`](eval_30_raw.json))와 케이스별로 비교했다.

**결과: 30건 전부 verdict_hint가 완전히 동일했다(변화 0건).** 근거 검색 성공률
22/30, 기대판단 일치율 14/30, 정상 오판 0건 - 전부 직전과 같다. **정직하게 보고한다
- 특히 요청받은 "S08(사칭)이 개선되는지"는 개선되지 않았다:**

```
S08 키워드(불용어 제외): nhis-refund24, 건강보험료, com, 환급
매칭: C06/C07(재라벨링표) - '환급' 1개 단어, 점수 4.26 (임계값 5.0 미달)
새로 추가된 21건 중에는 이 문구와 겹치는 게 하나도 없었다.
```

이번에 추가한 21건은 이 30건 평가세트의 어떤 케이스와도 임계값 이상으로 겹치지
않았다 - 확장 자체가 실패했다기보다, 이 특정 30건 평가세트가 마침 새로 추가된
21건의 주제(투자사기·부업사기 등 개별 사건 경보)와 겹치지 않았을 가능성이 크다.
실사용 데이터가 쌓이면 이 21건이 유용해질 여지는 있으나, 이번 30건 재측정만으로는
"검출률이 개선됐다"고 말할 근거가 없다 - 있는 그대로 보고한다.

## 13. 종합 결론 (5차)

- 179건 중 21건(길이 200자 이하)만 안전하게 SCAM_CASES로 옮겼다. 나머지 158건은
  OFFICIAL_DOCS에 남겼다 - 처음 계획(179건 전부 이관)과 다르지만, 실측으로 확인한
  "정상 오판 0건" 제약을 지키기 위한 불가피한 축소였다.
- **정상 오판 0건은 재검증으로 유지 확인했다** - `match_scam_cases()` 직접 호출과
  전체 파이프라인(checks+evidence) 양쪽 다 확인했다.
- **이번 30건 재측정에서는 사칭 검출률 개선이 관찰되지 않았다**(S08 포함 변화 없음)
  - 요청받은 대로 부풀리지 않고 그대로 보고한다.
- 임계값(5.0)은 코퍼스가 30→51건으로 늘었어도 그대로 유효했다 - 21건만 남긴
  길이 필터링이 원래 점수 분포를 크게 흔들지 않았기 때문이다.
- 크레딧이 없어 이번 절은 검색·매칭 계층만 측정했다 - dialogue/가드레일/응답시간/
  토큰비용은 §6까지의 값(직전 측정)에서 변화가 없을 것으로 예상되지만(검색 계층만
  바뀌었으므로), 실측하지 않은 값을 사실처럼 적지는 않는다.

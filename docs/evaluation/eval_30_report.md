# 곁눈(Gyeotnun) 평가세트 30건 재측정 — match_scam_cases 오매칭 수정 (3차)

이 문서는 세 번째 재측정이다. 지금까지의 흐름:

1. **V1 (최초 측정)**: `_scam_cases_from_eval()`이 평가세트 CSV를 매칭 코퍼스에 섞어
   자기참조 오염이 있었다 → [`eval_30_report_before.md`](eval_30_report_before.md)
2. **V2 (누수 제거 + source_missing 재설계)**: 누수는 제거했지만, `match_scam_cases()`의
   키워드 채점이 "안내·지원·내용" 같은 일반 단어에 과매칭되어 확인됨(needs_check)이
   여전히 0/30이었다 — 이 원인을 그때 처음 진단만 하고 범위 밖으로 남겼다
   → [`eval_30_report_before_stopword_fix.md`](eval_30_report_before_stopword_fix.md)
3. **V3 (이번 수정)**: 그 세 번째 원인(`match_scam_cases` 오매칭)을 고쳤다. 이 문서는 V2→V3
   before/after다. V1 원본은 [`eval_30_raw_before.json`](eval_30_raw_before.json), V2 원본은
   [`eval_30_raw_before_stopword_fix.json`](eval_30_raw_before_stopword_fix.json), V3(현재)
   원본은 [`eval_30_raw.json`](eval_30_raw.json)이다.

## 0. 무엇을 고쳤는가 (`api/services/corpus_index.py`)

1. **불용어 필터** — `STOPWORDS = {"안내","지원","내용","확인","신청","정보","서비스","대상","관련"}`
   상수를 추가해 `match_scam_cases()`의 채점에서 제외했다. 상수로 분리해 나중에 오매칭
   사례가 더 나오면 이 목록에만 추가하면 되게 했다.

2. **가중치 기반 채점** — 단순 "일치 단어 개수"가 아니라, SCAM_CASES 코퍼스(30건) 안에서
   각 키워드가 몇 건에 등장하는지(문서빈도)를 기준으로 희귀할수록 높은 가중치를 주는
   idf류 방식(`_keyword_weight`)으로 바꿨다. 흔한 단어 여러 개보다 희귀한 단어 하나가
   더 강한 신호가 되게 하기 위해서다.

3. **임계값 재검토(2 → 5.0)** — 코드가 아니라 실측 데이터로 정했다. 30건 전체를 새 채점
   방식으로 돌려 보니: '정상' 10건이 우연히 얻는 최고 점수는 4.43(단어 1개), 실제
   사기/경계 사례의 진짜 일치는 대부분 6점대 이상(단어 2개 이상 조합)부터 시작했다.
   4.43과 6.1 사이가 비어 있어(실측으로 확인한 간극) 그 사이인 5.0을 임계값으로 정했다.
   근거를 코드 주석으로 남겼다.

4. **매칭 근거 로깅** — 어떤 단어가 매칭돼서 어떤 사례와 연결됐는지 `log.info`로 남긴다.
   실제 로그 예시:
   ```
   INFO: [match_scam] case=C09 score=7.08 매칭단어=['계좌로', '계좌']
   INFO: [match_scam] case=C19 score=8.17 매칭단어=['주민센터', '하는']
   ```

## 1. 핵심 지표 Before(V2) / After(V3)

| 지표 | V2(오매칭 있음) | V3(불용어+가중치 적용) | 비고 |
|---|---|---|---|
| 실행 건수 | 30 | 30 | 실패 0건 |
| 근거 검색 성공률(references≥1) | 20/30 (67%) | **14/30 (47%)** | ↓ 오매칭이던 항목이 정직하게 "못 찾음"으로 바뀐 결과 |
| 기대판단 일치율 | 8/30 (27%) | **10/30 (33%)** | ↑ 개선 |
| verdict_hint 분포 | needs_check=0, partially_matched=20, no_source_found=10 | **needs_check=1**, partially_matched=13, no_source_found=16 | 확인됨이 처음으로 1건 나옴 |
| 재생성 발생 케이스 | 8/30 | 7/30 | 소폭 감소 |
| 재생성 발생율(시도 기준) | 15/45 (33%) | 14/44 (32%) | 거의 동일 |
| 폴백 | 3/30 | 3/30 | 동일 |

## 2. 유형별 상세 — 이번 요청이 명시한 3가지 확인

| 유형 | 근거 검색 성공률 (V2→V3) | verdict_hint 분포 (V3) | 기대판단 일치율 (V2→V3) |
|---|---|---|---|
| 정상 (기대: needs_check) | 4/10 → **1/10** | no_source_found=9, **needs_check=1** | 0/10 → **1/10** |
| 사칭 (기대: partially_matched) | 7/10 → **6/10** | partially_matched=6, no_source_found=4 | 7/10 → 6/10 |
| 경계 (기대: no_source_found) | 9/10 → **7/10** | partially_matched=7, **no_source_found=3** | 1/10 → **3/10** |

### ① 경계 10건이 '확인 불가'로 나오는가?

**여전히 대부분 아니다 — 3/10(B02, B04, B07)만 확인 불가다.** 개선(1/10→3/10)은 됐지만
기대(10/10)에는 한참 못 미친다. 나머지 7건(B01, B03, B05, B06, B08, B09, B10)은 여전히
`partially_matched`다 — 재라벨링표 30건과 진짜로(불용어 아닌 단어로, 임계값 이상) 겹치기
때문이다. 예: B10은 '정부24'·'화면' 두 단어가 겹쳐 8.17점으로 임계값을 넘는다. 이건
오매칭이 아니라 재라벨링표 코퍼스가 30건으로 작아서 "실재 제도명 + 미묘한 위험 단서"라는
경계 케이스의 뉘앙스까지 가려낼 만큼 촘촘하지 않다는 뜻이다 — 코퍼스 규모의 한계이지
이번에 고친 채점 로직의 결함이 아니다.

### ② 정상 10건이 '의심'으로 오판되지 않는가?

**확인됐다 — 0/10, 오판 없음.** V2에서는 정상 4건이 `partially_matched`(의심)로 잘못
나왔는데, V3에서는 정상 10건 전부 `partially_matched`가 아니다(no_source_found 9건 +
needs_check 1건). 이번 수정의 핵심 목표를 정확히 달성했다.

### ③ 정상 안내문 3개 직접 입력 — 눈으로 확인 (실제 API, mock 없음)

이 30건 평가세트와 무관하게 새로 작성한 문구 3개를 실제 API에 그대로 넣어 확인했다:

```
입력: "국민연금공단에서 발표한 2025년 기초연금 수급자 현황 자료에 따르면
       65세 이상 수급률이 늘었습니다."
→ verdict_hint: needs_check (확인됨)
→ signals: official_source_found(info) x2
→ references: "2025 고령자 통계", "2025 디지털정보격차 실태조사"

입력: "질병관리청 보도자료에 따르면 올해 독감 예방접종은 10월부터
       전국 보건소에서 무료로 진행됩니다."
→ verdict_hint: no_source_found (확인 불가)
→ signals: no_official_source(attention)
→ references: 없음

입력: "고용노동부는 이번 달부터 고용보험 실업급여 지급 기준 일부를
       조정한다고 밝혔습니다."
→ verdict_hint: no_source_found (확인 불가)
→ signals: no_official_source(attention)
→ references: 없음
```

**3건 모두 '의심'(partially_matched)으로 오판되지 않았다.** 1건은 실제 코퍼스와 매칭돼
확인됨, 2건은 코퍼스에 해당 제도가 없어 정직하게 확인 불가로 나왔다 — 곁눈의 원칙("애매하면
확인 불가로 유보한다")대로 동작한다.

## 3. 정직하게 보고해야 할 하락 — 사칭 케이스 1건(S08) 실측

사칭 케이스 중 S08("건강보험료 환급 신청 nhis-refund24.com")이 V2에서는 `partially_matched`
(정답)였는데 V3에서는 `no_source_found`로 바뀌었다 — **놓친 진짜 양성(false negative)이다.**
실측 원인:

```
S08 키워드(불용어 제외): ['nhis-refund24', '건강보험료', 'com', '환급']
매칭된 사기 사례: C06/C07 — 겹치는 단어는 '환급' 하나뿐, 점수 3.74 (임계값 5.0 미달)
```

'환급'이라는 단어 하나만으로는 임계값을 못 넘어 매칭에 실패했다. 이건 **의도된 트레이드오프다**
— 오매칭(정상 안내문을 사기로 오판)을 막으려고 기준을 높였더니, 약한 신호 하나짜리 진짜
사기 사례 일부도 함께 걸러진다. 정상 10건의 오판을 전부 없앤 대가로 사칭 검출 1건을
내줬다(7/10→6/10) — 수치가 나빠진 부분을 숨기지 않고 그대로 보고한다.

## 4. 재생성/폴백 — 거의 변화 없음

재생성 발생 케이스 8→7, 시도 기준 15/45(33%)→14/44(32%), 폴백 3→3(동일). 이번 수정은
근거 매칭 로직만 건드렸을 뿐 대화 생성(`prompt_chain.py`)은 그대로라 큰 변화가 없는 게
정상이다. `too_long` 근본 원인(2문장 제한, 프롬프트 길이 제약)은 이번에도 범위 밖이라
고치지 않았다.

## 5. 결론 요약

- **요청한 목표(정상 오판 제거)는 실측으로 달성을 확인했다** — 정상 10건 중 `partially_matched`
  (의심)는 0건이다(V2에서는 4건이었다).
- **확인됨(needs_check)이 이번에 처음으로 나왔다**(0/30→1/30, 실측 확인) — 세 가지 원인
  (데이터 누수, source_missing 좁은 키워드, match_scam_cases 오매칭)을 순서대로 다 고친
  뒤에야 도달했다.
- **경계 케이스의 '확인 불가' 재현율은 개선됐지만(1/10→3/10) 여전히 목표(10/10)에는 크게
  못 미친다** — 남은 원인은 오매칭이 아니라 재라벨링표 코퍼스 규모(30건)의 한계다.
- **대가도 있었다** — 사칭 검출 1건(S08)을 놓쳤고, 근거 검색 성공률 전반이
  67%→47%로 더 낮아졌다. 부풀려졌던 수치가 계속 진짜 수치로 수렴하는 과정이다.
- 남은 과제(이번 범위 밖, 고치지 않음): 경계 케이스 재현을 위한 코퍼스 확장,
  too_long 가드레일 재생성(프롬프트 길이 제약), 정상 케이스 근거매칭 70%(코퍼스 규모).

# 위험행동 신호 화면 전달 — 탐지기 수정 + 설계 두 안 측정 (2026-08-13)

**측정만 했다. `services/` 를 고치지 않았다. 채택은 사람이 정한다.**

측정: `api/experiments/exp_risk_action_fix.py` · `api/experiments/exp_risk_signal_designs.py`
발단: `docs/evaluation/본선과제_경고이유_화면표시.md` (R11 — 경고는 옳고 이유가 틀렸다)

---

## 0. 신호 키 — 확정됨

```json
{ "key": "risk_action_requested",
  "label": "앱을 설치하라는 내용이 있습니다.",
  "severity": "attention 또는 info",
  "detail": "앱설치" }            ← Signal 스키마에 Optional 필드 신설
```

키 4개가 아니라 **키 1개 + `detail`** 로 간다. `ATTENTION_KEYS` 허용목록이 1개만 늘어
8/12 에 배제→허용 방식으로 바꾼 취지가 살고, 유형이 늘어도(전화 회신 유도 등) 키가 안 는다.

## 1. 먼저 고친 것 — 탐지기 유형 정확도

### 왜 지금 고쳐야 했나

`detect_risk_action` 은 지금까지 `urgency_pressure` 강등 여부를 가르는 **이진 게이트**로만
쓰였다. 유형이 틀려도 무해했다. **화면이 유형을 말하는 순간 유형 오류는 곧 거짓말이 된다.**

| case | 원문 | 현재 검출 | 화면에 나갈 말 |
|---|---|---|---|
| **N17** (정상) | "응급안전안심 **장비를 설치**해 드리는 서비스" | 앱설치 | "앱을 설치하라는 문자예요" ← **거짓** |
| B25 / H40 | "**통장 사본**을 **보내 주**세요" | 계좌이체 | "돈을 보내라는 내용이 있어요" ← **거짓** |

### 수정 두 가지 — 둘 다 유형 정의에서 나온다

**(가) 최장 매칭 우선** — `dict` 순서 의존을 없앤다. 겹치면 더 구체적인(긴) 어휘가 이긴다.
`"통장 사본"`(5자) > `"보내 주"`(4자) → 개인정보요구.
*근거: 유형 정의상 '통장 사본을 보내라'는 개인정보 요구이지 자금 이체가 아니다.*

**(나) 문맥 조건**
- 계좌이체의 `"보내 주"`류 일반 동사 → **금전 문맥** 동반 필수
  (`"입금"·"송금"·"이체"` 처럼 자체가 금전 어휘인 것은 단독 인정)
- 앱설치의 `"설치하시"·"설치해"`류 → **소프트웨어 문맥** 동반 필수
  (`"앱 설치"·"다운로드"` 는 단독 인정)
*근거: 유형 이름이 '앱 설치'다. 장비 설치는 앱 설치가 아니다.*

> **(가)만으로는 N17 이 안 고쳐지고, (나)만으로는 순서 의존이 남는다. 둘 다 쓴다.**

### 결과 — 채택 기준 둘 다 충족

| | 검출(있다/없다) | **유형까지 일치** | 정상 과검출 |
|---|---|---|---|
| 현재 (확대112) | 37/39 (94.9%) | 36/39 (92.3%) | **1건** (N17) |
| **수정안** (확대112) | 37/39 (94.9%) | **37/39 (94.9%)** | **0건** |
| 현재 (홀드30) | 9/11 (81.8%) | 8/11 (72.7%) | 0건 |
| **수정안** (홀드30) | 9/11 (81.8%) | **9/11 (81.8%)** | 0건 |
| **합계 현재** | 46/50 (92.0%) | 44/50 (88.0%) | 1건 |
| **합계 수정안** | 46/50 (92.0%) | **46/50 (92.0%)** | **0건** |

| 채택 기준 | 결과 |
|---|---|
| 정상(라벨 '없음')에서 유형 오검출 **0** | **0건 ✅** |
| 검출률·유형일치율 격차가 **홀드아웃에서도** 해소 | 확대 0 · 홀드 **0 ✅** |

**바뀐 건은 정확히 3건이고 전부 옳은 방향이다. 나빠진 건 0건.**

```
B25  계좌이체 → 개인정보요구   근거구절 '통장 사본'
H40  계좌이체 → 개인정보요구   근거구절 '통장 사본'
N17  앱설치   → None          (정상 안내문의 '장비를 설치')
```

> **미검출 4건(B09·S24·H23·H24)은 그대로다.** 이 수정은 유형 정확도만 손댔고
> 재현율은 건드리지 않았다. 검출률 92.0% 는 변함없다.

### ★ 탐지기 수정만으로는 tier 가 하나도 안 바뀐다

`urgency_pressure` 강등 판단이 달라질 수 있어 따로 쟀다 — **tier 변경 0건.**
즉 이 수정은 **단독으로 안전하게 넣을 수 있다.**

## 2. 설계 두 안 — tier 를 올리는가, 이유만 바꾸는가

| | 안A — tier 올림 | 안B — 이유만 교체 |
|---|---|---|
| `severity` | `attention` | `info` |
| `ATTENTION_KEYS` | 추가 | 추가 안 함 |
| 화면 | hold 였던 글이 **warn 으로 올라간다** | tier 그대로, **'사실 한 줄'만 바뀐다** |
| 정상 오판 | 늘 수 있다 | **원리적으로 안 는다** |

### 네 지표 (화면 기준)

**확대 평가셋 112건**

| | 정상 오판 ↓ | 사칭 경고 ↑ | 축2 있음 ↑ | 축2 없음(헛경고) ↓ |
|---|---|---|---|---|
| 현재 | 1/37 | 18/37 | 19/39 | **2/70** |
| 탐지기 수정만 | 1/37 | 18/37 | 19/39 | 2/70 |
| **안A** | **2/37** | **28/37** | **38/39** | **2/70** |
| 안B | 1/37 | 18/37 | 19/39 | 2/70 |

**홀드아웃 30건**

| | 정상 오판 ↓ | 사칭 경고 ↑ | 축2 있음 ↑ | 축2 없음 ↓ |
|---|---|---|---|---|
| 현재 | 1/10 | 4/10 | 4/11 | **3/18** |
| **안A** | **1/10** | **9/10** | **11/11** | **3/18** |
| 안B | 1/10 | 4/10 | 4/11 | 3/18 |

**안A 가 바꾸는 것 (tier 변경 26건 전수는 스크립트 출력 참조)**

- 사칭 경고 **18→28** (확대) · **4→9** (홀드)
- 축2 안전 **19/39→38/39** (확대) · **4/11→11/11** (홀드) — 거의 전부 잡는다
- **★ 헛경고(축2 없음)는 확대 2/70 · 홀드 3/18 로 둘 다 불변.** 늘지 않는다
- 정상 오판은 확대에서만 **1→2** (R10 한 건). 홀드는 불변

## 3. ★ 정상인데 위험행동이 있는 2건 — 두 축이 정면으로 충돌한다

`min_score` 결정 때 R11 에서 본 것과 **같은 구조**다. 두 축을 합치지 않고 따로 적는다.

### R10 — 안A 에서만 문제가 된다

```
[Web발신](광고)[쿠팡CLS] 쿠하이어 오픈 기념 1만원 추가지급! …
30초 간편 본인인증으로 안전하고 빠르게 신청하세요.
```

| | |
|---|---|
| 라벨 | 정상 / 위험행동 **인증번호** (실사용 원문) |
| 검출 근거 구절 | `"30초 간편 본인인증으로 안전하고 빠르게 신청하세요."` |
| 현재 | `hold` |
| **안A** | **`warn`** — 축1(판정) **오판** / 축2(안전) **정답** |
| 안B | `hold` (변화 없음) |

### R11 — ★ **두 안 모두에서 고쳐진다**

```
[Web발신][KB국민카드, 당첨안내] … KB Pay 앱 설치 후 이용해주세요.
```

| | |
|---|---|
| 라벨 | 정상 / 위험행동 **앱설치** (실사용 원문) |
| 검출 근거 구절 | `"KB Pay 앱 설치 후 이용해주세요."` |
| 현재 | `warn` — 이유가 `similar_scam_case` → 화면엔 "이전에 확인된 사례와 비슷한 문장이 있어요" |
| **안A · 안B 모두** | `warn` — 이유가 **`위험행동:앱설치`** 로 바뀐다 |

> **★ 이 작업의 발단이 R11 이었다. 그런데 R11 은 tier 를 올리지 않는 안B 만으로도 고쳐진다.**
> R11 은 이미 `warn` 이었고 문제는 **이유**였기 때문이다.
> 즉 **"경고의 이유를 바로잡는다"는 원래 목적은 안B 로 충분히 달성된다.**
> 안A 는 그 위에 "더 많이 경고한다"를 얹는 별개의 결정이다.

| | 이유 교체 | warn·danger 전체 |
|---|---|---|
| 확대 112 | **20건** | 22건 |
| 홀드 30 | 2건 | 7건 |

```
S12·S16·S18·S22·S28  official_alert_matched → 위험행동:계좌이체/앱설치/개인정보요구
```

## 5. 인용 구절 — 안전 확인 완료

화면에 검출 근거가 된 **원문 구절을 그대로 인용**한다(프론트 개선요청서 원칙:
"받으신 주소를 그대로 보여주는 것이 중요합니다. 눈으로 비교할 수 있어야 합니다").
유형 라벨이 만에 하나 어긋나도 사용자는 실제 구절을 보므로 **거짓말이 구조적으로 어려워진다.**

| 확인 | 결과 |
|---|---|
| 인용은 **마스킹된 텍스트에서만** 뽑는가 | 그렇다 (`mask_text()` 결과에서만 추출) |
| 마스킹으로 구절이 사라지면 | **인용하지 않는다** (유형 문구만 나간다) |
| 전화번호·계좌·주민번호 패턴 잔존 | **48건 인용 중 0건** ✅ |
| 길이 | 60자 초과 시 말줄임 |

실제 생성 예:
```
[앱설치]       KB Pay 앱 설치 후 이용해주세요.
[인증번호]     30초 간편 본인인증으로 안전하고 빠르게 신청하세요.
[개인정보요구] 통장 사본과 신분증 사진을 문자로 보내 주세요.
```

## 6. 화면 문구 — 선택지 (★ 확정하지 않았다)

제약: '사기'·'가짜' 금지 / '찾았어요' 금지 / 검출하지 않은 것 적지 않기 / 두 문장 이내 / 쉬운 말

### 문구안 ㄱ — 사실 먼저

| 유형 | 사실 한 줄 |
|---|---|
| 앱설치 | **앱을 설치하라는 내용이 있어요.** 설치 전에 공식 앱스토어에서 직접 찾아보세요 |
| 계좌이체 | **돈을 보내라는 내용이 있어요.** 보내기 전에 기관 대표번호로 확인해 보세요 |
| 인증번호 | **본인인증을 하라는 내용이 있어요.** 문자 속 링크 말고 기관 앱에서 해 보세요 |
| 개인정보요구 | **개인정보를 보내라는 내용이 있어요.** 보내기 전에 기관 대표번호로 확인해 보세요 |

### 문구안 ㄴ — 행동 먼저 (지시하신 방향 예시에 가깝다)

| 유형 | 사실 한 줄 |
|---|---|
| 앱설치 | **앱을 설치하라는 문자예요.** 설치 전에 공식 앱스토어에서 직접 검색해 보세요 |
| 계좌이체 | **돈을 보내라는 문자예요.** 보내기 전에 기관 대표번호로 확인해 보세요 |
| 인증번호 | **본인인증을 요구하는 문자예요.** 기관 앱이나 누리집에서 직접 해 보세요 |
| 개인정보요구 | **개인정보를 요구하는 문자예요.** 보내기 전에 기관 대표번호로 확인해 보세요 |

> **ㄱ·ㄴ 차이**: ㄴ은 "…문자예요"로 글 전체를 규정한다. 광고 문자에 부수적으로
> 본인인증이 붙은 R10 같은 경우 **ㄴ이 더 세게 읽힌다.** ㄱ은 "내용이 있어요"라
> 부분을 가리킨다. **R10·R11 이 정상 문자임을 생각하면 ㄱ이 안전하다** — 다만
> 사칭 문자에는 ㄴ이 더 분명하다. 사람이 고를 일이다.

### 배치안

```
┌─────────────────────────────────┐
│  확인이 필요한 문자예요            │   ← 제목(기존 유지)
│                                 │
│  「 KB Pay 앱 설치 후 이용해주세요 」│   ← 인용 구절 (크게)
│                                 │
│  앱을 설치하라는 내용이 있어요.      │   ← 사실 한 줄
│  설치 전에 공식 앱스토어에서         │
│  직접 찾아보세요                   │   ← 다음 행동
└─────────────────────────────────┘
```

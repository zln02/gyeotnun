# 샘플 코퍼스 — 측정 후 기각 (2026-08-22)

**결정: 넣지 않는다. 결정자는 사람. 이 문서는 결정의 근거 기록이다.**

재현: `docker compose exec -T api python3 experiments/exp_sample_corpus.py`
(운영 인덱스·코퍼스·DB 무변경. 임시 색인은 `/tmp` 에 만들고 지운다.)

---

## 0. 무엇을 하려던 것인가

새로 클론한 환경에서는 코퍼스와 임베딩 색인이 없어 **근거 검색이 0건**이다.
화면에 오류가 뜨지 않고 근거만 비어서, 처음 보는 사람에게는 "검색이 안 되는
서비스"로 읽힌다. 그래서 **라이선스가 명확한 문서만으로 최소 코퍼스를 만들어
저장소에 넣을 수 있는가**를 쟀다.

★ 전제 조건 둘을 먼저 걸었다.
- "이용 조건 확인 필요"는 **한 건도 넣지 않는다.**
- 홀드아웃 30건의 정답 근거 원문은 **뺀다** — 넣으면 홀드아웃이 검색 코퍼스에
  들어간 것과 같아진다.

---

## 1. 후보 세트

| 단계 | 건수 |
|---|---:|
| `OFFICIAL_DOCS` 전체 | 1,059 |
| `license == "이용허락범위 제한 없음"` | **377** |
| 홀드아웃 정답 URL 과 겹쳐 제외 | −10 |
| **샘플 코퍼스** | **367** |

내역: 보건복지부·한국사회보장정보원 복지서비스정보 367건 + 경찰청 보이스피싱
현황 10건에서 홀드아웃 겹침 10건을 뺀 것.

> ★ 애초 후보였던 counterscam112 46건은 넣을 수 없다. `license` 필드가
> "공식 사이트 저작권정책 확인 필요"이고, 2026-08-13 조사도 **"보류 유지"**로
> 끝났다("kogl.or.kr 링크는 OPEN 정보공개 배너이고 공공누리 유형 표시가 아니다.
> 제1~4유형 어느 것도 명시돼 있지 않다"). 첫 전제에 걸린다.

## 2. 규모 — 저장소에 넣기에 부담 없다

| 항목 | 값 |
|---|---|
| 문서 / 청크 | 367건 / 371개 (전체는 1,059 / 2,036) |
| 원본 JSONL | 304 KB |
| 임베딩 색인 생성 | 39.7 ~ 46.0초 (3회 실행, 운영 컨테이너·CPU 공유) |
| 색인 파일 `.npz` | 528 KB |
| **저장소 추가량** | **약 832 KB** — LFS 불필요 |

## 3. ★★ 성능 — 근거는 남고 안전이 무너진다

| 지표 | 전체 코퍼스 (1,059건) | 샘플 코퍼스 (367건) |
|---|---|---|
| 근거를 붙인 건 (확대 112건) | 82/112 | **72/112** (88% 유지) |
| **확신 상태의 오답 근거** | **0건** | **★ 2건** |

문서를 **35%만 남겼는데 근거를 붙이는 능력은 88% 유지**된다. 복지서비스정보
367건이 정상·경계 케이스의 주 근거원이기 때문이다(확대셋에서 정답 URL 이 이
세트 안에 있는 케이스: 정상 18 + 경계 30 = 48건).

**그런데 확신 오답 근거가 0건 → 2건으로 늘어난다.**

```
N08 [정상] → '노인일자리 및 사회활동 지원사업' · '중앙노인돌봄지원기관 운영지원'
B16 [경계] → '암검진사업'
```

원인은 구조적이다. 정답 문서가 코퍼스에 없는 자리에서, **어중간하게 비슷한
문서가 top-1 으로 올라오고** 그게 확신 임계(`CONFIDENT_MATCH_THRESHOLD=0.6790`)를
넘는다. 코퍼스가 클 때는 더 가까운 문서에 밀려 올라오지 못하던 것들이다.

---

## 4. 그래서 기각했다

**확신 상태의 오답 근거 0건**은 이 서비스의 대표 수치이고, "절대 하면 안 되는
실패"로 정의한 항목이다. 샘플 코퍼스를 넣으면 **새로 클론한 사람의 환경에서
그 수치가 성립하지 않는다.** 저장소가 자기 대표 수치를 스스로 반증하는 상태가 된다.

### 함께 기각한 안 — "샘플 색인일 때 확신 판정을 끈다"

근거를 보여 주되 "확인됨"이라고 말하지 않으면 오답 근거는 0건이 된다.
**기각한다.** 실제 서비스와 다르게 도는 데모가 되기 때문이다. 데모에서 본
동작이 라이브에서 다르면, 그 데모는 저장소를 이해하는 데 도움이 되지 않는다.

### 실행 가능성은 다른 방법으로 답한다

`?mock=1` 로 전체 화면 흐름이 돈다. 고정 응답이지만 **실제 서비스가 하는 일과
같은 계약**이고, mock 질문도 `validate_question()` 을 통과한다. 근거 검색만
비어 있다는 사실을 README 가 그대로 말한다.

## 5. ★ 이 실험이 남긴 것 — 기각도 결과다

**코퍼스 커버리지는 성능이 아니라 안전에 직결된다.**

지금까지 "코퍼스를 늘리면 근거를 더 찾는다"는 방향으로만 생각했다. 이번 측정은
반대편을 보여 준다 — **코퍼스를 줄이면 근거를 덜 찾는 것이 아니라, 틀린 근거를
확신과 함께 내밀기 시작한다.**

```
문서 35%  →  근거 88% 유지  ·  확신 오답 0건 → 2건
```

근거 붙는 비율만 봤다면 "88%나 되는데 충분하다"고 결론냈을 것이다.
**안전 지표를 따로 세지 않았으면 못 봤다.**

이 성질은 반대 방향으로도 성립한다 — 코퍼스를 늘릴 때도 확신 오답을 같이 재야
한다. 늘리는 쪽은 안전할 것이라고 가정해 왔는데, 그 가정을 확인한 적이 없다.

> **규칙**: 코퍼스 규모를 바꾸는 변경은 "근거를 몇 건 찾는가"만으로 판단하지
> 않는다. **확신 오답 근거를 함께 세고, 0건이 아니면 채택하지 않는다.**
> (같은 성질의 다른 사례: `IDF척도이동_A안_2026-08-12.md` — 사례를 늘리면
> 하한선의 의미가 이동한다. 규모 변경은 늘 임계값을 흔든다.)

## 6. 측정 중 잡힌 것 — 가드가 내 실수를 막았다

첫 측정에서 임시 색인에 메타데이터(`provider`/`model`/`dimensions`)를 넣지 않았다.
`EmbeddingIndex` 의 3중 검증이 그 색인을 거부했고, 검색이 **BM25 로 조용히 폴백**해
28/112 라는 무의미한 값이 나왔다.

★ 폴백이 조용해서 숫자만 보면 알 수 없었다. 그래서 스크립트에 **폴백 감지**를
넣고 다시 쟀다(`EmbeddingUnavailableError` 를 세어 0건이 아니면 "측정 무효"로 표시).

이건 "모델명이 다른 인덱스가 섞이면 에러 없이 조용히 잘못된 결과가 나온다"는
이유로 만든 검증 장치가 **설계 의도대로 동작한 사례**다
(`local_embeddings_report.md` §1).

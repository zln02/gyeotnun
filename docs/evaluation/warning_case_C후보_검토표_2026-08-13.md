## 4. ★ 반영해도 지금 수치는 하나도 안 바뀐다 (실측)

메모리에서만 76건을 제외하고 확대 112 · 홀드 30 을 전수 재측정했다.

```
제외 대상 76건
tier 변경 0건 · 신호 변경 0건
확대112  정상오판 1/37→1/37 · 사칭경고 18/37→18/37 · 축2있음 19/39→19/39 · 축2없음 2/70→2/70
홀드30   정상오판 1/10→1/10 · 사칭경고  4/10→ 4/10 · 축2있음  4/11→ 4/11 · 축2없음 3/18→3/18
```

**이 76건은 지금 평가셋 어디에도 근거로 붙지 않는다.**
그래서 이 정리는 **눈에 보이는 오류를 고치는 일이 아니라, 앞으로 붙을 때를 막는 일**이다.

- 좋은 소식: **빼도 잃는 것이 0이다.** 되돌릴 위험이 낮다.
- 나쁜 소식: **효과도 지금은 0이다.** 급하지 않다.
- 정직하게: 코퍼스가 커지거나 질의가 달라지면 붙기 시작한다. `817039c0`("스미싱 피해,
  민간 기술과 함께 더 촘촘히 막는다")은 스미싱 문자를 받은 사용자 질의와
  임베딩 유사도가 높아질 소지가 크다.

## 5. 사람이 확정하면 — 반영 방식

1. CSV 의 `확정분류` 열을 채운다. **(2) 10건부터 보면 된다.**
2. 확정된 C 의 문서 id 를 `services/search.py` 에 **제외목록**으로 넣는다.

```python
# 예시 (아직 넣지 않았다)
ALERT_DOC_EXCLUDE_IDS = { …사람이 확정한 id… }

def _is_alert_doc(doc) -> bool:
    if doc.id in ALERT_DOC_EXCLUDE_IDS:
        return False
    return getattr(doc, "data_type", "") in ALERT_DOC_DATA_TYPES or doc.id in ALERT_DOC_IDS
```

3. `test_alert_allowlist_covers_only_reviewed_press_releases` 에 제외 검증을 더한다.

| 더할 단정 | 지키는 것 |
|---|---|
| 제외 id 가 전부 코퍼스에 있다 | 코퍼스가 바뀌면 재분류하라는 신호 |
| 제외 id 는 `_is_alert_doc` 이 **False** | 제외가 실제로 먹는다 |
| 제외 id 와 `ALERT_DOC_IDS` 가 겹치지 않는다 | 넣으면서 빼는 모순 방지 |
| `warning_case` 중 제외되지 않은 것이 남아 있다 | 통째로 꺼 버리는 실수 방지 |

**되돌리기**는 기존 스위치가 그대로 덮는다: `ALERT_DOC_AS_ATTENTION = False`.

## 6. 한 걸음 물러서서 — 이건 라벨 자체의 문제다

`warning_case` 155건 중 **78건(50%)** 이 사기 경보문이 아니다.
`press_release` 24건 중 **16건(67%)** 이 그랬다.

**원본 `data_type` 라벨을 신뢰한 것이 애초에 무리였다.** 이 라벨은 수집 출처(KISA 보도자료
게시판 / counterscam112 게시판)를 따라 붙은 것이지 문서의 성격을 읽고 붙인 것이 아니다.

지금 두 번 다 "사람이 읽고 id 목록으로 관리" 로 수습하고 있는데,
**코퍼스가 커지면 이 방식은 안 버틴다.** 본선 과제로 올릴 만하다 —
다만 오늘 결정할 일은 아니라 여기 적어만 둔다.

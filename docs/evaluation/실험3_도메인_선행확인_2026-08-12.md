# 실험 3 선행 확인 — 도메인과 위험 판단의 분리 (2026-08-12)

**결론: 진행하지 않고 멈췄다.** 지시하신 "도메인이 위험 판단 경로에 영향을 주는
지점이 있으면 목록으로 보고하고 멈춰라"에 해당하는 지점이 있고,
그보다 더 근본적인 사실이 나왔다 — **detected_domain 은 지금 검색 대상 코퍼스를
고르는 데 쓰이지 않는다.**

`services/` 무변경. (a)(b)(c) 어느 것도 적용하지 않았다.

---

## 1. domain 이 실제로 흐르는 경로 — 한 군데뿐이다

```
routers/checks.py:131   stored["domain"] = extracted.detected_domain
routers/checks.py:164   collect_evidence(masked_text, domain=stored["domain"])
services/search.py:367  legacy_refs = search_corpus(text, domain=domain)   ← 여기 하나
```

`collect_evidence()` 안에서 `domain` 을 쓰는 곳은 `search_corpus()` 호출 **한 줄뿐**이다.

**검색 함수 어느 것도 domain 을 받지 않는다.**

| 함수 | 시그니처 | domain |
|---|---|---|
| `match_official_docs_safe` | `(text, limit=2)` | ❌ |
| `match_embedding_docs` | `(text, limit=2, min_score=…)` | ❌ |
| `match_official_docs` | `(text, limit=2, min_score=…)` | ❌ |
| `match_scam_cases` | `(text, limit=2, min_score=5.0)` | ❌ |
| `match_evidence` | `(text, limit=2, min_score=1)` | ❌ |
| `search_corpus` | `(query, domain=None, limit=5)` | ✅ **유일** |

그리고 `search_corpus()` 가 보는 레거시 코퍼스는 **비어 있다.**

```
CORPUS_DIR 존재: True | *.json 파일 수: 0
search_corpus("기초연금 지원금") → 0건
```

**즉 detected_domain 은 현재 아무 일도 하지 않는다.** 임베딩 검색도, BM25 도,
사기사례 매칭도 전부 도메인과 무관하게 전체 코퍼스를 본다.

---

## 2. 그래도 위험 판단 경로에 닿는 지점이 있다 (멈춘 이유)

지시하신 목록이다. **오늘은 작동하지 않지만 구조적으로 연결돼 있다.**

| # | 경로 | 판정에 미치는 영향 |
|---|---|---|
| 1 | `domain` → `search_corpus()` → `legacy_refs` → `refs` | `refs` 가 비었는지가 판정을 가른다. 비면 `no_source_found` + **`no_official_source`(severity=attention)** 가 붙는다 |
| 2 | 같은 경로 → `refs` 비지 않음 → `risky` 분기 | `refs` 가 있으면 `partially_matched`/`needs_check` 로 갈 수 있다 |

`search_corpus()` 는 `domain` 이 일치하면 **점수에 +1** 을 준다(`search.py:169`).
지금은 코퍼스에 파일이 0개라 이 경로가 죽어 있지만, **레거시 코퍼스에 파일이
하나라도 들어오는 순간 도메인이 판정을 흔들기 시작한다.**

→ 지시하신 분리("도메인은 검색 대상을 고르는 데만, 위험 판단은 독립")는
**현재 코드에서 완전히 성립하지는 않는다.** 성립시키려면 `legacy_refs` 를
`refs` 에 합치기 전에 판정 입력에서 떼거나, `search_corpus` 의 domain 가산점을
없애는 선행 작업이 필요하다. 그건 이 실험의 범위 밖이라 손대지 않았다.

---

## 3. ★ 내 어제 제안이 틀렸다 — 정정

어제 실험 3(c)에서 이렇게 썼다.

> "바꾸면 검색 대상 코퍼스가 바뀌므로 네 지표를 다시 재야 채택 여부를 말할 수 있다."

**틀렸다.** `DOMAIN_PRIORITY` 를 바꿔도 **검색 대상 코퍼스는 바뀌지 않는다.**
도메인이 코퍼스 선택에 연결돼 있지 않기 때문이다. 지금 상태에서 (a) commercial 추가와
(b) 우선순위 재조정을 적용하면, 네 지표는 **한 자리도 움직이지 않는다.**
(레거시 코퍼스가 비어 있어 유일한 소비 지점이 무력하다.)

같은 이유로 어제 "finance 0/11 은 DOMAIN_PRIORITY 가 policy 를 우선하기 때문"이라고
쓴 것도 절반만 맞다. 분류가 틀리는 원인은 맞지만, **분류가 맞아도 검색 결과는
달라지지 않는다.** finance 로 제대로 분류돼도 갈 곳이 없다.

분류해도, 금감원·금융위 원문이 코퍼스에 없으면 결과는 같다.

## 5. 그래서 무엇을 해야 하는가 (제안만)

순서가 뒤바뀌어 있었다. 지금 상태에서 (a)(b)(c)를 적용하는 것은 **효과가 0인
변경을 프로덕션에 넣는 일**이다. 아래 순서를 제안한다.

| 순서 | 할 일 | 왜 먼저인가 |
|---|---|---|
| **1** | `legacy_refs` 를 판정 입력에서 분리 (또는 domain 가산점 제거) | 도메인/위험판단 분리를 코드로 성립시킨다. 이게 안 되면 뒤 단계가 판정을 오염시킨다 |
| **2** | 도메인을 실제 코퍼스 선택에 연결 (`match_*` 에 domain 전달) | 지금은 분류해도 쓰이지 않는다. 이게 없으면 (a)(b)가 무의미하다 |
| **3** | 금감원·금융위 공식 원문 수집 | finance 는 분류를 고쳐도 갈 곳이 없다 |
| **4** | (a) commercial 추가 · (b) 우선순위 재조정 | 1~3 이 된 뒤에야 네 지표가 움직인다 |
| **5** | (c) unknown 38건 어휘 보강 | N14 본인부담금 감경, N21 틀니·임플란트 같은 정상 제도 안내문부터 |

**1·2번은 판정 로직을 건드리는 변경**이라 실험 1·2보다 회귀 위험이 훨씬 크다.
평가셋·홀드아웃 양쪽 재측정이 반드시 따라야 한다.

## 6. commercial 화면 문구 — 결정하지 않았다

지시대로 선택지만 남긴다(어제 문서와 동일).

| 안 | 문구 | 위험 |
|---|---|---|
| A | "저희가 확인할 수 있는 대상이 아니에요" | 상업 거래를 가장한 사기(S18·S23·S26 등)에서 사용자를 방치한다 |
| B | 현행 "공식 자료를 못 찾았어요" 유지 | 찾을 수 없는 것을 못 찾은 것처럼 말한다 |
| C | 대상이 아님을 밝히되 확인 질문은 유지 | 문구가 길어져 시니어 UX 원칙과 부딪힌다 |

commercial 라벨 11건 중 **6건이 사칭**(S18·S21·S23·S26·S35·S40)이라는 점을
다시 강조해 둔다. 도메인으로 "확인 대상 아님"을 처리하면 이 6건이 그대로 빠져나간다.
도메인은 검색 대상만 가르고 위험 신호는 독립적으로 유지해야 한다는 지시가
바로 이 지점을 막는 것이고, §2 때문에 아직 그 분리가 보장되지 않는다.

# 곁눈(Gyeotnun) 공식 문서 검색 — 하이브리드(BM25+임베딩) 벤치마크

멘토 조언: "하이브리드를 기본으로 넣고 BM25 성능을 올리는 방법을 고민하라.
오픈소스 말고 유료 임베딩을 쓰는 게 낫다. 점수보다 순위로 표현하라."

이 문서는 그 조언에 따라 (1) BM25 토크나이저를 개선해 보고, (2) 유료 임베딩
(Upstage Solar Embedding)을 추가하고, (3) 점수가 아니라 순위(RRF)로 결합해서,
(4) 세 방식(BM25 단독/임베딩 단독/하이브리드)을 평가세트 30건으로 실측 비교한
결과다. **채택 여부는 사용자가 결정한다 - 이 문서는 판단 근거만 제공한다.**

---

## 0. 요약 (바쁘면 여기만)

| 방식 | Recall@3 | 정상 근거매칭 | 사칭 검출 | 경계 확인불가 | 정상 오판(절대조건) | 평균 응답시간 |
|---|---|---|---|---|---|---|
| BM25 단독 | 30% | 7/10 | 6/10 | 1/10 | **0/10 ✓** | 8.6ms |
| 임베딩 단독 | **65%** | **10/10** | 7/10 | 1/10 | **0/10 ✓** | 120.8ms |
| 하이브리드(RRF 1:1) | **65%** | **10/10** | 7/10 | **0/10 (↓악화)** | **0/10 ✓** | 124.7ms |

**임베딩이 BM25보다 뚜렷하게 낫다.** 정상 케이스 근거매칭이 7/10→10/10으로
완벽해졌고, Recall@3(정답이 상위 3위 안에 드는 비율)도 30%→65%로 두 배 이상
개선됐다. **다만 하이브리드가 임베딩 단독보다 나은 지점은 이번 30건에서 하나도
없었고, 경계(확인불가 기대) 케이스는 오히려 하이브리드가 가장 나빴다**(0/10 -
BM25·임베딩 단독은 1/10). 이유는 §5 참고. 정상 오판(최우선 절대조건)은 세 방식
모두 0건으로 안전했다.

## 1. Kiwi 형태소 분석기 비교 (BM25 개선 시도)

현재 BM25 토크나이저는 조사 제거 + 불용어 필터다. `kiwipiepy`(최신 한국어 형태소
분석기)로 명사/동사 어간만 뽑는 방식과 실측 비교했다.

**결과**: 부분적 개선. B04(경계 - "블로그에 2024년 기초연금... 공식 링크도
포함되어 있음")는 기존 방식에서 "포함되어"·"있음" 같은 동사 활용형이 우연히
무관한 문서와 겹쳐 오매칭됐는데, Kiwi 는 이런 활용형을 애초에 토큰으로 뽑지 않아
정답 문서("기초연금")가 정확히 1위로 올라왔다 - 구체적 개선.

하지만 전체 분리도(노이즈 최고점 대비 진짜 매칭 최저점의 비율)는 1.24배(기존)
→1.33배(Kiwi)로 소폭 개선에 그쳤고, B07 케이스는 오히려 악화됐다(무관한 문서
점수가 더 올라감 - "은행/직원/상담" 같은 진짜 명사가 다른 은행 사기 경보와도
합법적으로 겹치는 경우라 토크나이저로는 못 고치는 유형). 새 네이티브 의존성
(kiwipiepy, 약 90MB 모델 파일)과 임계값 재조정 비용까지 고려하면 **개선이
미미하다고 판단해 기존 토크나이저를 유지했다.**

원본 데이터: [`kiwi_vs_current_tokenizer.json`](kiwi_vs_current_tokenizer.json)

## 2. 임베딩 제공자 — Voyage → Upstage 전환

처음엔 Voyage AI(voyage-4-large)로 준비했으나(무료 티어 200M 토큰), 사용자가
"한국어 특화 + 국내 API가 데이터에 더 적합할 수 있다"는 판단으로 **Upstage Solar
Embedding 으로 전환**을 지시했다. 확인한 사양:

- 모델: **문서용/질의용이 분리돼 있다** - `solar-embedding-1-large-passage`(색인),
  `solar-embedding-1-large-query`(검색). 섞으면 검색 품질이 떨어진다는 공식
  경고가 있어, `embed_texts(input_type=...)` 가 자동으로 올바른 모델을 고르게
  구조를 짰다.
- 엔드포인트: `https://api.upstage.ai/v1/solar/embeddings` (Bearer 인증, 순수
  REST - 전용 SDK 없이 기존 `httpx` 의존성으로 직접 호출)
- 차원: 4096
- 가격: $0.10/1M 토큰 (**무료 티어 없음** - Voyage 와 다른 점)
- provider 전환 가능하게 구조화: `EMBEDDING_PROVIDER` 상수 + `_embed_<provider>()`
  함수 분리. 다른 제공자를 또 테스트하려면 이 함수만 추가하면 된다.

### 비용 실측 (지시대로 20건 소량 테스트 → 재추산 → 전체 실행)

| 단계 | 결과 |
|---|---|
| 사전 추정(글자 수 기반, 1.5~2.5토큰/자 가정) | 170만~280만 토큰, 약 $0.17~0.28 |
| 20건 소량 테스트 실측 | 8,153토큰/20청크 = 0.515토큰/자(추정보다 낮음) |
| 재추산(실측 비율 적용) | 약 58만 토큰, 약 $0.058 |
| **전체 1,882청크 실제 인덱싱** | **619,907토큰, 약 $0.062** (재추산과 거의 일치) |

인덱싱 중 429(레이트리밋)를 여러 번 만나 재시도/백오프(지수 백오프)와 배치 크기
조정(20→100청크/요청, 요청 "횟수" 자체가 레이트리밋 원인이었다)을 추가했다.
최종 소요 시간 63.9초.

### 인덱스 파일 메타데이터

`api/data/embeddings/embedding_index_upstage_solar_large.npz` 에 provider·모델명·
차원수를 함께 저장한다. 로드 시 지금 설정과 다르면(다른 모델/provider로 만든
인덱스) **조용히 무시하고 0건으로 동작한다** - 다른 임베딩 공간의 벡터가 섞여
검색이 소리 없이 망가지는 걸 막기 위한 방어 로직이다.

★ `corpus/` 는 컨테이너에 읽기 전용으로 마운트돼 있어(원본 보호 목적) 인덱스는
`corpus/` 바깥 `api/data/`(gitignore 처리)에 저장한다.

## 3. 임베딩 검색 임계값 실측

첫 벤치마크 실행에서 `min_score=0`(기본값)으로 뒀더니 **모든 질의가 항상 "가장
가까운" 문서를 반환**했다(잡음 문장 포함, refs_found_rate=100%) - BM25 를 처음
붙였을 때와 같은 문제(§docs/evaluation/eval_30_report.md 의 OFFICIAL_DOCS 임계값
근거)가 임베딩에도 그대로 있었다. 실측으로 다시 잡았다:

- 완전히 무관한 잡음 문장의 최고 유사도: 0.23~0.35
- 정상 10건(실제 대응 문서가 존재)의 최저 유사도: 0.5378
- 그 사이(0.35~0.5378)가 비어 있어 **0.45** 를 임계값으로 정했다.

적용 후 정상 오판(절대조건)은 여전히 0건이었고, refs_found_rate 는 100%→86.7%로
정직하게 낮아졌다(무관한 질의에 억지로 답을 만들지 않게 됐다는 뜻).

## 4. RRF 하이브리드 결합 + 가중치 튜닝

점수를 직접 더치지 않고 순위 기반(RRF, Cormack et al. 2009)으로 결합했다:

```
score(d) = Σ_r  weight_r / (k + rank_r(d))     k=60 (RRF 원 논문 기본값)
```

BM25 점수(0~30점대, 코퍼스 크기에 따라 변동)와 코사인 유사도(0~1 고정)는 척도가
달라서 그대로 더하면 BM25 가 지배해 버린다 - RRF 는 "몇 등인지"만 보므로 이 문제가
없다.

**가중치 튜닝**: BM25:임베딩 비율을 (2:1, 1.5:1, 1:1, 1:1.5, 1:2, 0.5:1, 1:0.5)로
바꿔 가며 실측했다. **결과: 테스트한 모든 비율에서 Recall@3·근거매칭·기대판단
일치율이 완전히 동일했다.** 임베딩 쪽 랭킹이 이미 강해서, BM25 가중치를 어떻게
조절해도 상위 3위 안의 결과가 바뀌지 않았다(RRF 는 순위만 보므로, 임베딩이 1~2위를
차지하면 BM25 가중치를 올려도 그 자리를 잘 못 뺏는다). 그래서 **표준값인 1:1을
그대로 채택했다** - 이 데이터 범위에서는 특별히 다른 값을 쓸 근거가 없었다.

## 6. 3방식 벤치마크 상세 (평가세트 30건, LLM 미사용 - 검색 계층만)

### 6-1. 지표 정의

- **Recall@3**: 평가세트의 정답 URL(`출처_URL` 컬럼)이 OFFICIAL_DOCS 에 실제로
  색인된 20/30건에 대해서만 계산했다(나머지 10건은 정답이 도메인 홈페이지
  수준이거나 SCAM_CASES 쪽에 있어 OFFICIAL_DOCS 검색 방식 비교에 안 맞는다 -
  §6-2 참고). 상위 3개 결과 안에 정답 문서가 있으면 성공.
- **근거 검색 성공률**: OFFICIAL_DOCS + EVIDENCE + SCAM_CASES 를 합쳐 뭐라도
  근거를 찾은 비율(30건 전체 기준). 세 방식 모두 EVIDENCE/SCAM_CASES 매칭
  로직은 동일하게 두고 OFFICIAL_DOCS 검색 방식만 바꿨다 - 변수를 하나로 좁히기
  위해서다.
- **기대판단 일치율**: 정상→needs_check, 사칭→partially_matched, 경계→
  no_source_found 매핑과 실제 verdict_hint 가 맞는 비율(30건 전체).
- **정상 오판**: 정상 10건 중 verdict_hint 가 partially_matched(의심)로 나온
  건수. **0건이 절대 조건.**

### 6-2. Recall@3 대상에서 제외한 10건

| case_id | 이유 |
|---|---|
| S01, S03 | 정답이 OFFICIAL_DOCS 가 아니라 SCAM_CASES 에 색인돼 있음(길이 필터 통과한 21건 중 하나) |
| B03,B04,B06,B08,B09,B10 | 정답이 특정 페이지가 아니라 도메인 홈페이지(bokjiro.go.kr, gov.kr 등) 수준이라 색인 단위와 안 맞음 |
| B05, B07 | 정답이 nhis.or.kr/fine.fss.or.kr 홈페이지 - 위와 같음 |

### 6-3. 유형별 상세

**정상 (기대: needs_check)**

| 방식 | 근거매칭 | 분포 | 일치율 |
|---|---|---|---|
| BM25 | 7/10 | needs_check=7, no_source_found=3 | 7/10 |
| 임베딩 | **10/10** | needs_check=10 | **10/10** |
| 하이브리드 | **10/10** | needs_check=10 | **10/10** |

**사칭 (기대: partially_matched)**

| 방식 | 근거매칭 | 분포 | 일치율 |
|---|---|---|---|
| BM25 | 6/10 | partially_matched=6, no_source_found=4 | 6/10 |
| 임베딩 | 7/10 | partially_matched=7, no_source_found=3 | 7/10 |
| 하이브리드 | 7/10 | partially_matched=7, no_source_found=3 | 7/10 |

**경계 (기대: no_source_found) — 하이브리드가 가장 나쁘다**

| 방식 | 근거매칭 | 분포 | 일치율 |
|---|---|---|---|
| BM25 | 9/10 | partially_matched=7, no_source_found=1, needs_check=2 | 1/10 |
| 임베딩 | 9/10 | partially_matched=7, no_source_found=1, needs_check=2 | 1/10 |
| 하이브리드 | **10/10** | partially_matched=7, needs_check=3, no_source_found=**0** | **0/10** |

**왜 하이브리드가 경계에서 더 나쁜가**: 하이브리드는 "BM25 가 찾거나 OR 임베딩이
찾으면" 근거가 잡히는 구조라, 두 방식을 합치면 커버리지(근거를 뭐라도 찾을 확률)
가 늘어난다. 경계 케이스는 설계상 "애매하면 확인불가로 유보"가 목표인데, 커버리지가
늘어날수록 오히려 확인불가에 도달하기 어려워진다 - **검색 성능이 좋아지는 방향과
"모르면 모른다고 말하기"가 반대로 작용하는 사례다.** 이번 30건에서는 정상 오판으로
이어지지는 않았지만(정상 10건은 여전히 0건 오판), 구조적으로 남는 리스크라 그대로
기록한다.

### 6-4. 응답 시간과 비용

| 방식 | 평균 응답시간(검색 계층만) | 비고 |
|---|---|---|
| BM25 | 8.6ms | 로컬 계산, API 호출 없음, 완전 무료 |
| 임베딩 | 120.8ms | 매 질의마다 Upstage API 실시간 호출 필요 |
| 하이브리드 | 124.7ms | BM25(로컬) + 임베딩(API) 둘 다 - 임베딩 쪽이 지배적 |

임베딩/하이브리드는 BM25보다 약 14배 느리다(그래도 100ms대라 절대적으로는 여전히
빠르다). 더 중요한 건 **매 사용자 요청마다 외부 API 호출이 추가된다는 것** - 이건
Upstage 가용성에 대한 의존성이 새로 생긴다는 뜻이다(BM25/현재 EVIDENCE/SCAM_CASES
매칭은 전부 로컬 연산이라 외부 서비스 장애와 무관했다). 비용은 질의 1건당 극히
작지만(질의 텍스트가 짧아 문서 인덱싱보다 훨씬 저렴), 0은 아니다.

## 7. 결론 및 채택 제안 (최종 결정은 사용자)

**데이터가 말하는 것**:
- 임베딩(Upstage)이 BM25보다 확실히 낫다 - 정상 케이스 근거매칭 100%(BM25 70%),
  Recall@3 65%(BM25 30%). 정상 오판(절대조건)도 0건으로 안전하다.
- 하이브리드는 이번 벤치마크에서 임베딩 단독을 능가한 지표가 하나도 없었고,
  경계 케이스에서는 오히려 더 나빴다(0/10 vs 1/10).
- 하이브리드/임베딩은 응답시간이 늘고(8.6ms→~120ms) 외부 API 의존성이 새로
  생긴다. BM25 는 이 부담이 없다.

**제 제안(참고용, 채택은 사용자 결정)**: 이번 30건 벤치마크만 보면 "임베딩 단독"이
가장 균형 잡힌 선택으로 보인다 - 하이브리드보다 구현이 단순하고, 경계 케이스에서

# 검색 폴백 관측 (2026-08-13)

**판정 로직 무변경. 임계값 무변경. 관측만 붙였다.**

---

## 1. 폴백 발동 시 기록이 남는가 — **남는다. 단, 개별 발생만.**

`services/search.py match_official_docs_safe()` 의 폴백 경로에서 두 곳에 남는다.

| 무엇 | 어디에 | 형식 |
|---|---|---|
| 애플리케이션 로그 | `gyeotnun.search` 로거 → 도커 로그 | `[official_search] 임베딩 검색 실패 - BM25 로 폴백: <사유>` (WARNING) |
| 장애 기록 | `gyeotnun.incidents` 로거 + **DB `error_logs` 테이블** | `log_incident("EX-003", detail=<사유 앞 120자>)` |

`error_logs` 는 `GET /errors/summary` 로 코드별 집계를 볼 수 있다.
실제로 누적돼 있다(2026-08-13 조회): **EX-003 117건**.

### 없던 것 — **비율**

EX-003 은 "이번 1건이 폴백이었다"만 말한다. **"계속 이러고 있다"를 말해 주는 것이
없었다.** 이건 질문 생성 쪽에서 이미 한 번 크게 데인 구조다.

> 8/9, 외부 LLM 크레딧이 바닥나 **8시간 동안 폴백률 100%** 였는데 아무도 몰랐다.
> 개별 실패(GN-001)는 그때도 138건이 꼬박꼬박 쌓이고 있었다. 쌓이기만 했다.
> 그래서 붙인 것이 GN-003(폴백률 50% 초과 경고)이다.

검색 쪽은 이보다 나쁠 수 있다.

- **폴백이 도는 상황은 이미 장애 상황이다.** 임베딩 인덱스가 없거나, 모델 로드가
  실패했거나, 질의 임베딩이 타임아웃 났을 때만 이 경로로 온다.
- **그런데 화면은 평소와 똑같다.** 사용자는 지금 임베딩이 아니라 BM25 로 근거가
  붙고 있다는 사실을 알 수 없다.
- **폴백 중에는 기준이 평소보다 무르다.** BM25 하한선 `_OFFICIAL_MIN_SCORE = 12.0` 은
  절대값인데 BM25 점수 척도는 코퍼스 크기를 탄다(청크 500→2,012 에서 상위점수
  7.94→10.70). 코퍼스가 커질수록 실질적으로 느슨해진다.
  → `docs/evaluation/본선과제_BM25폴백_척도이동.md`

즉 **장애 중에, 평소보다 무른 기준으로, 평소와 같은 화면으로 근거가 나간다.**

## 2. 붙인 것 — GN-003 과 같은 형식

같은 형식으로 맞출 수 있는지 확인했고, 맞출 수 있어서 그대로 맞췄다.

| | 질문 생성 (기존) | 검색 (신규) |
|---|---|---|
| 코드 | `GN-003` | **`EX-006`** |
| 위치 | `routers/dialogue.py` | `services/search.py` |
| 창 | 최근 20건 | 최근 20건 |
| 최소 표본 | 5건 | 5건 |
| 임계 | 50% 초과 | **50% 초과 (같은 값)** |
| 플래핑 방지 | 임계 초과 중 1회만 경고, 정상 복귀 시 재무장 | 동일 |
| 상태 저장 | 프로세스 메모리(deque), 워커 1개 전제 | 동일 |

```
[search_fallback_rate] 최근 20건 중 13건이 BM25 폴백 (65%) - 임베딩 인덱스·모델 상태를 점검할 것
[incident] code=EX-006 detail=최근 20건 중 BM25 폴백 13건 (65%)
```

**동작은 아무것도 바뀌지 않는다.** 폴백은 그대로 돌고, 사용자 화면도 그대로다.
`_OFFICIAL_MIN_SCORE`·`EMBEDDING_MIN_SCORE`·`CONFIDENT_MATCH_THRESHOLD` 전부 무변경.

### 되돌리기

`match_official_docs_safe()` 안의 `_observe_search_fallback(...)` 두 줄을 지우면
2026-08-13 이전 동작으로 즉시 복귀한다. 판정 경로에는 아무것도 걸려 있지 않다.

### 검증

`api/tests/test_search_fallback.py`
- `test_search_fallback_rate_warns_when_repeated` — 폴백 5건 연속 시 경고 1회 + EX-006 1회
  (플래핑 방지가 실제로 도는지까지 본다)
- `test_search_fallback_rate_is_silent_when_healthy` — 정상 20건에서는 아무 경고도 없다
  (관측이 소음이 되면 아무도 안 본다 — GN-003 을 붙일 때와 같은 이유)

전체 `pytest -q` **86 passed** (84 → 86).

## 3. 이 작업 중 확인한 것 하나 — 기록만 남긴다

**테스트를 돌리면 운영 DB `error_logs` 에 행이 들어간다.**
폴백을 모의하는 테스트가 `log_incident("EX-003")` 을 실제로 호출하기 때문이다
(2026-08-13 테스트 1회 실행 후 EX-003 3건 · GN-001 2건 유입 확인).
**이번에 생긴 문제가 아니라 원래 그랬다.** 고치지 않았다 — 고치려면 테스트에서
`log_incident` 를 전역으로 차단해야 하는데, 그건 "장애 기록이 실제로 남는가"를 보는
기존 테스트의 전제를 흔든다. 별도로 판단할 일이라 여기 적어만 둔다.

다만 **EX-006 이 테스트 때문에 들어가지는 않게** 막았다 — `api/tests/conftest.py` 에
매 테스트 앞뒤로 관측 상태를 비우는 픽스처를 뒀다. 없으면 폴백 모의 테스트가 남긴
기록이 다음 테스트까지 따라가 엉뚱한 곳에서 임계를 넘긴다(실행 순서에 따라 결과가
달라지는 불안정한 테스트가 된다). 실행 후 확인: **EX-006 유입 0건.**

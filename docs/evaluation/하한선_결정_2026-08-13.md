## 1. 근거

### (1) 깨끗한 하한선이 존재하지 않는다

정상과 사칭의 어휘점수 분포가 겹친다.

```
정상 최고  10.98 (H19)  ────┐
                            │  겹치는 구간 3.56 ~ 10.98
사칭 최저   3.56 (H26)  ────┘
```

어떤 값을 골라도 한쪽을 잃는다. "정상 오판만 지우는 값"은 없다.

### (2) 올리면 사칭 검출이 반토막 난다

| min_score | 정상 오판 (확대/홀드) | 사칭 경고 (확대/홀드) |
|---:|---|---|
| **5.0 (유지)** | 1/37 · 1/10 | **16/37 · 2/10** |
| 6.75 | 0/37 · **1/10** | 14/37 · 2/10 |
| 11.0 | 0/37 · 0/10 | **9/37 · 1/10** |

- 6.75 는 **확대셋에서만** 오판이 0 이 된다. 홀드아웃 1건은 그대로 남는다 —
  한쪽만 좋아지는 값은 채택하지 않는다는 기존 원칙에 걸린다.
- 양쪽 모두 0 을 만드는 11.0 은 사칭 검출을 **16→9 · 2→1** 로 떨어뜨린다.
  오판 2건을 지우려고 사칭 경고 8건을 끈다.

### (3) 남는 오판 1건(R11)은 축2 기준으로는 정답이다

R11 은 실사용 원문이다.

```
[Web발신][KB국민카드, 당첨안내] … 당첨 경품 메가커피 아메리카노 5잔.
쿠폰 확인하기 https://e.kbcard.com/coupon … KB Pay 앱 설치 후 이용해주세요.
```

| 축 | 라벨 | 현재 결과 | 평가 |
|---|---|---|---|
| 축1 판정 | 기대판단 **정상** | 경고(warn) | **오판** |
| 축2 안전 | 위험행동 **앱설치** | 경고(warn) | **정답** |

같은 한 건이 한쪽에서는 실패로, 다른 쪽에서는 성공으로 세어진다.
하한선을 6.75 로 올리면 축1 오판이 1→0 이 되는 동시에 축2 있음이 17→14 로
내려간다(R11 포함). **오판 1건을 지우는 것이 곧 주의 표시 1건을 끄는 것이다.**

앱 설치를 요구하는 문자에 주의를 붙이는 것 자체는 잘못이 아니다.
**잘못된 것은 그 이유를 화면이 말하지 않는다는 점이다** — §4 로 넘긴다.

### (4) 헛경고는 하한선으로 풀리지 않는다

축2 없음(헛경고)은 확대셋에서 13.0 까지 올려야 2→1 이다. 원인이 사기사례
매칭이 아니라는 뜻이다. 하한선을 올려도 이 지표는 거의 움직이지 않는다.

## 2. 이 결정이 서 있는 전제

~~**CI 회귀 테스트가 기준선을 지킨다**~~ → **자동 회귀 검사(서버 일일 실행)가 기준선을 지킨다**
— `api/tests/test_scam_threshold_regression.py`

```
BASELINE = {"확대 평가셋": 1, "홀드아웃": 1}
```

정상 케이스의 사기사례 매칭이 각 세트 1건을 넘으면 테스트가 실패한다.
5.0 유지는 "지금 1건뿐이니 감당할 수 있다"는 판단이므로, **1건이 늘어나는 순간
이 결정의 전제가 깨진다.** 그때 테스트가 빨간불로 알려 준다.

> **정정 (2026-08-15)**
> 작성 시점(8/13)에 **자동 실행이 실재하지 않았다.** 테스트 파일은 있었지만
> 그것을 자동으로 돌리는 것이 저장소 어디에도 없었다(2026-08-14 전체 감사에서 확인).
> 즉 이 결정은 **성립하지 않는 전제 위에 서 있었다.** 사람이 pytest 를 손으로
> 돌릴 때만 지켜지는 상태였고, 문서는 그것을 "CI 가 지킨다"고 적었다.
>
> 이는 우리 규칙 "측정하지 않은 것을 측정한 것처럼 쓰지 마라" 위반이다.
> 숨기지 않고 여기 남긴다.
>
> 2026-08-15 에 전제를 실제로 세웠다 — `api/tools/regression_check.py` 를
> 서버 cron 에 등록(매일 05:00, `deploy/regression.log`). GitHub Actions 가
> 아니라 서버 cron 인 이유와 확인 방법은 `deploy/README.md` §5 참고.
> 그 시점 실측: `SCAM_CASES=51건 / 확대평가셋 1/37 / 홀드아웃 1/10` — 위 표와 일치.

## 3. 재검토 조건 — `SCAM_CASES` 규모가 바뀔 때

`_keyword_weight = log((N_DOCS + 1) / (df + 1)) + 1.0` 이라 **N 이 늘면 모든 점수가
함께 올라간다.** `min_score=5.0` 은 절대값이라 따라가지 않는다.

실측(같은 문서 §(a)):

| | N=51 | N=185 |
|---|---:|---:|
| 확대 정상 최고 (R11) | 6.72 | **14.58** (+117%) |
| 홀드 정상 최고 (H19) | 10.98 | 13.48 (+23%) |

**사례를 늘린 것 말고 아무것도 바꾸지 않았는데** 정상 최고점이 두 배가 된다.
즉 **5.0 유지는 "N=51 에서의 5.0" 을 유지한다는 뜻이지, 영구 결정이 아니다.**

재검토 절차 (기존과 동일)
1. `test_scam_corpus_size_is_recorded` 가 `EXPECTED = 51` 불일치로 실패한다
2. `api/experiments/exp_scam_min_score_tradeoff.py` 로 분포·손익표를 다시 잰다
3. 결과를 `docs/evaluation/` 에 남긴 뒤 이 결정을 갱신한다
4. **숫자만 올리지 않는다** — 근거 없이 상수만 바꾸면 회귀 테스트가 무의미해진다

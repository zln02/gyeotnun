# 본선 과제 — 경고의 **이유**를 화면이 말하게 한다 (2026-08-13 기록)

**지금 고치지 않는다. 본선 과제로 기록만 한다.**
발단: `min_score` 5.0 유지 결정에서 남은 오판 1건(R11)
→ `docs/evaluation/하한선_결정_2026-08-13.md` §1-(3)

---

## 1. 무엇이 문제인가

### R11 (실사용 원문, 사용자가 실제로 받은 문자)

```
[Web발신][KB국민카드, 당첨안내] 고객님께서 참여해주신 이벤트에 당첨되셔서
진심으로 축하드립니다! 당첨 경품 메가커피 아메리카노 5잔.
쿠폰 확인하기 https://e.kbcard.com/coupon
본 쿠폰은 KB Pay 전용 쿠폰으로 KB Pay 쿠폰함에서 확인 가능합니다.
KB Pay 앱 설치 후 이용해주세요.
```

**지금 화면 (2026-08-13 실측)**

| | |
|---|---|
| tier | `warn` (주황 경고) |
| 제목 | **확인이 필요한 문자예요** |
| 사실 한 줄 | **이전에 확인된 사례와 비슷한 문장이 있어요** |
| 근거 신호 | `similar_scam_case` (attention) — 유일한 경고 신호다 |

**어긋나는 지점**

- 사용자가 읽는 뜻: *"이 문자는 사기와 비슷하다"*
- 시스템이 실제로 잡은 것: **"앱 설치를 요구한다"** (`위험행동 = 앱설치`,
  겹친 단어는 `[쿠폰, 설치]`)

경고 자체는 옳다 — 앱 설치를 요구하는 문자에 주의를 붙이는 것은 축2(안전) 기준으로
정답이다. **틀린 것은 이유다.** 화면이 실제 근거와 다른 이유를 말한다.

### 왜 이게 단순한 문구 문제가 아닌가

1. **정직성 원칙 위반이다.** `web/src/verdict.js` 머리말이 못 박아 둔 원칙이
   "'사실 한 줄'은 **실제로 검출한 것만** 적는다"인데, 지금 R11 은 검출하지 않은
   것(사기 수법 유사)을 적고 있다.
2. **행동으로 이어지지 않는다.** "비슷한 문장이 있어요"를 읽은 60대 사용자가
   다음에 무엇을 해야 하는지 알 수 없다. 반면 "설치 전에 공식 앱스토어에서
   직접 검색해 보세요"는 그 자리에서 실행 가능하다.
3. **경보 피로를 만든다.** 진짜 정상 문자에까지 "사기와 비슷" 이 붙으면 사용자는
   경고 자체를 무시하게 된다 — 그러면 진짜 위험한 문자의 경고도 같이 죽는다.

## 2. 지금 코드가 어떻게 돼 있는가 (사실 정리)

**위험행동은 이미 서버가 잡고 있다.** 2026-08-12 에 들어간 것이다.

```python
# api/services/search.py
RISK_ACTION_KEYWORDS = {"계좌이체": [...], "앱설치": [...], "인증번호": [...],
                        "개인정보요구": [...]}
def detect_risk_action(text: str) -> str | None: ...
```

그런데 **이 결과는 지금 `urgency_pressure` 의 severity 를 낮출지 결정하는 데에만
쓰인다.** 화면으로 내보내는 신호가 아니다. 즉 **필요한 정보는 이미 서버 안에 있는데
화면까지 오지 않는다** — 새 판정 로직이 필요한 과제가 아니라, 있는 것을 전달하는
과제다.

프런트 쪽:

```js
// web/src/verdict.js — ② attention 분기
const fact = attention.key === 'similar_scam_case'
  ? '이전에 확인된 사례와 비슷한 문장이 있어요'
  : firstSentence(attention.label)
```

`similar_scam_case` 하나에 **고정 문구**가 걸려 있다. 어떤 이유로 걸렸든 같은 문장이 나간다.

## 3. 본선에서 할 일

| 순서 | 할 일 |
|---|---|
| 1 | `detect_risk_action()` 결과를 화면까지 내려보낼지 결정한다 (신호로? 필드로?) |
| 2 | 위험행동 종류별 화면 문구·행동 안내를 정한다 — **문구는 사람이 정한다** |
| 3 | 경고 이유가 여러 개일 때 무엇을 먼저 보여줄지 정한다 (R11 은 앱설치 + 사기사례 매칭) |
| 4 | 평가셋·홀드아웃 양쪽에서 전후 대조 후 채택 여부를 사람이 결정한다 |

### 방향 예시 (★ 확정 문구가 아니다. 선택지다)

사용자가 제시한 형태:

> **앱을 설치하라는 문자예요**
> 설치 전에 공식 앱스토어에서 직접 검색해 보세요

**문구를 정할 때 반드시 지킬 제약** (기존 기준 그대로다)

- **'사기'·'가짜' 를 쓰지 않는다.** `validate_question` 금지어와 같은 기준이다.
  이 화면은 판정이 아니라 안내다.
- **'찾았어요' 를 쓰지 않는다.** 초록 tier 문구와 겹쳐 S22 에서 사용자를 오도한
  바로 그 표현이 된다.
- **검출하지 않은 것을 적지 않는다.** 앱 설치 요구를 잡았으면 앱 설치 요구만 적는다.

## 4. 지금 하지 않는 이유

1. **판정 로직 변경이다.** 신호를 새로 내보내면 tier 계산에 영향이 간다.
   8/8 사고가 정확히 이 경로였다.
2. **예선 제출 수치가 재측정 대상이 된다.** 축1·축2 양쪽이 모두 움직인다.
3. **문구는 사람이 정해야 한다.** 60대 대상 문구를 코드 쪽에서 임의로 확정하면
   안 된다는 기준이 이미 서 있다(A안 때와 같다).

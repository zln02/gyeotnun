## 1. 지연(버퍼링) 분석 — 병목은 알고리즘이 아니라 콜드스타트였다

개선 전 사용자 흐름 전 구간 실측(라이브 HTTPS):

| 구간 | 시간 | 정체 |
|---|---|---|
| POST /checks(텍스트) | 0.21초 | 정상 |
| GET /evidence | **5.9초** | ← 콜드스타트 |
| POST /dialogue | **8.5초** | ← LLM(Claude) 호출 |
| POST /verdict | 3.5초 | ← LLM 태깅 |
| **합계** | **18.1초** | |

서버 내부 프로파일로 원인을 갈랐다:
```
match_embedding_docs  10.179s  ← 첫 호출(모델 로드)
collect_evidence(전체)  0.162s  ← 웜
collect_evidence(2회차) 0.142s
detect_signals/match_evidence/match_scam  0.000~0.003s
```
**검색 로직은 0.14초로 이미 빠르다.** 5.9초는 게으른 모델 로드 탓이었고, 재시작 때마다
*첫 사용자 한 명만* 손해를 봤다 → 기동 시 백그라운드 프리워밍으로 제거(적용).

### 남은 지연: LLM 구간 (8.5초 + 3.5초)
이건 콜드스타트가 아니라 **외부 모델 호출 자체**다. 튜닝 여지(미적용, 제안):

| 방안 | 기대 | 위험 |
|---|---|---|
| dialogue **선요청**(사용자가 근거 화면 읽는 동안 미리 호출) | 체감 8.5초 → 거의 0 | 프론트 변경, 미사용 호출 비용 |
| **스트리밍** 출력 | 첫 글자까지 1~2초 | 가드레일이 전문(全文) 검증이라 구조 충돌 |
| verdict 태깅 **비동기화**(화면 먼저, 태깅 나중) | 3.5초 제거 | 훈련카드 연결 순서 변경 |
| effort/모델 하향 | 수초 | 질문 품질 저하 — **비권장**(서비스 핵심) |
| 가드레일 재시도 상한 조정 | 재시도 시 수초 | 원칙(2단 검증) 훼손 위험 |

> 권장 순서: **dialogue 선요청 > verdict 비동기 > 나머지 보류.** 앞의 둘은 품질을 안
> 건드리고 체감만 줄인다. 제출 후 프론트와 함께 작업할 것.

## 2. 시스템 안정화

### 고친 것
- **`restart: unless-stopped`** (api·db). 이전엔 `restart=no` 라 **호스트 재부팅 시 서비스가
  안 올라왔다** — 발표 당일 최대 위험이었다. nginx·certbot 과 정책을 통일했다.
- **프리워밍**(백그라운드 스레드) — startup 을 막지 않아 기동/헬스체크는 그대로.
  `PREWARM=0` 으로 끌 수 있다(메모리 빠듯한 환경 대비).

### 남은 위험 (미적용, 제안)
1. **`_MEMORY_STORE` 프로세스 메모리 의존** — 진행 중인 확인 건이 재시작 시 전부 사라지고,
   워커를 1개로 묶는 원인. DB/Redis 이관이 근본책(다중 워커·수평 확장의 전제).
2. **워커 1개** — 동시 5건은 실측 OK(직렬 처리)지만, LLM 8.5초짜리 요청이 겹치면 대기가
   쌓인다. 위 1번 해결 후 워커 2~4로 올리는 것이 정석.
3. **컨테이너 메모리 상한 없음**(`mem_limit=0`) — 로컬 모델 2종 상주(현재 api 626MB→
   프리워밍 후 증가)라 폭주 시 호스트 전체가 영향. 상한 설정 권장.
4. **스왑 1.9GB 사용 중** — 메모리 압박 이력. 위 3번과 함께 관측 필요.
5. **api 헬스체크 미정의**(compose) — 죽은 채 살아있는 상태를 감지 못한다.

## 3. 모델 안정화 (OCR·임베딩·LLM)

- **OCR**: 로컬(PaddleOCR) 채택 후 사칭 10/10·정상 오판 0 유지. `OCR_PROVIDER` 한 줄
  롤백(6초) 보존. 경계 공백 보정으로 S08 회복(별도 문서).
- **임베딩**: 인덱스 메타데이터 계약 일치(`e5-small-ko-v2`), 로드 로그로 확인 가능.
  BM25 폴백 경로도 살아 있다.
- **LLM**: `claude-sonnet-5` + 2단 가드레일 + 재시도. 실패해도 규칙 기반으로 내려앉는
  폴백이 있어 **가용성은 안정적**. 다만 재시도가 지연을 키운다(§1).
- 취약점: **일일 비용 상한이 없다**(nginx 레이트리밋은 IP 단위 방어일 뿐).
  device_id 단위 제한 + 총비용 상한은 아직 없음 — 보안 문서에도 기록된 미해결 항목.

## 4. UX 점검

### 좋은 것 (유지)
- 확인 중 화면의 **단계별 진행 표시**(STEPS) — 18초 대기를 견디게 해 준 핵심 장치.
- 4단계 판정(빨강/주황/초록) 분리, 표시 정직성 원칙(하지 않은 대조를 말하지 않음).
- a11y 선언 233곳, `aria-live/label` 21곳, PWA(manifest·sw.js), 이미지 업로드 전
  **클라이언트 리사이즈**(최대 1280px) — 업로드 지연을 미리 줄이고 있다.

### 부족한 것 (제안)
1. **클라이언트 타임아웃·재시도 없음** (`web/src/api.js` 에 `AbortController`·retry 부재).
   백엔드가 늦거나 끊기면 **어르신 화면이 무한 대기**한다. 20~30초 타임아웃 + "다시
   시도" 버튼이 필요하다. → **가장 시급한 UX 결함.**
2. 오류 복구 동선이 "처음으로 돌아가기" 위주 — 같은 자리에서 재시도가 낫다.
3. 프리워밍 전 첫 요청처럼 **드물게 긴 대기**가 나면 안내 문구가 없다(현재는 단계 표시만).
4. 훈련 카드 화면이 하드코딩 경로(`/training/today` 미연동) — 이전 문서에 기록된 미결.

# 로컬 임베딩 후보 실측 비교 (2026-08-03~04)

멘토 지적("이미지·텍스트를 외부로 보내는 것 자체가 문제")에 대응해, 상용
Upstage 를 대체할 수 있는 **로컬 임베딩** 후보를 실측했다. OCR 실험과 같은
방식으로 **기존 경로는 건드리지 않고 나란히 추가**했다.

**채택은 사용자가 결정한다. `services/embeddings.py`·`search.py` 의 기본 경로는
수정하지 않았다.**

---

## 1. 측정 조건

| 항목 | 내용 |
|---|---|
| 평가 데이터 | `corpus/곁눈_평가세트_30건.csv` 의 `평가용_제시문구` 30건 (정상10/사칭10/경계10) |
| 코퍼스 | `OFFICIAL_DOCS` 996건 → 재청킹 1,882 청크 (기존과 동일) |
| 판정 로직 | 프로덕션 `collect_evidence()` 와 **동일하게 재현** — 공식문서 검색만 후보 모델로 교체 |
| 환경 | 격리 도커(`--memory=10g --cpus=3.5`, torch 3스레드). 운영 스택과 분리 |
| Recall@3 분모 | 정답 URL 이 `OFFICIAL_DOCS` 에 실제 색인된 20건만 |

**★ dense 임베딩만 사용했다.** sparse·colbert 는 쓰지 않았다(하이브리드는 이미
실측으로 기각 — `hybrid_search_report.md`). sentence-transformers 로 로드하면
dense 표현만 나오므로 이 조건이 구조적으로 지켜진다.

**★ e5 계열 접두어**: `_NEEDS_E5_PREFIX` 집합으로 분리해 `query:`/`passage:` 를
자동 부착하게 했다. bge-m3 계열은 접두어 규약이 없어 원문 그대로 넣는다.
(이번 측정 대상은 bge-m3 계열 2종이라 접두어는 적용되지 않았다.)

**★ 후보마다 인덱스를 새로 만들었다.** `local_index_{provider}.npz` 로 분리하고,
파일 메타데이터에 provider·모델명·차원수를 기록한 뒤 로드 시 3중 검증한다
(모델명이 다르면 인덱스를 거부한다 — 벡터 공간이 다른 인덱스가 섞이면 에러 없이
조용히 잘못된 결과가 나오기 때문).

**★ 임계값은 후보마다 재보정했다.** 모델별로 유사도 분포가 달라서 고정 임계값을
쓰면 비교가 불공정해진다. 잡음 문장 5개 / 정상 10건 / 경계 10건의 실측 분포에서
`min_score`(근거로 보여줄 최저선)와 `confident`(확인됨으로 볼 최저선)를 각각 뽑았다.

## 2. 결과 — 상용 Upstage 와 나란히

| 후보 | Recall@3 | 근거검색 성공률 | 기대판단 일치율 | **정상10건 오판** | 질의 응답시간 | 인덱싱 | 상주 메모리 | 인덱스 파일 |
|---|---|---|---|---|---|---|---|---|
| **Upstage (상용, 현재)** | **0.65** (13/20) | **0.867** | **0.667** | **0/10 ✓** | **112ms** | — (API) | — | 23.5MB |
| **bge-m3** (BAAI, MIT) | **0.65** (13/20) | **0.867** | 0.633 | **0/10 ✓** | 558ms | 52분 | 1,098MB | 6.9MB |
| **bge-m3-ko** (dragonkue) | 0.60 | 0.800 | 0.600 | **0/10 ✓** | 572ms | 52분 | 2,191MB | 6.9MB |

응답시간은 중앙값 기준 Upstage 102ms / bge-m3 558ms. 인덱싱은 1회성이며
CPU 3스레드 기준이다(GPU 없음).

### 2-1. 유형별 판정 분포

| 후보 | 정상(기대 needs_check) | 사칭(기대 partially_matched) | 경계(기대 no_source_found) |
|---|---|---|---|
| Upstage | needs_check **10** | partially 7 / no_source 3 | partially 7 / **no_source 3** |
| bge-m3 | needs_check 9 / **no_source 1** | partially 7 / no_source 3 | partially 7 / **no_source 3** |
| bge-m3-ko | needs_check 9 / no_source 1 | partially **6** / no_source 4 | partially 7 / **no_source 3** |

**일치율 차이(0.667 vs 0.633)의 정체는 정확히 이 정상 1건이다.** bge-m3 가 정상
안내문 1건에서 근거를 충분히 찾지 못해 "확인 불가"로 유보했다.

★ 중요: 이 1건은 **오판(의심)이 아니라 보수적 유보**다. 절대조건인 "정상을
의심으로 판정하지 않는다"는 세 방식 모두 **0건으로 지켰다**. 곁눈의 설계 원칙상
'확인 불가'는 안전한 실패 방향이다(애매하면 단정하지 않는다).

## 3. ★ 주목할 차이 — 유사도만으로 정상/경계를 못 가른다

임계값 보정 과정에서 드러난 구조적 차이다.

| 후보 | 잡음 최대 | 정상 최소 | 경계 최대 | 잡음/정상 분리 | **경계/정상 분리** |
|---|---|---|---|---|---|
| Upstage | 0.35 내외 | 0.5378 | 0.5058 | 가능 | **가능** (0.5058 < 0.5378) |
| bge-m3 | 0.5447 | 0.6677 | **0.7225** | 가능 | **불가** (경계가 정상보다 높음) |
| bge-m3-ko | 0.4288 | 0.5611 | **0.5865** | 가능 | **불가** |

두 로컬 모델 모두 **경계 케이스의 유사도가 정상 케이스보다 높게** 나온다. 즉
"유사도가 높으면 확인됨"이라는 규칙을 세울 수 없다. 현재 프로덕션이 쓰는
`CONFIDENT_MATCH_THRESHOLD`(0.52) 같은 장치를 로컬 모델에는 그대로 이식할 수 없다는
뜻이다.

결과적으로 경계 확인불가는 세 방식 모두 3/10 으로 같게 나왔지만, 그건 유사도가 아니라
**다른 신호(위험 신호·사기사례 매칭)가 판정을 주도했기 때문**이다. 유사도 기반
확신 판정은 로컬 모델에서 사실상 작동하지 않는다.

잡음 분리는 두 모델 모두 가능하다 — 무관한 문장(김치찌개·고양이 등)은 확실히
낮게 나온다. 따라서 `min_score`(근거로 보여줄 최저선)는 문제없이 설정된다.

## 4. 후보별 판정

**bge-m3 (BAAI/bge-m3, MIT)** — 유일하게 상용에 근접
Recall@3 와 근거검색 성공률이 상용 Upstage 와 **완전히 동일**(0.65 / 0.867)하다.
일치율만 정상 1건 차이로 낮다. 정상 오판 0건. MIT 라이선스라 B2G 도입에 제약이
없다. 다만 질의 응답이 **5배 느리고**(112ms → 558ms), 유사도로 경계/정상을 못 가른다.

**bge-m3-ko (dragonkue/BGE-m3-ko)** — 원본보다 나빴다
"한국어 파인튜닝"이라는 기대와 달리 **모든 지표에서 원본 bge-m3 보다 낮다**
(Recall@3 0.60, 근거검색 0.800, 일치율 0.600). 사칭 검출도 1건 더 놓쳤다.
메모리도 2배(2,191MB). 이 과제(공공 복지문서 검색)에서는 파인튜닝이 역효과였다.

**e5-large / KoE5** — 미측정
bge-m3 계열 2종만으로 인덱싱에 104분이 걸려, 지시서상 3순위("여유 있으면")인
두 후보는 돌리지 않았다. 접두어 처리는 코드에 이미 반영해 뒀으므로
`python3 tools/bench_local_embeddings.py e5-large koe5` 로 바로 측정 가능하다.

## 5. 판단 (결정은 사용자)

**bge-m3 는 정확도 면에서 상용을 대체할 수 있다.** 핵심 지표인 Recall@3(0.65)와
근거검색 성공률(0.867)이 Upstage 와 소수점까지 같고, 절대조건인 정상 10건 오판도
0건을 지켰다. 일치율 차이는 30건 중 1건(정상 안내문을 '확인 불가'로 유보)이고,
그마저 오판이 아니라 안전한 방향의 보수적 판단이다. 인덱스 파일도 6.9MB 로 상용
(23.5MB)보다 작다(1024차원 vs 4096차원). MIT 라이선스라 기획서의 B2G 도입 계획과도
충돌하지 않는다.

**막는 요인은 정확도가 아니라 속도다.** 질의 1건당 558ms 로 상용(112ms)의 5배다.
여기에 Claude 질문 생성(초 단위)이 더해지므로 전체 체감에서 차지하는 비중은 크지
않지만, 시니어 대상 서비스에서 0.5초는 무시할 값도 아니다. 게다가 이 수치는
GPU 없이 CPU 3스레드로 잰 것이라, 동시 사용자가 늘면 더 나빠진다.

**따라서 선택지는 이렇게 갈린다.** 개인정보(외부 전송 없음)를 최우선하면 bge-m3 로
전환할 근거가 충분하다 — 정확도 손실이 사실상 없다. 반대로 응답 속도와 운영
단순함을 우선하면 현재 Upstage 유지가 맞다. **양자택일이 아니라, 텍스트는 로컬
임베딩으로 돌리고(외부 전송 제거) 이미지 OCR 만 상용을 쓰는 조합도 가능하다** —
로컬 임베딩은 OCR 과 달리 정확도 손실이 거의 없기 때문에, OCR 보다 전환 근거가 더
강하다.

### 남은 확인 사항
- e5-large·KoE5 미측정(접두어 처리는 준비됨)
- 응답시간은 CPU 3스레드 단일 요청 기준 — 동시 요청 시 성능은 미측정
- bge-m3 에는 `CONFIDENT_MATCH_THRESHOLD` 방식을 그대로 못 쓴다(§3). 전환한다면
  확신 판정을 유사도가 아닌 다른 신호로 다시 설계해야 한다

## 부록: 재현

```bash
docker build -f api/Dockerfile.local-experiment -t gyeotnun-local-experiment api/

docker run --rm --memory=10g --cpus=3.5 \
  -v "$PWD/api:/app" -v "$PWD/corpus:/corpus:ro" \
  -e HF_HOME=/app/data/hf_cache -e EMBED_THREADS=3 --env-file .env \
  -w /app gyeotnun-local-experiment \
  python3 -u tools/bench_local_embeddings.py bge-m3 bge-m3-ko
```

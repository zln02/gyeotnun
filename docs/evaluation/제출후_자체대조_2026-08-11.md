# 제출 기획서 ↔ 저장소 자체 대조 (2026-08-11)

예선 기획서를 제출한 뒤, 문서가 말하는 것과 저장소가 실제로 하는 것을 다시 대조했다.
어긋난 지점 3건을 찾았고 아래에 남긴다.

**방향을 분명히 해 둔다.** 저장소 서술을 기획서에 맞추지 않았다. 기획서는 이미
제출돼 고칠 수 없고, 저장소를 거기 맞추면 저장소가 실제보다 좋게 말하게 된다.
그래서 반대로 했다 — 저장소는 실측 그대로 두고, 차이를 이 문서에 기록한다.

대조 대상
- 기획서: `docs/[2026년 제8회 K-디지털 트레이닝 해커톤] 예선심사과제_Second Look.pdf`
- 저장소: `README.md`, `tests/eval/masking_report.md`, `api/tools/purge_old_records.py`,
  `docs/CONTRIBUTING.md`, `api/services/masking.py`

> 세 건 모두 **측정값 자체는 조작되지 않았다.** 어긋난 것은 분모의 범위(①),
> 서술이 가리키는 데이터의 종류(②), 표기(③)다. 성능을 부풀린 항목은 없다.

## ① 마스킹 재현율의 분모 범위

**기획서 서술 (3.4)**
> "주민등록번호·카드번호·전화번호·계좌번호 4종을 정규식으로 마스킹한다.
> 합성 PII 156개 필드에서 재현율 97.8%였고, 누락 10건은 패턴 보강 후 회복했다."

**실제** (`tests/eval/masking_report.md` §1)
97.8% 의 분모는 156이 아니라 **90**이다. 평가셋에 실제로 구현된 유형만 세면
전화 39 + 주민 22 + 계좌 29 = 90필드이고, 여기서 88건을 잡아 **88/90 = 97.8%** 다.
156필드 전체 기준으로는 **88/156 = 56.4%** 다. 차이는 이름 38 + 주소 28 = 66필드로,
이 둘은 `masking.py` 에 정규식도 사전도 호출부도 없다. 즉 0% 는 "패턴이 약해서"가
아니라 **기능이 없어서**다.

| 유형 | 필드 | 재현율(보강 전 → 후) |
|---|---:|---|
| phone | 39 | 79.5% → **100.0%** |
| rrn | 22 | 90.9% → **100.0%** |
| account | 29 | 93.1% → 93.1% |
| name | 38 | 0.0% → 0.0% (미구현) |
| address | 28 | 0.0% → 0.0% (미구현) |
| **전체** | **156** | 50.0% → **56.4%** |
| **구현된 3종** | **90** | 86.7% → **97.8%** |

**차이의 성격**
비율(97.8%)은 정확하고 **분모의 범위가 어긋났다.** 성능 과장은 아니다 —
오히려 156을 분모로 쓰면 실제(56.4%)보다 좋게 보이는 방향이라, 기획서 문장은
"97.8%" 라는 맞는 숫자에 "156개 필드" 라는 넓은 모수를 붙인 형태다.
"누락 10건" 은 78→88 로 회복된 10건을 가리키며 이 값은 정확하다.

**본선 처리 방안**
발표에서 먼저 밝힌다. 이름·주소는 정규식으로는 오탐이 커서 NER 도입 후 재측정하고,
그때 156필드 전체를 하나의 분모로 다시 보고한다.

### 덧붙임 — 카드번호는 어디 갔나 (확인 요청 항목)

기획서는 **4종**(주민·카드·전화·계좌)이라 했는데 실측 90필드는 **3종**(전화·주민·계좌)이다.
확인한 결과는 이렇다.

- **구현은 되어 있다.** `api/services/masking.py:117` 에 `CARD_RE` 가 있고,
  오탐을 줄이려고 `CARD_POSITIVE_CONTEXT_RE`(:125) / `CARD_NEGATIVE_CONTEXT_RE`(:129) /
  `CARD_CONTEXT_WINDOW=24`(:134) 문맥 판정까지 붙어 있다.
- **평가셋에 없다.** `tests/eval/masking_cases.json` 의 156필드를 유형별로 세면
  phone 39 / name 38 / account 29 / address 28 / rrn 22 이고 **card 는 0건**이다.
  평가셋 생성 지시서의 5개 유형(전화·주민·계좌·이름·주소)에 카드가 빠져 있었기 때문이다
  (`masking_report.md` §1 각주에 같은 취지가 적혀 있다).

즉 **카드번호는 90 안에 포함돼 있지 않고, 검증에서 빠졌다.**
"4종을 마스킹한다" 는 코드 기준으로 참이지만, "4종을 156필드에서 측정했다" 는 성립하지 않는다.
**카드번호는 구현됐으나 미검증 상태**로 보는 것이 정확하다.

→ 본선: 카드번호 합성 케이스를 평가셋에 추가해 4종 전부를 같은 분모로 재측정한다.

## ② 90일 자동 삭제의 대상

**기획서 서술 (2.5 / 3.4)**
> "판정 문장은 남기지 않으며, 마스킹 텍스트·놓친 질문·최종 선택만 90일 보관 후 자동 삭제한다."
> "마스킹된 이용·훈련 기록은 90일이 지나면 자동 삭제하고, 삭제 작업과 건수는 매일 기록한다."

**실제** (`api/tools/purge_old_records.py:38`)
삭제 잡이 도는 테이블은 **`events` 와 `error_logs` 2종뿐**이다.
마스킹 텍스트(`checks`)·놓친 질문·최종 선택(`taggings`)은 이 잡이 건드리지 않는다.
스크립트 독스트링이 이유를 밝히고 있다 — *"checks/taggings 등 서비스 데이터는 현재
DB 에 쓰이지 않으므로(인메모리) 대상이 아니다."* README "알려진 한계" 의
"확인 기록을 프로세스 메모리에 보관한다" 와 같은 사실이다.

삭제 잡 자체는 정상 동작한다. 검증 결과는 아래와 같다
(`docs/reports/2026-08-11_보관기간_자동삭제_동작확인.txt` §4-1).

| 항목 | 결과 |
|---|---|
| cron 등록 | `0 4 * * *`, `python -m tools.purge_old_records` |
| 최근 실행 | 2026-08-11 04:00:03 UTC 성공 (8/8~8/11 4일 연속 발화 확인) |
| 삭제 건수 기록 | 실행 1회당 2줄(cutoff + 완료), 매일 남음 — 기획서 3.4 서술과 일치 |
| 실삭제 검증 | 임시 DB에 오래된 행 투입 → events 7/7, error_logs 4/4 삭제, 최근 행은 보존 |

**차이의 성격**
"삭제 작업과 건수를 매일 기록한다" 는 부분은 **참이다.** 어긋난 것은 삭제 **대상**이다.
해당 데이터(checks/taggings)는 인메모리라 프로세스 재시작 시 소멸하므로
90일 축적 위험 자체는 없다. 다만 **"90일 보관 후 삭제" 라는 서술은 그 데이터에
성립하지 않는다** — 보관 기간이 90일이 아니라 프로세스 수명이기 때문이다.
개인정보가 더 오래 남는 방향의 문제는 아니다.

**본선 처리 방안**
저장소 외부화(인메모리 → DB 세션) 시 `checks`/`taggings` 를 DB 로 옮기고
`purge_old_records.py` 의 삭제 대상에 추가하면 기획서 서술이 그대로 참이 된다.
`purge_old_records.py` 독스트링에 이미 *"이후 DB 로 옮기면 여기 추가할 것"* 이라고
적혀 있다. README "알려진 한계" 와 "남은 과제(박진영: 메모리 저장소 → DB 세션 교체)" 가
같은 항목을 가리킨다.

## ③ 팀원 역할 표기

**기획서 서술 (10p 팀원 역할)**

| 팀원 | 기획서 |
|---|---|
| 박진 | PM · 데이터 통합 (통합 근거표 · 문제 정의, 최종 기획서) |
| 김태희 | 공식 근거 검증 (기관·연도·페이지·URL 근거표) |
| 장지석 | 사례 분석 (중복 제거 사례화, 대표 질문) |
| 박진영 | 백엔드 · 배포 (공식 검색과 질문 생성 API, 배포 완성) |
| 김유리 | 프론트 · 시니어 UX (공유→질문→판단→복습, 화면) |
| 조희진 | UX 리서치 · 시니어 시나리오 (실제 사용자 접점, 심사자료 시각화) |

**실제** (`docs/CONTRIBUTING.md:7-12`)

| 팀원 | CONTRIBUTING.md | 기획서와 |
|---|---|---|
| 박진 | 인식 · 마스킹 (`ocr.py`, `masking.py`) | 다름 |
| 김유리 | 검색 · 공공데이터 대조 (`search.py`) | **다름 (조희진과 뒤바뀜)** |
| 김태희 | 프롬프트 (판정 억제) (`prompt_chain.py`) | 다름 |
| 장지석 | 태깅 · RAG · 코퍼스 (`tagger.py`, `rag.py`, `corpus/`) | 대체로 일치 |
| 조희진 | 프론트 (`web/` 전체) | **다름 (김유리와 뒤바뀜)** |
| 박진영 | API · DB · 배포 | 일치 |

가장 눈에 띄는 것은 **김유리 ↔ 조희진** 이다. 기획서는 김유리=프론트/조희진=UX리서치,
저장소는 김유리=검색/조희진=프론트로 서로 반대다.

**차이의 성격**
**표기 불일치이며, 어느 쪽이 실제인지 미확정이다.** 기획서는 기여 영역을 넓게
적었고 `CONTRIBUTING.md` 는 폴더 소유권을 적은 것이라, 둘이 같은 축을 재고 있지
않을 가능성도 있다. 확인 전에 한쪽을 고치면 없는 사실을 만드는 셈이라
**양쪽 다 그대로 두었다.**

**본선 처리 방안**
팀 확인 후 통일한다. 현재 **지시 대기 중**이며, 확인될 때까지 어느 쪽도 수정하지 않는다.

## 이 문서를 만든 이유

심사위원이 먼저 찾아내면 감점이지만, 우리가 먼저 말하면 점검 능력의 증거가 된다.
세 건 모두 실측을 다시 해서 확인한 것이고, 저장소의 수치를 기획서에 맞춰
바꾸지 않았다.

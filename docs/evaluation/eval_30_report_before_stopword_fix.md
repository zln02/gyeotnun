# 곁눈(Gyeotnun) 평가세트 30건 재측정 — Before/After (데이터 누수 제거 + 확인불가 판정 개선)

이전 측정([`eval_30_report_before.md`](eval_30_report_before.md))에서 두 가지 문제를 발견했다.
이 문서는 그 두 문제를 고친 뒤 같은 30건을 다시 돌려 before/after로 비교한 결과다.
**수치가 대부분 낮아졌다 — 그대로 보고한다.** 낮아진 것은 대부분 예상되고 바람직한 교정이다.

## 0. 무엇을 고쳤는가

1. **평가 데이터 누수 제거** (`api/services/corpus_index.py`)
   `_scam_cases_from_eval()`을 완전히 삭제했다. 예전엔 평가세트 CSV의 사칭/경계 20행을
   `SCAM_CASES`(실제 매칭 코퍼스)에 그대로 편입시켜서, 이 CSV로 평가를 돌리면 각 케이스가
   **평가세트 자기 자신 또는 형제 케이스와 매칭**되는 자기참조 오염이 있었다.
   이제 `SCAM_CASES`는 `사례_20-46건_재라벨링표.csv`(30건, 운영 참조 데이터)만 쓴다.
   모듈 docstring에 "평가 데이터는 참조 코퍼스에 포함하지 않는다"를 명시했고,
   기동 시 코퍼스 적재 로그에 출처 파일명을 남긴다(재발 방지용 안전장치):
   ```
   INFO: [corpus] EVIDENCE 11건 적재 (출처: 근거_검증표.csv)
   INFO: [corpus] EVAL_CASES 30건 적재 (출처: 곁눈_평가세트_30건.csv, 평가/회귀 전용 - 매칭 코퍼스에 포함 안 함)
   INFO: [corpus] SCAM_CASES 30건 적재 (출처: 사례_20-46건_재라벨링표.csv만 - 평가세트 CSV는 제외)
   ```

2. **'확인 불가' 판정 로직 재설계** (`api/services/search.py`)
   - `source_missing`(발행기관 명시 여부)이 8개 특정 기관명("보건복지부·질병관리청·..." 등)을
     문자 그대로 포함해야만 "명시됨"으로 인정하던 것을, 공공기관 이름에 흔한 접미사
     패턴(`부/처/청/원/공단/공사/재단/센터/협회/위원회/복지로/정부24/건강보험/국민연금`)으로
     넓혔다. 또 이 신호의 severity를 attention → info로 낮췄다 — "이 신호 하나만으로
     의심/확인불가를 정하지 않는다"는 뜻이다.
   - verdict_hint 판정을 신호 조합 방식으로 다시 짰다:
     ```python
     risky = any(s["severity"] == "attention" for s in signals)
     if not refs:
         hint = "no_source_found"   # 확인 불가 - 기본값
     elif risky:
         hint = "partially_matched"  # 의심 - 사기 패턴 일치 또는 위험 신호
     else:
         hint = "needs_check"        # 확인됨 - 공식 출처 매칭 + 위험 신호 없음
     ```
     `official_source_found`/`source_missing`(둘 다 severity=info)은 더 이상 판정을
     막지 않는다 — 예전엔 "신호가 하나라도 있으면 의심"이었는데, 공식 자료를 찾았다는
     사실 자체가 info 신호로 signals 배열에 들어가는 바람에 `needs_check`가 구조적으로
     도달 불가능했다(§4-1 참고).

## 1. 핵심 지표 Before/After

| 지표 | Before(누수 있음) | After(수정 후) | 비고 |
|---|---|---|---|
| 실행 건수 | 30 | 30 | 실패 0건, 동일 |
| 근거 검색 성공률(references≥1) | 27/30 (90%) | **20/30 (67%)** | ↓ 누수 제거로 예상된 하락 (§2) |
| 기대판단 일치율 | 10/30 (33%) | **8/30 (27%)** | ↓ (§3에서 유형별로 상세 설명) |
| verdict_hint 분포 | partially_matched=27, no_source_found=3, **needs_check=0** | partially_matched=20, no_source_found=10, **needs_check=0** | 확인불가 3→10건으로 증가, 확인됨은 여전히 0건(§4-1) |
| 단정문 재생성 발생 케이스 | 4/30 (13%) | **8/30 (27%)** | ↑ (§5) |
| 재생성 발생율(시도 기준) | 9/39 (23%) | **15/45 (33%)** | ↑ |
| 폴백(3회 모두 실패) | 2/30 (7%) | **3/30 (10%)** | ↑ |

## 2. 유형별 상세 Before/After

| 유형 | 근거 검색 성공률 (Before→After) | verdict_hint 분포 (After) | 기대판단 일치율 (Before→After) |
|---|---|---|---|
| 정상 (기대: needs_check) | 7/10 → **4/10** | partially_matched=4, no_source_found=6 | 0/10 → 0/10 |
| 사칭 (기대: partially_matched) | 10/10 → **7/10** | partially_matched=7, no_source_found=3 | 10/10 → **7/10** |
| 경계 (기대: no_source_found) | 10/10 → **9/10** | partially_matched=9, no_source_found=1 | 0/10 → **1/10** |

### 관찰 1 — 근거 검색 성공률 하락(사칭 100%→70%, 경계 100%→90%)은 예상된 정상 현상이다

이전 보고서 §6-2에서 진단한 그대로다. 사칭·경계가 100%였던 건 각 케이스가 **평가셋에 있는
자기 자신 또는 형제 케이스**와 매칭됐기 때문이고, 그 통로를 없앴으니 낮아지는 게 맞다.
실측으로 확인했다 — B01이 매칭한 근거가 더 이상 자기 자신(B01/B05의 정답근거 문구)이 아니라
재라벨링표의 실제 사례(서울시 희망회복자금 문자 주의, 국세청 사칭 문자 주의)로 바뀌었다:

```
B01(경계) 매칭 근거:
  1) "공식/서울특별시·희망회복자금 선정대상 문자 클릭 주의"
  2) "공식/국세청·국세청 사칭 문자 메시지 주의 필요"
→ 둘 다 재라벨링표의 실제 항목이다. 더 이상 자기참조가 아니다.
```

사칭 케이스의 성공률도 10/10→7/10으로 떨어졌다 — 이제 진짜 30건짜리 재라벨링표 코퍼스만으로
승부해야 하니, 평가세트 문구와 우연히 겹치지 않는 사칭 시나리오 3건은 매칭에 실패한다.
**이 하락은 버그가 아니라, 부풀려졌던 수치가 실제 코퍼스 규모(30건)에 맞는 진짜 수치로
교정된 것이다.**

### 관찰 2 — 경계 케이스 일치율 0/10 → 1/10: 자기참조는 사라졌지만 근본적 한계는 남아 있다

경계 10건 중 9건이 여전히 `partially_matched`로 나온다. 다만 이제는 **진짜 재라벨링표 항목과의
키워드 중복** 때문이지, 자기참조 때문이 아니다(위 B01 예시 참고). 재라벨링표 30건만으로는
"실재하는 제도명 + 미묘한 위험 단서"라는 경계 케이스의 뉘앙스를 가려내기엔 코퍼스가 작고,
아래 §4-1에서 설명하는 것처럼 `match_scam_cases()`의 키워드 채점 방식 자체가 거칠다.

## 3. 확인됨(needs_check)이 여전히 0/30인 이유 — 새로 드러난 세 번째 원인 ★

이번에 고친 두 가지(데이터 누수, source_missing 좁은 키워드)는 실제로 고쳐졌다 — 로직을
검증하는 별도 스크립트로 확인했다:

```
국민건강보험공단에서 발표한 2025 고령자 통계... (공식 자료 매칭, 위험 신호 없음)
→ signals: official_source_found(info) 뿐 → risky=False → hint="needs_check"  ✓ 확인됨 도달 성공
```

**하지만 이번 30건 평가세트 자체에서는 needs_check 가 여전히 한 번도 안 나왔다.** 원인을
추적해 보니 이번에 고친 두 원인과는 **다른, 세 번째 원인**이 있었다:

`match_scam_cases()`는 텍스트에서 뽑은 키워드가 사기 사례의 `_blob`과 2개 이상 겹치면
매칭시킨다. 그런데 이 키워드 목록에 불용어 제거가 없어서, **"안내"·"지원"·"내용"처럼 거의
모든 공공기관 문구에 등장하는 일반 단어**만으로도 2점을 쉽게 채운다. 실측 예시(N01, 정상
유형 — "복지로 노후준비서비스 안내 페이지입니다. 지원 내용과 문의처를 확인하세요."):

```
매칭된 키워드: 안내, 지원, 내용  (모두 일반적인 공공 안내문에 흔한 단어)
매칭된 사기 사례: "국민지원금 신청·접수를 사칭한 스미싱 사례" 등 - 실제로는 무관한 내용
→ similar_scam_case 신호 발생(attention) → 정상 안내문인데도 '의심'으로 판정됨
```

즉 데이터 누수와 source_missing 문제를 고쳐서 needs_check 로 가는 길은 열렸는데,
`match_scam_cases`의 키워드 채점 방식이 일반 단어에 너무 관대해서 공식 자료를 찾은 대부분의
케이스가 사기 사례와도 함께 매칭돼 버려 결과적으로 `partially_matched`로 밀려난다.

**이번 작업 범위 밖이라 고치지 않는다.** 다음 후보를 남겨 둔다(진단만):
- 조사/일반 기능어뿐 아니라 "안내·지원·내용·확인·문의" 같은 공공문서 상투어를 불용어로
  추가 제거
- 키워드 빈도(코퍼스 내 등장 빈도) 기반 가중치 — 희귀한 단어의 일치에 더 높은 점수를 주는
  방식(TF-IDF류)으로 교체

## 4. 가드레일(재생성/폴백) — 증가했다(4→8건, 9→15회, 폴백 2→3건)

코드를 바꾼 대상(`corpus_index.py`/`search.py`)은 가드레일(`prompt_chain.py`)과 직접 관련이
없다. 하지만 대화 생성(`generate_question()`)은 evidence의 references/signals를 프롬프트
컨텍스트로 받는데, 이번 수정으로 references 개수와 신호 구성 자체가 달라졌다(§1) — 특히
근거를 못 찾는 케이스가 3건→10건으로 늘면서, Claude가 참고할 실제 자료 없이 스스로 질문을
구성해야 하는 상황이 늘었다. 재생성 사유는 이번에도 전부 `too_long`(6/8건) 또는
`forbidden_word`(1건)였다 — **이 원인(2문장 제한, 프롬프트 길이 제약)은 이번 요청에서 명시적으로
범위 밖으로 지정된 항목이라 고치지 않는다.** 다만 "근거가 없을 때 재생성이 늘어난다"는 상관관계
자체는 이번 재측정으로 새로 관찰된 사실이라 기록해 둔다.

## 5. 결론 요약 — 정직한 평가

- **데이터 누수는 실측으로 확인 및 제거됐다.** B01의 매칭 근거가 자기 자신에서 실제 재라벨링표
  항목으로 바뀐 것을 직접 확인했다.
- **source_missing의 좁은 키워드 문제도 고쳤다** — 별도 검증(§3)에서 "확인됨(needs_check)"에
  실제로 도달하는 입력을 만들어 확인했다.
- **그럼에도 이번 30건 평가세트 자체의 확인됨 비율은 0/30으로 그대로다** — 새로 드러난 세 번째
  원인(match_scam_cases의 일반 단어 과매칭) 때문이다. 두 가지를 고쳤다고 끝난 게 아니라,
  진단할수록 다음 단계가 보이는 구조라는 뜻이다. 이 세 번째 원인은 이번 작업 범위가 아니므로
  고치지 않고 다음 과제로 남긴다.
- **근거 검색 성공률·기대판단 일치율 하락은 버그가 아니라 교정이다** — 부풀려졌던 사칭·경계
  100%가 실제 코퍼스 규모(30건)에 맞는 진짜 수치(70%/90%)로 낮아졌다. 정상 케이스의
  근거매칭 70%(이전 보고서 기준)는 이번 재측정 대상이 아니다(코퍼스 규모 확장은 별도 과제,
  요청에 따라 이번엔 다루지 않음).
- **가드레일 재생성·폴백은 늘었다** — 근거가 줄어든 영향으로 보이며, 근본 원인(2문장 제한)은
  이번 범위 밖이라 고치지 않는다.

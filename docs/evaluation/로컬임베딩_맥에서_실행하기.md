# 로컬 임베딩 실험을 Mac 에서 돌리기 (2026-08-04)

지금까지의 측정은 **AWS EC2 Linux 서버(x86_64, 4코어, GPU 없음)** 에서 했다.
같은 실험을 Mac 에서 돌리려면 아래를 따르면 된다.

**왜 Mac 이 유리한가**: Apple Silicon(M 시리즈)에는 MPS(GPU 가속)가 있다.
서버에서 bge-m3 인덱싱에 **52분**이 걸렸는데, MPS 를 쓰면 훨씬 짧아질 가능성이
크다. 청크 크기·겹침을 바꿔가며 **재인덱싱을 반복해야 하는 실험**이라 이 차이가
그대로 실험 속도가 된다.

> ★ 다만 **속도만 빨라지는 것이지 정확도 수치가 달라지지는 않는다**(같은 모델·
> 같은 코퍼스). 부동소수 연산 순서 차이로 유사도 끝자리가 미세하게 흔들릴 수는
> 있으나, Recall@3·근거검색 성공률 같은 지표가 뒤집힐 정도는 아니다.
> 최종 수치를 보고서에 쓸 때는 **어느 장치에서 쟀는지 함께 적을 것.**

---

## 1. Docker 를 쓰지 말 것

Mac 의 Docker 는 리눅스 VM 위에서 돌기 때문에 **MPS(GPU)에 접근하지 못한다.**
컨테이너로 돌리면 Mac 의 최대 장점을 버리는 셈이라, Mac 에서는 **네이티브
Python 가상환경**으로 돌린다.

## 2. 준비

```bash
git clone https://github.com/zln02/gyeotnun.git
cd gyeotnun
git checkout feat/home-ui          # 실험 코드가 있는 브랜치

python3 -m venv .venv
source .venv/bin/activate
pip install -U pip

# 임베딩 실험에 필요한 것만 (OCR 실험까지 하려면 requirements-local-experiment.txt 전체)
pip install sentence-transformers==3.3.1 numpy
pip install -r api/requirements.txt      # rank-bm25 등 코퍼스 적재에 필요
```

`.env` 는 저장소에 없다(의도적). 상용 Upstage 와 비교하려면 프로젝트 담당자에게
`UPSTAGE_API_KEY` 를 받아 저장소 루트에 `.env` 로 두어야 한다. **로컬 모델
(bge-m3 등)만 돌릴 거면 키 없이도 된다.**

## 3. 실행

```bash
cd api
python3 tools/bench_local_embeddings.py bge-m3
```

경로는 자동 판별된다 — 컨테이너(`/app`)든 로컬 체크아웃(`<repo>/api`)이든
같은 스크립트가 그대로 돈다. 별도 설정이 필요 없다.

### 장치 확인

실행하면 로그 첫 줄에 어느 장치를 쓰는지 찍힌다.

```
[local_embeddings] 실행 장치: mps        ← Apple Silicon 정상
[local_embeddings] 실행 장치: cpu        ← Intel Mac 이거나 MPS 미지원
```

강제로 고정하고 싶으면(예: 서버 결과와 정확히 맞춰 비교할 때):

```bash
EMBED_DEVICE=cpu python3 tools/bench_local_embeddings.py bge-m3
```

## 4. Mac 에서 주의할 점

| 항목 | 내용 |
|---|---|
| **모델 다운로드** | bge-m3 는 약 2.2GB. 최초 1회 HuggingFace 에서 받는다. `HF_HOME` 을 지정하지 않으면 `~/.cache/huggingface` 에 쌓인다 |
| **메모리** | bge-m3 상주 약 1.1GB, bge-m3-ko 약 2.2GB. 8GB Mac 이면 다른 앱을 닫는 편이 안전하다 |
| **MPS 미지원 연산** | 드물게 MPS 가 특정 연산을 지원하지 않아 오류가 날 수 있다. 그럴 땐 `PYTORCH_ENABLE_MPS_FALLBACK=1` 을 붙이거나 `EMBED_DEVICE=cpu` 로 돌린다 |
| **Intel Mac** | MPS 가 없으므로 CPU 로 동작한다. 서버와 비슷하거나 더 느릴 수 있다 |
| **결과 파일** | `api/data/local_embeddings_bench.json` 에 누적 저장된다(`api/data/` 는 gitignore). 후보를 나눠 돌려도 합쳐진다 |
| **인덱스 파일** | `api/data/local_embeddings/local_index_{후보}.npz`. 후보별로 분리되고 모델명·차원수를 검증하므로 섞일 위험은 없다 |

## 5. 청크 크기 실험을 한다면

현재 튜닝 후보로 지목한 값들이다(자세한 배경은 아래 §6).

```python
# api/services/corpus_index.py
_CHUNK_TARGET_CHARS = 900     # ← 현재값. 300~500 으로 낮추는 실험
```

이 값을 바꾸면 **청크 수가 바뀌므로 반드시 재인덱싱**해야 한다. 후보 인덱스
파일을 지우고 다시 돌리면 된다.

```bash
rm api/data/local_embeddings/local_index_bge-m3.npz
python3 tools/bench_local_embeddings.py bge-m3
```

> ★ 주의: `corpus_index.py` 는 **프로덕션 코드**다. 실험하려고 값을 바꿨다면
> **커밋하지 말고 되돌릴 것.** 확정된 값만 별도 논의 후 반영한다.

## 6. 현재 튜닝 여지 요약

| 레버 | 현재값 | 근거 | 재인덱싱 필요 |
|---|---|---|---|
| `_CHUNK_TARGET_CHARS` (corpus_index.py) | 900 | 근거 주석 없음 | **필요** |
| 청크 겹침(overlap) | 없음 | — | **필요** |
| `limit` (반환 문서 수, embeddings.py) | 2 | 근거 주석 없음 | 불필요 |
| `EMBEDDING_MIN_SCORE` | 0.45 | 실측 근거 있음(잡음 0.23~0.35 vs 정상최저 0.5378) | 불필요 |
| `CONFIDENT_MATCH_THRESHOLD` (search.py) | 0.52 | 실측 근거 있음(경계최대 0.5058 vs 정상최저 0.5378) | 불필요 |

현재 코퍼스는 문서 996건 → 청크 1,882개(**문서당 1.9개**)다. 900자면 문서 하나가
한두 청크에 통째로 들어가서, 뒷부분의 구체적 내용(신청 조건·금액)이 앞부분 총론에
희석된다. 300~400자로 줄이면 청크가 4~6배 늘어 특정 조건을 묻는 질의에 더 정확히
걸릴 가능성이 있다 — **가설이고, 측정해서 확인할 대상이다.**

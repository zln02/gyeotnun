# 마스킹 파이프라인 재현율 측정 (2026-08-09)

- 대상: `api/services/masking.py` `mask_text(text) -> MaskResult`
- 평가 세트: `tests/eval/masking_cases.json` — **합성 138건 / PII 필드 156개**
- 측정 스크립트: `tests/eval/eval_masking.py`
- 파이프라인 위치: 업로드 → OCR(`ocr.py`) → **`mask_text()`** → DB 저장(`masked_text`)

## 0. 먼저 알아야 할 것 — 5개 유형 중 2개는 구현 자체가 없다

`mask_text()` 가 처리하는 유형은 **주민등록번호 · 카드번호 · 전화번호 · 계좌번호** 4종이다.
**이름과 주소를 다루는 코드는 한 줄도 없다.** 정규식도, 사전도, 호출부도 없다.

따라서 이름·주소의 재현율 0% 는 "패턴이 약해서 놓쳤다"가 아니라
**"측정 대상 기능이 존재하지 않는다"** 는 뜻이다. 이 구분이 아래 표를 읽는 전제다.

## 2. 고친 것 — 패턴 보강 3가지 (10건 회복)

| # | 보강 | 회복된 케이스 |
|---|---|---|
| 1 | 국번 뒤 **닫는 괄호만** 쓰는 표기 `02)731-2048` 허용 | P10 |
| 2 | **OCR 혼동문자 정규화**(O/o→0, l/I→1, 키릴 О→0, З→3) — 전화·주민번호 매칭에만 적용 | P11 P12 P14 P15 P27 M06 R07 R17 |
| 3 | **자간 벌어진 전화번호** 전용 패턴 (`0 1 0 - 0 4 8 2 - 7 3 6 5`) | P13 |

### 안전 설계 두 가지

**(a) 정규화는 매칭에만 쓰고, 치환은 원본 위치에 한다.**
`_sub_on_normalized()` 가 정규화본에서 찾은 구간을 원본 문자열의 같은 인덱스에
치환한다. 각 대응이 1글자→1글자라 인덱스가 정확히 보존된다.
정규화된 문자열이 본문으로 새어 나가면 안 되기 때문이다.

**(b) 계좌·카드에는 정규화를 적용하지 않는다.**
계좌·카드는 "자릿수만 맞으면 후보"인 느슨한 패턴이라, 글자를 숫자로 바꿔 주면
오탐이 늘어난다. 전화(`01x/07x/0x`)·주민번호(`6자리+[1-4]`)는 앞자리가 형태를
강하게 제약해 오탐 위험이 낮다.

자간 패턴은 느슨해서 replace 단계에 가드를 뒀다 — **공백이 실제로 섞여 있고
숫자가 정확히 10~11자리일 때만** 전화번호로 인정한다.

### 회귀 확인

| 검사 | 결과 |
|---|---|
| `api/tests/test_masking.py` | **17 passed** |
| 전체 `pytest -q` | **79 passed** |
| 평가셋 30건 · 홀드아웃 5건 `verify_scam_fix.py` | 정상 오판 **0** / 사칭 위험신호 **10/10** / 홀드아웃 실패 **0** → 채택 가능: 예 |
| 수정 전/후 마스킹 출력 비교 (평가셋30 + 홀드아웃5 + 실사용SMS + OCR실측 + **공식문서 1,017건** = 1,058건) | **달라진 건 1건** |

그 1건은 공식문서 코퍼스의 LH 대표번호 표기다:

```
전: LH 공사 본사강원지역본부033)760-6242
후: LH 공사 본사강원지역본부033-****-****
```

★ 이 문서들은 **마스킹을 거치지 않는다**(`mask_text()` 는 사용자 업로드
텍스트에만 적용된다). 실제 동작에는 영향이 없다. 다만 신호로 읽으면:
보강 ①이 `033)760-6242` 형태의 **기관 대표번호**도 마스킹한다는 뜻이다.
종전에도 `(033)760-6242` 와 `033-760-6242` 는 마스킹됐으므로 **새로운 종류의
과잉이 아니라 표기별 불일치가 해소된 것**이다.

## 4. 과잉 마스킹 (참고치)

비-PII 토큰 24개 중 마스킹된 것은 **1건**이다.

| ID | 토큰 | 결과 |
|---|---|---|
| A13 | `214-88-04920` (사업자등록번호) | `사업자등록번호 ***-***-****** / 입금 계좌 ***-***-******` |

원인: 같은 문장 안 24자 이내에 `계좌` 가 있어 문맥 검사를 통과했다.
문맥어 창(24자)이 **문장 경계를 모른다**. 사업자등록번호 단독 문장(A11)과
접수번호 단독 문장(A12)은 정상적으로 보존되므로, 이 오탐은 "계좌와 나란히
적힌 다른 번호"에 한정된다.

수정하려면 문장 단위 분리나 `사업자등록번호/접수번호/고유번호` 같은
**부정 문맥어를 계좌 쪽에도 추가**해야 한다(카드에는 이미 있다).
1건짜리 과잉이고 안전한 방향(과잉 → 덜 지움)으로 바꾸는 변경이라
성급하게 넣지 않았다. 제출 후 처리 후보로 남긴다.

### 부분 누출 1건은 지표의 오탐이다

`A29 계좌 352-0492-073193` 가 마스킹된 뒤에도 숫자 `0492` 가 남았다고 잡혔는데,
그 `0492` 는 **같은 문장의 사업자등록번호 `110-82-04920` 의 일부**다.
계좌 자체는 정상 마스킹됐다. 실제 누출이 아니다.
(지표가 값 안의 숫자 덩어리를 전역 검색하기 때문에 생기는 교차 일치다.)

## 5. 평가 세트의 개인정보 안전장치

`tests/eval/gen_masking_cases.py` 가 규칙으로 생성하고, 생성 시점에 강제 검증한다.

1. **주민등록번호는 전부 검증식(체크섬)을 고의로 틀린 값**이다. 생성기가
   `rrn_checksum_ok()` 로 검사해, 발급 가능한 형태가 하나라도 있으면 즉시 중단한다.
   → 실제 발급 가능한 번호는 **0건**.
2. 휴대전화 중간 그룹은 원칙적으로 **국내 미할당 대역(0 으로 시작)**을 쓴다.
   예외는 지시서에 명시된 함정 예시(`010-1234-5678` 계열)뿐이며, 이는 국내
   문서에서 관용적으로 쓰는 예시값이다.
3. 계좌번호는 실제 은행의 자릿수 규칙을 따르지 않는 합성값이다.
4. 주소는 실재 도로명을 쓰되 번지는 가공값이고, 특정 개인과 연결되지 않는다.
   (`서울 강남구 테헤란로 123` 은 지시서에 제시된 예시를 그대로 썼다.)

### ★ 한계 — 정직하게 적는다

**한국 성명은 조합 수가 적어 "실존 인물과 절대 겹치지 않는다"를 증명할 수 없다.**
유명인·공인의 성명을 피하는 선에서 관리했고, 관용 예시명(`홍길동`)조차
실존 인물 오인을 피하려고 배제했다. 그러나 `김민준`·`박서윤` 같은 이름은
통계적으로 실존 동명인이 있을 수밖에 없다. 이 파일의 이름은 **누군가를
가리키는 데이터가 아니라 문자열 패턴 시료**로만 쓰인다.

## 6. 정리

- **구현된 유형(전화·주민·계좌) 재현율 86.7% → 97.8%.** 전화·주민번호는 각각
  100.0% 가 됐다. 패턴 보강 3가지로 10건을 회복했고, 회귀는 없다
  (79 passed, 30건·5건 게이트 유지).
- **계좌 2건은 고치지 않았다.** 재현율보다 과잉 마스킹 억제를 택한 설계고,
  masked_text 가 판정 입력이라는 구조 때문에 그 선택이 옳다.
- **이름·주소는 기능이 없어 0%다.** 이건 측정 결과가 아니라 **구현 공백**이다.
  넣으려면 NER 급 작업이고, 넣는 순간 판정 입력이 훼손될 위험이 있다.
  → **제출 전에 넣을 것을 권하지 않는다.** 대신 이 리포트로 공백을 명시한다.
- 과잉 1건(A13)은 문맥 창이 문장 경계를 모르는 데서 온다. 안전한 방향의
  수정이라 제출 후 후보로 남긴다.
